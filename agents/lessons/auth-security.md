> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** your diff touches auth middleware, secrets, tokens, allow-lists, bypass flags, a fail-closed gate, session capture/telemetry redaction, or decoding attacker-supplied input.

- **A new X-Node-Secret / internal endpoint is UNREACHABLE until its path is registered in `TenantAuthMiddleware` — handler-level auth never runs otherwise (2026-07-10):** C9FE02 built `POST /internal/pipeline/auto-file` (router prefix `/internal/pipeline`) with a correct in-handler `X-Node-Secret` fail-closed check, but `backend/app/middleware/tenant_auth.py` exempts the REVERSED prefix `/pipeline/internal/` plus a fixed `NODE_SECRET_EXEMPT_ROUTES` list — neither matches `/internal/pipeline/*`. Automated callers send only `X-Node-Secret` (no Bearer JWT), so the middleware 401s them at the Bearer fallthrough BEFORE the handler runs → the whole feature is dead. When adding any machine/internal endpoint: (1) grep `tenant_auth.py` and confirm the exact path is covered by `PUBLIC_PATHS`, a prefix check at the `call_next` line, `PUBLIC_POST_PATHS`, or `NODE_SECRET_EXEMPT_ROUTES` — a fail-closed handler check is NOT enough on its own; (2) prefer reusing an already-exempt prefix (here `/pipeline/internal/`, which the codebase already exposes) over inventing a new top-level path that needs a fresh middleware edit; (3) mind prefix ORDER — `/internal/pipeline` ≠ `/pipeline/internal`. Rejected at gate; fix: CASE-20260710-AF9C01. **RECURRENCE 2026-07-26 (CASE-20260726-5A81AD merged-with-fix → CASE-20260726-SYNCWR), and the variant that looks MOST covered: the router's SIBLING endpoint was already exempt.** `POST /internal/scantap/converge-intervals` was added to `routers/scantap_internal_sync.py`, whose other endpoint `POST /internal/scantap/sync-run` IS exempt — but every `NODE_SECRET_EXEMPT_ROUTES` entry is a `$`-ANCHORED per-path regex (`r"^/internal/scantap/sync-run/?$"`), and the only startswith prefixes are `/api/v1/nodes/` and `/claude-app/runner/` (the `dispatch()` list has `/pipeline/internal/`, NOT `/internal/`). So "my router's existing route works from the scheduler" is NOT evidence the new one is reachable — exemption is per PATH, never per prefix or per router. Author rule: adding an endpoint to an already-exempt internal router still requires its own `NODE_SECRET_EXEMPT_ROUTES` line. Gate rule: don't eyeball the regex list — EXECUTE the real matcher against the new path and its working sibling and compare (`exec` the constants block out of `tenant_auth.py`, then `_is_node_secret_exempt("POST", p)` for both); `False` vs `True` turns "looks unregistered" into an audit fact in one command. Second half of the same defect: a node-secret handler that acquires a tenant pool must ALSO `set_current_tenant_id(str(body.tenant_id))` before `get_pool_for_tenant` — a `placement='pooled'` tenant gets the SHARED shard pool whose per-acquire init calls `get_current_tenant_id()` and RAISES with no ContextVar (there is no TenantAuthMiddleware on an exempt path), so the endpoint 500s for pooled tenants only; copy the pattern from `routers/print_cloud_agent.py:75` / `routers/documents.py:1081`.
- **NEVER hardcode a real secret as an `||` fallback in a test spec — even in a fully-mocked test, a production secret literal committed to git is a permanent leak requiring rotation, not just a code fix (2026-07-13):** review-gate 2026-07-13 CASE-20260713-776BBF (products QA Playwright spec) set `const JWT_SECRET = process.env.JWT_IMPERSONATION_SECRET || 'df4cd8ce…aa61b'` — and that literal, byte-for-byte, EQUALS the real `grotap/prd` Doppler `JWT_IMPERSONATION_SECRET` (verified by hashing both). The spec mocks ALL backend APIs so the JWT is never actually verified (the secret is functionally dead weight), which is exactly why the fallback looked harmless to the author — but the value is now in git history forever and can forge impersonation tokens against any env still using it. It was NOT a new leak: 5 pre-existing master specs (`agent-store`, `agent-team-dashboard`, `brand-lock`, `platform-brand`, `suggest-submit-50`) already carry the identical literal — a systemic pattern. Correct fallbacks already in-repo: `ag-grid-license-smoke.spec.ts` throws if the env var is absent; `test_auth_brand_filter.py` uses a dummy `"test-secret"`. Gate action: merged the test-only branch (156 committed e2e PNGs already establish that screenshot convention; backend filtering test already lived on master as `test_products_presentation.py`) but stripped the literal to a `'test-secret'` dummy in the merge (fix commit c0848167), filed P1 CASE-20260713-SECFIX1 to sweep the 5 master files, and flagged that the code fix does NOT remediate the historical exposure — the owner must ROTATE the secret in Doppler prd+dev and refresh every Railway copy. Author rule: a test JWT signed with a secret the backend never checks (mocked APIs) needs only a dummy `'test-secret'`; a test that hits a real backend needs the env var with a throw-if-absent guard — NEVER embed the literal. Gate rule: grep any e2e/test branch for hex-looking `|| '…'` fallbacks and byte-compare against live Doppler secrets before merge.
- **A bypass/allow-flag for a cross-cutting concern (rate-limit, auth, blocklist, feature-gate) must cover EVERY layer that enforces it — the platform enforces abuse-defense in TWO middlewares, so wiring the bypass into only the named one silently leaves the other half enforcing (2026-07-19, review-gate MERGE+FIX of CASE-20260719-5F0E20):** the case asked for a load-test bypass (`LOADTEST_BYPASS_TOKEN`/`X-Loadtest-Token`, constant-time `hmac.compare_digest`) to "skip rate-limit checks, strike delays/blocks, and blocklist enforcement." The branch wired it correctly into `RateLimitMiddleware` (`rate_limit.py`, Tier-1 per-IP) and even set `request.state.is_loadtest=True` — but `TenantAuthMiddleware` (`tenant_auth.py`) runs INSIDE RateLimit and enforces a SEPARATE full Tier-2 stack (blocklist api_key_prefix + org via `match_api_key_prefix`/`match_org`, `is_strike_blocked`, `apply_strike_delay`, org/user 240-rpm `rate_limit_incr`, `handle_429` auto-block) that never reads the flag. So authenticated load traffic is still throttled/blocked at 240 rpm/org — the feature is inert for the realistic (tenant-endpoint) load case, while the startup log prints "bypass ACTIVE." Safe to MERGE (fully inert unless the token env is set; bypasses LESS than intended = no added exposure; no bad data / no auth break) but incomplete — filed CASE-20260719-LTBP2X to honor `request.state.is_loadtest` in tenant_auth. Author rule: when a task names ONE enforcement point for a cross-cutting concern, `git grep` the enforcement primitives (here `is_strike_blocked`/`apply_strike_delay`/`get_active_entries`/`rate_limit_incr`) across `backend/app/middleware/` and wire the bypass into every hit — prefer setting a `request.state` flag in the outermost enforcer and reading it in the inner ones (single constant-time compare). Gate rule: for any bypass/allow-flag/kill-switch case, grep for sibling enforcers of the same concern before accepting single-layer coverage; a bypass that only covers Tier-1 is a MERGE-with-fix (or FIX if the misleading "active" state could burn a scheduled run window).
- **A fail-closed check on one app's OPTIONAL secret must NEVER abort platform boot — not in the `main.py` lifespan and not at MODULE scope in anything imported at boot. Warn at import, fail closed at REQUEST time (2026-07-19, review-gate batch17 + batch20/21; two occurrences, merged 2026-07-25):** aborting boot for an app-scoped secret converts a single-endpoint 500 into a whole-platform outage on every deploy lacking that var, and Railway then pins the old image and blocks ALL future deploys — unrelated apps included — until it is set. (a) `main.py` lifespan, CASE-20260719-B6B7B0 (hunk REJECTED, its 2 test files merged alone via `git checkout <branch> -- tests/...`): the branch replaced master's `logger.critical("GOOGLE_SERVICE_ACCOUNT_JSON is not set …")` with an unconditional `raise RuntimeError(...)` gated only on env-var presence, NOT on whether the Drive app is enabled — while `core/config.py` explicitly documents empty = `Drive integration disabled` (503 on that route) as a SUPPORTED state and `google_drive_provider._load_sa_json()` already raises at request time. (b) Module scope, CASE-20260719-19F4C7 → -19F4FX, the SAME bug one layer down and the 2nd occurrence in one case (batch20 SKIP'd it, it came back unchanged): `backend/app/services/strike_engine.py` added, at module top level, `if os.environ.get("LOADTEST_TEST_ORG_IDS") is None: raise RuntimeError(...)`. `strike_engine` is imported at boot via `rate_limit.py`, that var is CONFIRMED ABSENT in Doppler grotap/prd → RuntimeError at import → whole backend fails to boot. Correct handling: default a missing/empty value to an empty frozenset and log ONE warning. Rule: only secrets required by CORE platform paths (auth, DB, control-plane) may hard-abort boot; an app-scoped integration logs at boot and fails closed in its provider at request time. Gate rule: grep every diff for a bare `raise`/`sys.exit`/`assert` at module scope (not inside a function) under `services/`, `providers/` or `core/`, plus any lifespan `raise` on an app-scoped secret — reject both. `py_compile` is blind here; `python -c "import app.main"` under the prod env catches it.
- **Verifying an invite/reset/magic link by reading the delivered mail through the Gmail MCP: `htmlBody` DOUBLE-DECODES quoted-printable, so any `=` followed by two hex digits is eaten — a perfectly good link reads as corrupt and you will file a P0 that does not exist (2026-07-28, beta-invite path verification):** `?token=f33ccacd-…` came back as `?token<U+FFFD>3ccacd-…` because `=f3` is a well-formed QP escape decoding to byte 0xf3 (invalid UTF-8). It is READ-side only — the wire is clean. The trap is that it looks selective and therefore real: the four invite links verified earlier the same day survived untouched because their WorkOS base62 tokens began `=kA`/`=SR`, which are NOT hex pairs, so "only the beta path is broken" is exactly what a healthy system looks like through this tool. UUID tokens are all-hex and corrupt 100% of the time; base62 tokens corrupt ~7%. Decide it by observation, not inference: send one control mail whose HTML and plaintext parts are worded DIFFERENTLY (`text` must be set explicitly — Resend otherwise generates plaintext FROM the html and both parts read alike, which is what makes control #1 inconclusive), then compare Gmail's server-side `snippet` — its own independent decode — against `htmlBody`; snippet intact + htmlBody mangled = read-path artifact, both mangled = a real send-side encoding bug. `plaintextBody` is also trustworthy (it is not QP), so for a quick link check read that, never `htmlBody`. Same class as the frontend `textContent`-sees-invisible-text lesson: **the instrument can corrupt the evidence, so confirm a suspected defect through a second, independent decode before filing.**
- **An agent-worker→backend machine call MUST target an endpoint that is BOTH listed in NODE_SECRET_EXEMPT_ROUTES AND accepts dual-auth (_resolve_tenant), and MUST read that endpoint's ACTUAL response keys — /agent-context/master is JWT-only and NOT exempt, so a node-secret call to it 401s and a soft-failing feature silently does nothing (2026-07-24, review-gate, CASE-20260720-A87351 REJECTED → CASE-20260724-A87351FX):** fetchMasterContext() in agent-worker `context-client.ts` called `GET /agent-context/master` with X-Node-Secret+X-Tenant-Id, but backend `get_master_context()` uses `_get_tenant` (JWT-only) and the middleware only exempts `^/agent-context/composed/?$` → 401 at the middleware AND again at the handler; even had it passed, `/master` returns `{content,version,updated_at,is_template}` while the client read `raw.master_md`/`raw.master_version` → both undefined → empty context injected → feature is a no-op. The machine path is `/agent-context/composed` with NO loop_id (dual-auth, exempt, returns `{master_md,master_version}`) — the sibling `fetchAgentContext` in the SAME file already uses it correctly. This keeps recurring (see B7848D, F9BFIX). Reviewer tell: any worker fetch sending `X-Node-Secret` must hit a path in NODE_SECRET_EXEMPT_ROUTES and its field reads must match that handler's real return keys — a green tsc proves neither (the response type is author-declared).
- **Session-capture / replay defaults are NOT privacy-safe, and the vendor's "mask everything" switch is the trap that looks like the fix: rrweb's `maskAllInputs: true` expands to a FIXED list of input *types* that OMITS `hidden`, `file`, `checkbox`, `radio`, `submit` and `button` — so a CSRF or session token in `<input type="hidden">` is recorded in the clear — and it OVERRIDES any `maskInputOptions` passed alongside it, silently discarding the more specific config you added to compensate (2026-07-30):** mask by TAG NAME (`input`/`textarea`/`select`), which rrweb checks BEFORE the type, so a type it has never heard of cannot leak. Read the flag's implementation rather than its name for any capture/telemetry/logging redaction switch — "all" in a vendor option nearly always means "all of an enumerated list written years ago". Second half, and the reason this shipped: **a test that asserts the masking CONFIG proves nothing — assert on the SERIALIZED CAPTURED OUTPUT.** Put a known sentinel value into the DOM, run the recorder, and assert the sentinel does not appear anywhere in the emitted event stream; and pair it with a POSITIVE control (a field that must be captured), because without one an emitter that captured nothing at all passes every redaction assertion vacuously. Same family as the frontend `textContent`/`getComputedStyle` lesson: assert on what the system actually produced, never on the settings you asked it for.
- **Enforce a size limit BEFORE decoding, never after — and always pass `validate=True` (2026-07-30):** a handler that runs `raw = base64.b64decode(payload)` and then checks `len(raw) > MAX` has already performed the attacker's allocation, so the cap defends nothing; bound the ENCODED length first (`len(payload) > MAX * 4 // 3` → reject) and only then decode. Independently, Python's `b64decode` WITHOUT `validate=True` silently DISCARDS every character outside the base64 alphabet, so truncated or corrupted input decodes to plausible garbage and is stored as if it were real — the write succeeds and the corruption is only found later, in the data, with no error anywhere in the logs. Generalize to every decode/decompress/parse of untrusted input (gzip, JSON, image, archive): validate the bound on the WIRE form, and turn on the library's strict/validating mode rather than accepting its lenient default.

- **An auth guard must key off token VALIDITY, not token PRESENCE, and the app must always expose a way to drop the session — otherwise an expired credential locks the user out of the login screen that would fix it (2026-07-28, commit 380155dd):** Scan M's root layout routed on `token ? home : login`, so an EXPIRED token still counted as signed-in and bounced every attempt to re-authenticate; with no logout anywhere in the app the only escape was `pm clear`, which also destroys locally queued offline data. Compounding it, the guard read the token ONCE at mount and never re-read it, so a SUCCESSFUL login bounced back to an empty form (the credential was saved — only a relaunch revealed it), training users to retype a token that had already worked. Author rule: hold session state in ONE observable store that both the login path and the API layer publish to, have the API layer sign out on a 401 (so "expired" becomes "absent" and the guard resolves itself), and ship an explicit logout that clears ONLY the credential — never the queued data. Reviewer tell: a guard whose token comes from a `useState` + one-shot `useEffect` read, rather than a subscription, cannot react to any auth change made after mount.

- **A secrets script's "key already exists → do NOT rotate" guard must be proven by EXECUTING it, never by reading it: `doppler secrets --only-names` prints a BORDERED ASCII TABLE even when piped (no TTY), so the idiomatic `| grep -qx "KEY"` can never match and the script silently ROTATES a live secret on every re-run (2026-08-10, review-gate, CASE-20260810-CLAM01 merged as 758421ab → fix CASE-20260810-CLAM01C):** verified on doppler v3.76.0 — `doppler secrets --only-names | grep -qx "DATABASE_URL"` exits **1** for a key that certainly exists, while `doppler secrets --only-names --json | jq -e 'has("DATABASE_URL")'` exits 0 (`--json` emits `{"KEY":{},…}`; `--plain` is NOT a flag on `doppler secrets`, only on `doppler secrets get`). The guard therefore always falls through to `doppler secrets set "KEY=$(openssl rand -hex 32)"` while printing "Generating secret and uploading…", which is indistinguishable from correct first-run output — no error, no non-zero exit. What turns a dead guard into an outage is the blast radius of an ACCIDENTAL rotation, and it is three-way: the same branch made `deploy.sh` short-circuit on an existing `.env.runtime` (`if [[ -f .env.runtime ]]` → "Using existing"), so the box keeps the OLD secret and a redeploy still reports success, and per CLAUDE.md the Railway copy is a STATIC copy that also goes stale — so under a fail-closed consumer every request 401s and the symptom points a debugger at the header/middleware, not at a secret that rotated itself days earlier. Author rule: an existence/idempotency check over ANY CLI must parse a MACHINE-READABLE mode (`--json`, `-Atc`, `--format`), and must be executed against both a present and an absent key with the two exit codes recorded in the case notes — a guard whose condition can never match silently converts "skip" into "do it again" (same family as the never-matching idempotency predicate in `state-jobs.md`; the CLI-format variant is worse because the wrong branch is the DESTRUCTIVE one). Never write an idempotency claim into a script's header comment that the code does not deliver: that comment is precisely what persuades the next operator it is safe to re-run — here `docs/deployment/CLAMAV_GO_LIVE.md` §1 already tells them to "re-run that script on the box". And for any script that may overwrite an existing secret, require an explicit `--rotate`/`FORCE_ROTATE=1` and print only a FINGERPRINT (`sha256 | cut -c1-8`) of what it wrote, so the value stays unlogged but drift between Doppler, the box and Railway is visible. **Widened by a second defect in the same stack (2026-08-10, review-gate, CASE-20260810-CLAM01B merged 7c944749; same fix case CLAM01C): every CLI FLAG in a secrets script needs the same execute-it-once proof, because `set -euo pipefail` makes a bad flag destructive.** `deploy.sh` had shipped `doppler secrets download --format env --no-file --only-keys CLAMAV_SCAN_SECRET > .env.runtime` since before CLAM01, but `--only-keys` does not exist on `doppler secrets download` (v3.76.0: `Error: unknown flag`; the help lists NO key-filtering flag at all) — and because the shell truncates the redirect target BEFORE the command runs, the abort leaves a 0-byte `.env.runtime` that the file-first branch above then happily reuses forever. Two rules fall out. (1) A flag you have not executed is a guess: `--plain` is valid on `doppler secrets get` but NOT on `doppler secrets` or `doppler secrets download`, and `--value` does not exist on `doppler secrets set` at all — near-identical subcommands do not share flags, so check the one you are actually calling. (2) The naive fix to a rejected FILTERING flag is the dangerous one: `doppler secrets download` cannot filter keys, so deleting `--only-keys` writes EVERY prd secret into the `env_file` of the container whose entire job is parsing hostile files, on the box the roster documents as deliberately holding no Doppler token — write the single `KEY=value` line from `doppler secrets get --plain` instead, and chmod/umask it before the value lands. Corollary for the read side: `--format env` QUOTES values (`DOPPLER_CONFIG="prd"`), so an operator snippet doing `grep KEY .env.runtime | cut -d= -f2-` ships the quotes inside the auth header and gets a 401 that looks exactly like a rotated secret — source the file (`set -a; . ./file; set +a`) or use `--format env-no-quotes`. Four more traps in this same family, all found on the same file. (1) Do NOT "fix" a never-matching `grep -qx` by relaxing it to a substring grep — on table output that then matches a longer NEIGHBOUR (`CLAMAV_SCAN_SECRET_OLD`) and skips generation wrongly; the anchor was never the bug, the format was. (2) Decide the guard's FAIL DIRECTION explicitly: if the listing command itself fails (revoked token, wrong config, no network) the pipeline yields zero lines and the script rotates — so capture the listing, `exit 1` on a non-zero exit, and only then test for the key, because "could not determine" must never fall through to "generate a new one". (3) `deploy.sh`'s `if [[ -f .env.runtime ]]` short-circuit means even a DELIBERATE redeploy cannot repair the drift it caused — a refresh path (or at least a fingerprint comparison against Doppler) has to exist, or the documented recovery step is a no-op that reports success. (4) None of this is reachable by any gate — `py_compile`/`tsc`/jest never execute a shell script, so a dead guard and a broken flag are invisible to CI forever: the only proof is running the guard's condition against the real CLI and pasting both exit codes. Related, same script: pass a generated secret on STDIN, never in argv — `doppler secrets set "KEY=$(openssl rand -hex 32)"` puts the plaintext in `/proc/<pid>/cmdline` and `ps` for any local user, while `doppler secrets set --help` documents stdin as the RECOMMENDED method (`openssl rand -hex 32 | doppler secrets set KEY --no-interactive`); and verify a flag exists before trusting a diff that removes one — `--value` is NOT a flag on this CLI version, so the pre-fix form was already broken and the removal was correct.
- **A token minted by ONE issuer cannot survive a refresh handled by ANOTHER — /auth/switch-company mints a local 1-hour JWT scoped to the chosen org, but /auth/refresh re-authenticates against WorkOS, whose refresh token is bound to the ORIGINAL sign-in session, so the refreshed token silently re-scopes the session to a different company an hour in (2026-08-10, apps.grotap.com account switcher):** the tell was cosmetic — a blue ✓ beside BOTH companies in the switcher after a long session — but the real defect was that the session had actually MOVED, while localStorage still named the company the user picked; the switcher merely reported both stories at once. Two rules. (1) Whenever a scoped/impersonation/step-up token can be replaced by a generic refresh, re-apply the scope after every refresh (re-mint through the membership-gated endpoint) or the scope silently expires with the token — and note a claim can go MISSING rather than wrong: a WorkOS token with no `org_id` sends `tenant_auth` down its `memberships[0]` fallback, which for a two-org user is a coin flip. Re-mint with RAW axios, never the shared instance, or the 401 interceptor re-enters `refreshAccessToken()` and awaits the very promise it is running inside. (2) For any "exactly one of these is active" UI, resolve ONE id first and compare rows by equality — `active = row.id === ctxId || row.is_current` OR-s two sources that are only equal until they aren't, and makes the double-selected state representable; ordering the sources by authority (live token claim → client context → server snapshot) also fixes WHICH one is right, not just how many. Same family as the `is_default`/`is_current` sibling flags: two booleans that must sum to one are a single id wearing a disguise.
- **An access-control bypass must be gated on the OUTCOME it justifies, not on the caller's INTENT — and before accepting any bypass condition, evaluate it against the endpoint that actually reaches it: on a route that already requires the privileged identity, an `is_admin`-style guard is ALWAYS TRUE, so the enforcement it wraps becomes dead code (2026-08-14, review-gate batch-4, CASE-20260814-D34FA1 REJECTED → CASE-20260814-7C2E19):** the branch wrapped the Drive specs-folder block and `drive_settings.allowed_folder_ids` in `if not (is_grotap_admin and tenant_pool and tenant_id):` inside `google_drive_service.read_file_content()`, with `_gdrive_is_admin = tool_ctx.user_email.endswith("@grotap.com")` set in `claude_app.stream_chat()`. But `stream_chat()` opens with `email = await _require_grotap(request)`, which 403s every non-Grotap caller, and `tenant_pool`/`tenant_id` are always set by tenant-auth on an authenticated request — so all three conjuncts are always true, the condition is always False, and commit 065b705b's per-tenant folder allowlist is enforced for nobody (the only other caller, `routers/tools/drive.py:42`, passes no `drive_settings` and never enforced either). The INTENT-vs-OUTCOME half is what made it worse than the branch it was porting: the superseded version gated on `using_tenant_sa` (a tenant SA had actually been loaded), while this one moved the gate up a layer where it can only test that a tenant SA was *requested* — so when `_load_tenant_drive_sa_json()` returns None (no verified credential, `LOOP_ENGINE_ENC_KEY` unset, decrypt failure) the provider falls back to the PLATFORM service account with enforcement already skipped. Author rule: a per-tenant consent control (allowlist, retention, redaction, region) governs regardless of WHICH credential performs the fetch — enforce it unconditionally and make any escape hatch an explicit, audited flag, never a side effect of the credential in use. Gate rule: for every `if <cond>:` wrapping an authz check, trace `<cond>` back to its producer and to the auth dependency of each reachable route — if no reachable caller can make it false, the check is deleted, not conditioned; `py_compile`/`tsc` and a green suite are blind to enforcement that is structurally unreachable. Inverse of the same-file "bypass must cover EVERY enforcement layer" lesson (CASE-20260719-5F0E20): that one bypassed too little, this one bypasses everything — both are found by grepping the enforcement primitive across all its call sites before accepting the diff.
