# Lessons — Auth & security

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** your diff touches auth middleware, secrets, tokens, allow-lists, bypass flags, or a fail-closed gate.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,
> claim-first, with the case id. Before appending, check whether an existing line already
> covers it — generalize that line instead of adding a near-duplicate.

- **A new X-Node-Secret / internal endpoint is UNREACHABLE until its path is registered in `TenantAuthMiddleware` — handler-level auth never runs otherwise (2026-07-10):** C9FE02 built `POST /internal/pipeline/auto-file` (router prefix `/internal/pipeline`) with a correct in-handler `X-Node-Secret` fail-closed check, but `backend/app/middleware/tenant_auth.py` exempts the REVERSED prefix `/pipeline/internal/` plus a fixed `NODE_SECRET_EXEMPT_ROUTES` list — neither matches `/internal/pipeline/*`. Automated callers send only `X-Node-Secret` (no Bearer JWT), so the middleware 401s them at the Bearer fallthrough BEFORE the handler runs → the whole feature is dead. When adding any machine/internal endpoint: (1) grep `tenant_auth.py` and confirm the exact path is covered by `PUBLIC_PATHS`, a prefix check at the `call_next` line, `PUBLIC_POST_PATHS`, or `NODE_SECRET_EXEMPT_ROUTES` — a fail-closed handler check is NOT enough on its own; (2) prefer reusing an already-exempt prefix (here `/pipeline/internal/`, which the codebase already exposes) over inventing a new top-level path that needs a fresh middleware edit; (3) mind prefix ORDER — `/internal/pipeline` ≠ `/pipeline/internal`. Rejected at gate; fix: CASE-20260710-AF9C01.
- **NEVER hardcode a real secret as an `||` fallback in a test spec — even in a fully-mocked test, a production secret literal committed to git is a permanent leak requiring rotation, not just a code fix (2026-07-13):** review-gate 2026-07-13 CASE-20260713-776BBF (products QA Playwright spec) set `const JWT_SECRET = process.env.JWT_IMPERSONATION_SECRET || 'df4cd8ce…aa61b'` — and that literal, byte-for-byte, EQUALS the real `grotap/prd` Doppler `JWT_IMPERSONATION_SECRET` (verified by hashing both). The spec mocks ALL backend APIs so the JWT is never actually verified (the secret is functionally dead weight), which is exactly why the fallback looked harmless to the author — but the value is now in git history forever and can forge impersonation tokens against any env still using it. It was NOT a new leak: 5 pre-existing master specs (`agent-store`, `agent-team-dashboard`, `brand-lock`, `platform-brand`, `suggest-submit-50`) already carry the identical literal — a systemic pattern. Correct fallbacks already in-repo: `ag-grid-license-smoke.spec.ts` throws if the env var is absent; `test_auth_brand_filter.py` uses a dummy `"test-secret"`. Gate action: merged the test-only branch (156 committed e2e PNGs already establish that screenshot convention; backend filtering test already lived on master as `test_products_presentation.py`) but stripped the literal to a `'test-secret'` dummy in the merge (fix commit c0848167), filed P1 CASE-20260713-SECFIX1 to sweep the 5 master files, and flagged that the code fix does NOT remediate the historical exposure — the owner must ROTATE the secret in Doppler prd+dev and refresh every Railway copy. Author rule: a test JWT signed with a secret the backend never checks (mocked APIs) needs only a dummy `'test-secret'`; a test that hits a real backend needs the env var with a throw-if-absent guard — NEVER embed the literal. Gate rule: grep any e2e/test branch for hex-looking `|| '…'` fallbacks and byte-compare against live Doppler secrets before merge.
- **A bypass/allow-flag for a cross-cutting concern (rate-limit, auth, blocklist, feature-gate) must cover EVERY layer that enforces it — the platform enforces abuse-defense in TWO middlewares, so wiring the bypass into only the named one silently leaves the other half enforcing (2026-07-19, review-gate MERGE+FIX of CASE-20260719-5F0E20):** the case asked for a load-test bypass (`LOADTEST_BYPASS_TOKEN`/`X-Loadtest-Token`, constant-time `hmac.compare_digest`) to "skip rate-limit checks, strike delays/blocks, and blocklist enforcement." The branch wired it correctly into `RateLimitMiddleware` (`rate_limit.py`, Tier-1 per-IP) and even set `request.state.is_loadtest=True` — but `TenantAuthMiddleware` (`tenant_auth.py`) runs INSIDE RateLimit and enforces a SEPARATE full Tier-2 stack (blocklist api_key_prefix + org via `match_api_key_prefix`/`match_org`, `is_strike_blocked`, `apply_strike_delay`, org/user 240-rpm `rate_limit_incr`, `handle_429` auto-block) that never reads the flag. So authenticated load traffic is still throttled/blocked at 240 rpm/org — the feature is inert for the realistic (tenant-endpoint) load case, while the startup log prints "bypass ACTIVE." Safe to MERGE (fully inert unless the token env is set; bypasses LESS than intended = no added exposure; no bad data / no auth break) but incomplete — filed CASE-20260719-LTBP2X to honor `request.state.is_loadtest` in tenant_auth. Author rule: when a task names ONE enforcement point for a cross-cutting concern, `git grep` the enforcement primitives (here `is_strike_blocked`/`apply_strike_delay`/`get_active_entries`/`rate_limit_incr`) across `backend/app/middleware/` and wire the bypass into every hit — prefer setting a `request.state` flag in the outermost enforcer and reading it in the inner ones (single constant-time compare). Gate rule: for any bypass/allow-flag/kill-switch case, grep for sibling enforcers of the same concern before accepting single-layer coverage; a bypass that only covers Tier-1 is a MERGE-with-fix (or FIX if the misleading "active" state could burn a scheduled run window).
- **A fail-closed STARTUP check for one app's OPTIONAL secret must NEVER abort platform boot (`raise`/`sys.exit`) — warn at boot, fail closed at REQUEST time (2026-07-19, review-gate batch17, CASE-20260719-B6B7B0 main.py hunk REJECTED, tests merged alone):** the branch replaced master's `logger.critical("GOOGLE_SERVICE_ACCOUNT_JSON is not set …")` (boot proceeds) with an unconditional `raise RuntimeError(...)` gated only on env-var presence — NOT on whether the Drive app is enabled. That converts a single-endpoint 500 into a whole-platform outage on every deploy lacking that optional var, and Railway would pin the old image and block ALL future deploys (unrelated apps included) until it's set. `core/config.py` explicitly documents empty=`Drive integration disabled` (503 on that route) as a SUPPORTED state, and `google_drive_provider._load_sa_json()` already raises at request time (app-scoped). Gate merged only the 2 test files (`git checkout <branch> -- tests/...`) and dropped the main.py change — no fix case needed since master's warning is already the desired behavior. Rule: a startup "fail-closed" check may only hard-abort boot for secrets required by CORE platform paths (auth, DB, control-plane); for a single app's optional integration, log at boot + fail closed in the provider at request time. Reject any main.py lifespan change that adds an unconditional `raise` on an app-scoped secret.
- **The "never abort platform boot for an optional secret" rule (line ~215) applies to MODULE-LEVEL `raise` in any SERVICE imported at boot, not just `main.py` lifespan — a module top-level `raise` on a missing env var is the same landmine one layer down (2026-07-19, review-gate batch20 SKIP → batch21 FIX, CASE-20260719-19F4C7 → CASE-20260719-19F4FX):** the rebuilt auto-block-notification branch added, at `backend/app/services/strike_engine.py` module scope, `if os.environ.get("LOADTEST_TEST_ORG_IDS") is None: raise RuntimeError(...)`. `strike_engine` is imported at boot (via `rate_limit.py`, and the branch also added an explicit `from app.services.strike_engine import LOADTEST_TEST_ORG_IDS` to the `main.py` lifespan). `LOADTEST_TEST_ORG_IDS` is CONFIRMED ABSENT in Doppler grotap/prd → RuntimeError at import → whole backend fails to boot, Railway pins the old image, ALL deploys blocked. This is the 2nd occurrence of the identical bug in this case (batch20 SKIP'd it, it came back unchanged). An env var that classifies test-vs-prod orgs for an app-scoped email alert is OPTIONAL: default a missing/empty value to an empty frozenset and log ONE warning at import; NEVER `raise` at module top level. Gate rule: grep every branch's diff for a bare `raise`/`sys.exit`/`assert` at module scope (not inside a function) in anything under `services/`/`providers/`/`core/` — if it fires on a missing/empty env var that isn't a CORE-path secret (auth/DB/control-plane), reject it. `py_compile` is blind (import-time only); `python -c "import app.main"` with the prod env would catch it.
- **An agent-worker→backend machine call MUST target an endpoint that is BOTH listed in NODE_SECRET_EXEMPT_ROUTES AND accepts dual-auth (_resolve_tenant), and MUST read that endpoint's ACTUAL response keys — /agent-context/master is JWT-only and NOT exempt, so a node-secret call to it 401s and a soft-failing feature silently does nothing (2026-07-24, review-gate, CASE-20260720-A87351 REJECTED → CASE-20260724-A87351FX):** fetchMasterContext() in agent-worker `context-client.ts` called `GET /agent-context/master` with X-Node-Secret+X-Tenant-Id, but backend `get_master_context()` uses `_get_tenant` (JWT-only) and the middleware only exempts `^/agent-context/composed/?$` → 401 at the middleware AND again at the handler; even had it passed, `/master` returns `{content,version,updated_at,is_template}` while the client read `raw.master_md`/`raw.master_version` → both undefined → empty context injected → feature is a no-op. The machine path is `/agent-context/composed` with NO loop_id (dual-auth, exempt, returns `{master_md,master_version}`) — the sibling `fetchAgentContext` in the SAME file already uses it correctly. This keeps recurring (see B7848D, F9BFIX). Reviewer tell: any worker fetch sending `X-Node-Secret` must hit a path in NODE_SECRET_EXEMPT_ROUTES and its field reads must match that handler's real return keys — a green tsc proves neither (the response type is author-declared).
