> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** you add or consume an endpoint, event, payload field, storage key, config key, or any contract another case/component depends on.

Fix: CASE-20260709-09C6D1.
- **Migrating a SHARED storage key to a new backend must update EVERY reader, not just the writer (2026-07-10):** 88162F moved the AI-support session id from `localStorage` to `sessionStorage` in the dock (`announceAiSupportSession`) but left `AnnotationOverlay.tsx` — a second component landed in parallel (09C6D1) — still gating on the old `localStorage.getItem` + `storage` event, so the overlay went permanently inactive after reload (old key never written again). - **"Modify the intake logic to prevent X" means WIRE it into the live path — a new helper nothing calls is dead code, not a fix (2026-07-10):** D2DD45 was tasked to dedup auto-filed failure cases; it added `pipeline_automation.py::auto_file_case()` with a correct-looking 30-min-window signature check, but nothing calls it and `pipeline_automation.py` has no failure-intake entrypoint — so duplicate parents are still created (the 541957 storm stayed unfixed) and the case merely LOOKED done. Two rules: (1) a case that says "prevent/dedup/intercept at intake" is unmet until the ACTUAL insert path invokes your logic — grep for the real `INSERT INTO pipeline_cases` from automated alerts and route it through your function; adding an orphan helper the dependent test can call directly is a false green. (2) Dedup by SELECT-then-INSERT with no DB-level guard still races: two near-simultaneous auto-files (the exact storm: same failure twice in ~45s) both miss the SELECT and both insert. Use a partial unique index / advisory lock / `ON CONFLICT` on the signature+window so concurrent dupes are impossible, not merely narrowed. Rejected at gate; fix: CASE-20260710-D2DDFX.
- **Rebase-staleness on hot files: notifications/side-effects belong wherever master CURRENTLY handles that transition, not where it did when you branched (2026-07-10):** 0FB344 put its Slack send inside the `dependencyCheck.ts` DB `step.run`, but master ac1b9d29 had already moved released-case handling into a post-step `for (const caseId of counts.releasedIds)` loop (request-dispatch + metadata stamp) — structural conflict at the gate, merge aborted. - **Worker-side severity enums are UPPERCASE; backend `severity_map` keys are lowercase — normalize at the boundary (2026-07-10):** agent-worker `BugFinding.severity` is `'CRITICAL'|'HIGH'|'MEDIUM'|'LOW'`, but `cobrowse.py::save_bug_report_internal` maps via `{"critical":"P1","high":"P2","medium":"P3","low":"P4"}.get(body.severity, "P2")` — sending uppercase silently falls through to the `"P2"` default AND stores the uppercase string in `bug_reports.severity`. When one side of a wire enum is cased differently from the other's lookup table, `.toLowerCase()` (or match the map keys) at the send site. Fixed in CASE-20260710-0C818B (`snapshot-test.ts`).
- **A docs/smoke-test file that shows example request bodies or asserts response codes must match the REAL handler contract — a wrong example produces false failures for whoever runs it (the deploy looks broken when it isn't) (2026-07-14):** review-gate 2026-07-14 CASE-20260713-1D7D28 shipped `docs/landing-register/README.md` with a smoke curl using `"category":"info"` (not in the registration handler's `VALID_CATEGORIES` = {manufacturing, agriculture_row_crops, re_wholesale, government} → real response is 422, not the asserted 201), and claimed the honeypot path returns **200**. FastAPI applies the route decorator's `status_code=201` to EVERY return unless the handler overrides it with a Response object; the honeypot's bare `return {"ok": True}` therefore returns **201** too — the only observable tell is the missing `id`, not a different status code. Author/gate rule: when a doc asserts an enum value or an HTTP status, grep the handler (the enum set, the `@router.post(..., status_code=N)` decorator) and confirm — don't trust the doc's own numbers. Gate-fixed the category slug and the honeypot status in the merge commit; shipped.

Fix filed CASE-20260715-E2CFIX.

- **A FRONTEND-only branch (especially a REBASE of an older UI onto refactored master) must be validated against the actual RESPONSE SHAPE and PATH-PARAM IDENTITY of every endpoint it consumes on master — not merely that the route EXISTS. - **An event/message CONSUMER that reads a NEW payload field breaks the moment it merges unless the PRODUCER(S) on master already emit that field — verify both sides of the contract land together (2026-07-19, review-gate batch20, CASE-20260719-796DEB defect → forward-fix CASE-20260719-796TFX):** the branch added tenant-ownership verification to `agent-worker/src/functions/resume-erp-agent.ts` — it destructured a NEW `tenant_id` off the `erp/agent.intervention-resolved` Inngest event and passed it to a fail-closed `verifyCheckpointTenant(thread_id, tenant_id, sql)`. - **A fetch/read endpoint that reads from a NEW table/column nothing WRITES is an inert feature — the mirror of the "dead write key" trap (2026-07-20, review-gate batch5 REJECT, CASE-20260720-DD442D→DD44FX):** the case "inject composed customer context into loop runs, reusing the ASM-A contract" instead added a NEW `/loop-engine/internal/context/{tenant}/{loop}` endpoint + migration `v007` creating `loop_engine.tenant_context` and `loop_engine.loops.automation_md`, and read context from THOSE. But every authoring path writes `agent_context.agent_context_docs` (the ASM-A store) — nothing writes the new tables — so the agent-worker always fetches EMPTY context. It also reimplemented a contract that already exists (`GET /loop-engine/loops/{id}/composed` and `GET /agent-context/composed`, X-Node-Secret dual-auth, both reading agent_context schema). Gate rule: when a case says "reuse the existing contract/endpoint", grep master for that endpoint FIRST and re-point the consumer at it; if a branch adds a read path against a new store, grep for a WRITER of that store — a read-only new table (no producer) means the feature returns empty forever. Pairs with the batch24 703B04 "dead write key" lesson: verify producer↔consumer use the SAME storage namespace on BOTH the write and read side. **The same check runs in the OTHER direction, and there it fails louder: a WRITE to a queue/work table that nothing SELECTs is not merely inert — if any live path filters on that table, the orphan row actively BLOCKS the working one (2026-07-26, hand-fixed b14ef604, prod-measured 0/49):** `POST /pipeline/webhook/team1-requeue` INSERTed a `pipeline_dispatch_log` row and returned, on the strength of a comment naming a "dispatch-poller" that does not exist anywhere in backend, orchestrator, or `agents/` — every real dispatch is PUSHED (`_log_dispatch` then `_route_dispatch` → orchestrator POST), nothing polls for `status='pending'`. So the open-model runner exited 0 logging "task continues on team1" while the case went nowhere. Worse, the assign loop selects `plan_approved AND NOT EXISTS (dispatch row IN ('pending','active'))`, so the row the webhook wrote was precisely what made the case undispatchable; it then sat until `dispatch_reconciler` failed it at 45 min, burning a retry strike per pass until the 3-strike cap escalated it to a critical hold.
