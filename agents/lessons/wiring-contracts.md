# Lessons — Wiring & contracts

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** you add or consume an endpoint, event, payload field, storage key, config key, or any contract another case/component depends on.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,
> claim-first, with the case id. Before appending, check whether an existing line already

- **Verify the output channel EXISTS before building on it (2026-07-09):** AIS-C (E4C9F5) closed `done` with its user-visible deliverable (screen annotations) terminating in a log-only stub (`loggingAnnotations` → `annotation_skipped`); the render channel it assumed (@openreplay/tracker-assist draw) is call/remote-control-gated and never mounts for chat-only agents. A deliverable resting on a stub or assumed-but-unverified adapter seam is NOT done: grep the seam for stubs and prove the visible effect end-to-end before building AND at the gate. Fix: CASE-20260709-09C6D1.
- **Migrating a SHARED storage key to a new backend must update EVERY reader, not just the writer (2026-07-10):** 88162F moved the AI-support session id from `localStorage` to `sessionStorage` in the dock (`announceAiSupportSession`) but left `AnnotationOverlay.tsx` — a second component landed in parallel (09C6D1) — still gating on the old `localStorage.getItem` + `storage` event, so the overlay went permanently inactive after reload (old key never written again). When you branch from a stale master and change a key/event both a writer and reader share, grep the whole tree for the key and route both through ONE shared helper. Fix: CASE-20260710-72AF65.
- **"Modify the intake logic to prevent X" means WIRE it into the live path — a new helper nothing calls is dead code, not a fix (2026-07-10):** D2DD45 was tasked to dedup auto-filed failure cases; it added `pipeline_automation.py::auto_file_case()` with a correct-looking 30-min-window signature check, but nothing calls it and `pipeline_automation.py` has no failure-intake entrypoint — so duplicate parents are still created (the 541957 storm stayed unfixed) and the case merely LOOKED done. Two rules: (1) a case that says "prevent/dedup/intercept at intake" is unmet until the ACTUAL insert path invokes your logic — grep for the real `INSERT INTO pipeline_cases` from automated alerts and route it through your function; adding an orphan helper the dependent test can call directly is a false green. (2) Dedup by SELECT-then-INSERT with no DB-level guard still races: two near-simultaneous auto-files (the exact storm: same failure twice in ~45s) both miss the SELECT and both insert. Use a partial unique index / advisory lock / `ON CONFLICT` on the signature+window so concurrent dupes are impossible, not merely narrowed. Rejected at gate; fix: CASE-20260710-D2DDFX.
- **Rebase-staleness on hot files: notifications/side-effects belong wherever master CURRENTLY handles that transition, not where it did when you branched (2026-07-10):** 0FB344 put its Slack send inside the `dependencyCheck.ts` DB `step.run`, but master ac1b9d29 had already moved released-case handling into a post-step `for (const caseId of counts.releasedIds)` loop (request-dispatch + metadata stamp) — structural conflict at the gate, merge aborted. Before adding a hook to a pipeline/orchestration file, `git log -p` the target function on current master first; if the flow was recently restructured, attach to the NEW seam. Superseded by CASE-20260710-FB3F01.
- **Worker-side severity enums are UPPERCASE; backend `severity_map` keys are lowercase — normalize at the boundary (2026-07-10):** agent-worker `BugFinding.severity` is `'CRITICAL'|'HIGH'|'MEDIUM'|'LOW'`, but `cobrowse.py::save_bug_report_internal` maps via `{"critical":"P1","high":"P2","medium":"P3","low":"P4"}.get(body.severity, "P2")` — sending uppercase silently falls through to the `"P2"` default AND stores the uppercase string in `bug_reports.severity`. When one side of a wire enum is cased differently from the other's lookup table, `.toLowerCase()` (or match the map keys) at the send site. Fixed in CASE-20260710-0C818B (`snapshot-test.ts`).
- **A docs/smoke-test file that shows example request bodies or asserts response codes must match the REAL handler contract — a wrong example produces false failures for whoever runs it (the deploy looks broken when it isn't) (2026-07-14):** review-gate 2026-07-14 CASE-20260713-1D7D28 shipped `docs/landing-register/README.md` with a smoke curl using `"category":"info"` (not in the registration handler's `VALID_CATEGORIES` = {manufacturing, agriculture_row_crops, re_wholesale, government} → real response is 422, not the asserted 201), and claimed the honeypot path returns **200**. FastAPI applies the route decorator's `status_code=201` to EVERY return unless the handler overrides it with a Response object; the honeypot's bare `return {"ok": True}` therefore returns **201** too — the only observable tell is the missing `id`, not a different status code. Author/gate rule: when a doc asserts an enum value or an HTTP status, grep the handler (the enum set, the `@router.post(..., status_code=N)` decorator) and confirm — don't trust the doc's own numbers. Gate-fixed the category slug and the honeypot status in the merge commit; shipped.

The agent installed `@mantine/rte@5.10.5` against the repo's `@mantine/core@^6.0.22` and added an `overrides` block forcing the v5 editor's peers up to v6 — a v5-on-v6 render-crash landmine that `tsc` misses because nothing imports it yet. Author rule: `npm view <pkg> versions` before adding; if the requested version/package doesn't exist or its peer range excludes the repo's installed major, STOP and report the contradiction — never paper over a peer mismatch with `overrides`. Gate rule: on a dep-add branch, check the added version's peer ranges against the root's installed majors and reject `overrides` that force a cross-major peer. Filed CASE-20260715-RTEFIX (needs owner product decision: `@mantine/tiptap` vs drop).

- **A lookup-by-external_ref call (update_live_state / any "find the row I ingested earlier" helper) MUST use the EXACT external_ref string the ingest site wrote — grep the producer for its literal ref; a plausible-but-invented prefix silently no-ops because the helper returns False on no-match and every downstream state transition dies quietly (2026-07-15):** review-gate 2026-07-15 batch24 rejected CASE-20260715-E2C59B. Its `voice.py` dial-result/voicemail-complete handlers called `update_live_state(external_ref=f"ring-{call_sid}", source_system="Voice", ...)` for all three transitions (answered/missed/voicemail), but the ringing tap `_fire_voice_ringing_tap` (voice.py ~line 249, already on master) ingests that event with `external_ref=f"call-{call_sid}"`. `update_live_state` matches on `(tenant_id, source_system, external_ref)`, finds NO row with the `ring-` prefix, returns False, and no-ops — so ringing cards never resolve via Twilio webhooks and the 25s reaper reaps even ANSWERED calls to 'missed' (wrong data). `compileall`/`tsc` are BLIND — the string is valid, the function exists, the signature matches; only the value is wrong. The branch also added a duplicate module constant `_FREE_STREAM_VOICE_TENANT` when `_FREE_STREAM_LEADS_TENANT` (same env var, same value) already existed. Author rule: before writing an `external_ref=` on a lookup/update call, grep the ingest site for the literal ref it produces and copy it — never guess a prefix. Gate rule: for any branch calling update_live_state / a by-external_ref lookup, `grep -n 'external_ref=' ` the producer and the consumer and confirm the prefixes match byte-for-byte; a mismatch is a feature-breaking defect, not a small latent one — reject. Fix filed CASE-20260715-E2CFIX.
- **A helper that POSTs an HI hold / notification MUST use the platform's REAL hold endpoint (`POST https://api.grotap.com/human-intervention/`, in PUBLIC_PATHS so NO auth) — an agent will otherwise invent a plausible internal route and mint an unnecessary auth token, and because such helpers are wrapped in a non-fatal try/except the wrong URL fails silently, so no hold is ever filed (2026-07-15):** review-gate 2026-07-15 merged loadtest LT-A skeleton (CASE-20260715-1EB877) + LT-E cleanup_mail (CASE-20260715-DB1D05); DB1D05's `_file_hi_hold()` in `loadtest/cleanup_mail.py` POSTed to `https://api.grotap.com/internal/holds` with a Bearer HS256 token (jose-minted from `JWT_IMPERSONATION_SECRET`) — but `/internal/holds` does NOT exist (grep `backend/app/routers/` — the only hold route is `human_intervention.py` `prefix="/human-intervention"`, allow-listed in `tenant_auth.py:107` PUBLIC_PATHS = no auth). The auth-failure remediation still WORKS (prints the checklist, exits nonzero), so it merged with a fix case (CASE-20260715-DB1DFX) rather than being rejected — the broken part is only the automated hold POST, which fails into its own `except` and prints "POST failed (non-fatal)". Author rule: to file a hold from a script, POST unauthenticated JSON `{task_id, category, priority, description}` to `https://api.grotap.com/human-intervention/` (curl/urllib both fine, no token) — never invent an `/internal/*` route or attach a JWT. Gate rule: grep any new hold/notify helper for its POST URL and confirm it's `/human-intervention/`; a non-fatal try/except around a wrong URL is a silent-no-op defect (merge-with-fix if the primary path still works, reject if the hold is the only signal path). Also: sibling coalesced cases that each scaffold a shared package file (both LT-A and LT-E created `loadtest/__init__.py`) produce an add/add conflict at merge — keep the skeleton-owner's version, take only the module file from the consumer branch.

- **A FRONTEND-only branch (especially a REBASE of an older UI onto refactored master) must be validated against the actual RESPONSE SHAPE and PATH-PARAM IDENTITY of every endpoint it consumes on master — not merely that the route EXISTS. An endpoint that returns `string[]` when the FE types it as `object[]`, or a route keyed on `contact_submission_id` when the FE sends `call_sid`, compiles and type-checks cleanly yet crashes at runtime (render throw / 500 / 404). `tsc` is BLIND: the FE's own `interface`/generic ASSERTS the shape the code wants, so `a.email`/`row.field` is well-typed even though the server never sends it (2026-07-17):** review-gate 2026-07-17 verdicted CASE-20260715-7FCFIX (rebase of 7FCD71 voice-lead assignment UI onto refactored CallsPage) as FIX — but the orchestrator had already merged it to master. Fix filed CASE-20260717-7FCFX2 (P1 — it is LIVE). Author rule: before a FE branch dereferences `resp.<field>` or interpolates an id into a route path, open the CONSUMED endpoint's serializer/handler on master and confirm (a) the JSON shape matches the FE interface field-by-field, and (b) the path param is the SAME identifier the FE holds (call_sid ≠ submission_id ≠ uuid). Gate rule: for any frontend-only/rebase branch, for each `api.get/post/patch(<path>)` grep the backend route — verify the response shape against the FE interface and that any `{id}` path segment is the identifier the FE actually sends; a shape/identity mismatch is a runtime crash, not a latent nit. (Related: the existing "frontend that consumes a LIST endpoint expecting a nested child array" and "text→uuid cast" lessons — same blind spot, different surface.)
- **Generalizing a literal-keyed branch means fixing EVERY comparison site of that literal — and a "generalized" gate is only proven by a test that iterates the WHOLE registry (2026-07-17):** the TEAM2-DISPATCH generalization (FC0208 child) claimed to kill the `team2||team3` literal in `agents/dispatch.sh`, but both decision sites still compared `_TEAM_RUNTIME_SCRIPT == "agents/team-run.sh"` — the pool/cap/model-env gate (~:150) AND the runner-script write (~:182). - **An event/message CONSUMER that reads a NEW payload field breaks the moment it merges unless the PRODUCER(S) on master already emit that field — verify both sides of the contract land together (2026-07-19, review-gate batch20, CASE-20260719-796DEB defect → forward-fix CASE-20260719-796TFX):** the branch added tenant-ownership verification to `agent-worker/src/functions/resume-erp-agent.ts` — it destructured a NEW `tenant_id` off the `erp/agent.intervention-resolved` Inngest event and passed it to a fail-closed `verifyCheckpointTenant(thread_id, tenant_id, sql)`. But BOTH producers on master (`backend/app/routers/farms.py` `resolve_intervention` and `human_intervention.py` update-hold erp_review branch) still emitted `{thread_id, approved, notes}` with NO `tenant_id`. So `tenant_id` arrives `undefined` → `rows[0].tenant_id.toLowerCase() !== undefined.toLowerCase()` throws `TypeError: Cannot read properties of undefined` → EVERY resume (approve AND reject) fails closed and paused LangGraph threads never resume — a live functional break. compileall/tsc are blind to it: the consumer type-checks fine in isolation because the event shape is cast, not validated. The orchestrator auto-merged it before the gate could reject. Gate rule: for any branch that reads a NEW field from an event/queue/webhook/RPC payload (Inngest `event.data`, Stripe metadata, internal pub/sub), grep every PRODUCER of that event name on master and confirm they ALREADY populate the field with a meaningful value — land the producer change FIRST (adding a field is backward-compatible; old consumers ignore it), then the consumer. Same shape as the FE→endpoint dependency rule, one layer down. Also: a fail-closed verifier must guard its inputs — check `if (!payloadTenantId) throw new Error('missing tenant_id')` BEFORE `.toLowerCase()`, so a missing field is a descriptive rejection, not a TypeError. And never source the verified identity from the same table you're checking against (looking up `checkpoint_threads.tenant_id` to pass INTO the checkpoint_threads ownership check makes it tautological) — the value must come from the authenticated caller (`request.state`).

- **A consumer that reads owner-set JSONB config must read the SAME keys AND units the already-landed migration documents — a fresh key convention silently ignores every configured value (2026-07-19, review-gate batch24 FIX, CASE-20260719-154B29 → CASE-20260719-154BFX):** master's landed `v069_usage_review_config.sql` documents the `pipeline_automation.usage_review_config` contract as keys `threshold_warn_pct` (default 80) / `threshold_strong_warn_pct` (95) as PERCENTAGES, but the new alert script read `warn_pct`/`strong_warn_pct` as FRACTIONS (0.70/0.90). It also reimplemented a contract that already exists (`GET /loop-engine/loops/{id}/composed` and `GET /agent-context/composed`, X-Node-Secret dual-auth, both reading agent_context schema). Gate rule: when a case says "reuse the existing contract/endpoint", grep master for that endpoint FIRST and re-point the consumer at it; if a branch adds a read path against a new store, grep for a WRITER of that store — a read-only new table (no producer) means the feature returns empty forever. Pairs with the batch24 703B04 "dead write key" lesson: verify producer↔consumer use the SAME storage namespace on BOTH the write and read side. RECURRENCE 2026-07-26 (CASE-20260726-DD2DD9 REJECTED → CASE-20260726-SYNCCV), sharpest variant yet — **the unwritten field was a TIEBREAK input, so the dead read silently promoted the FALLBACK to the entire behaviour**: to converge two divergent `settings.flows` intervals "taking the LATER-EDITED one", `resolve_flows` compared `stored[flow]["updated_at"]` for `inventory_detail` vs `committed_qtys` — but the only writer of those entries (the flows PATCH in `backend/app/routers/scantap.py`) rebuilds each one from scratch as exactly `{"enabled", "interval"}`, so the key is absent today AND would be dropped on the next save even if backfilled. Author rule: before keying a comparison, sort, priority, or tiebreak on a field, grep for the code that WRITES it and confirm the writer preserves it (a rebuild-from-scratch dict is a silent dropper); if no writer exists, adding one is part of your scope, not an assumption. Gate rule: for any branch whose logic branches on a stored field, read the writer and ask "can this field ever be non-null?" — if not, evaluate the code with the field absent and judge THAT behaviour, because it is the only behaviour that ships; a fallback reached 100% of the time is the implementation, no matter how it reads in the diff.
- **A frontend control that sends an identifier to a backend allow-list must send the value the allow-list VALIDATES, at the field the backend READS — sending an adjacent internal field, or nesting it where validation is skipped, stores garbage that no consumer matches (2026-07-21, review-gate batch3 REJECT, CASE-20260721-1E2756 → CASE-20260721-1E2FIX):** the Agent-Teams lane click passed `lane.lane ?? lane.id` to createSession, but `lane.lane` is the INTERNAL routing letter (A/B/C) from `GET /claude-app/lanes` while the backend `_VALID_LANE_CHOICES = {auto,team1..team4,local}` is the `lane.id`. It also nested the value inside the `context` JSONB object instead of the top-level `lane_choice` body field the backend's `CreateSessionRequest` validates (422 on invalid) — so the invalid "B"/"C"/"A" bypassed validation AND got persisted, and the active-lane highlight (`lane.id === activeTeamId`, which reads `context.lane_choice`) never matched. Two compounding bugs: wrong value + wrong field. Rule: before wiring a selector→POST, grep the backend request model + its allow-list to confirm (a) which id the allow-list contains, and (b) that you send it as the SAME top-level field the server validates — never smuggle a validated field inside a free-form JSONB blob, or you silently defeat the server-side check. Reviewer tell: FE sends `context: {…, someKey}` while the backend model has a dedicated top-level `someKey` field with validation.
