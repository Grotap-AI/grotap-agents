- **Verify referenced DB columns against the LIVE schema — task-provided "SCHEMA FACTS" can be wrong (2026-07-10):** 6EC85C built `scripts/pipeline_backlog_report.py` faithfully to a task that asserted `pipeline_dispatch_log` has a `created_at` column; it does NOT (real timestamps: `queued_at` sparse, `dispatched_at` always-populated, `started_at`, `completed_at`), so Section 4 raises asyncpg `UndefinedColumnError` at runtime and crashes the report. Even when a task hands you "SCHEMA FACTS (do not guess others)", confirm every column exists (`information_schema.columns` or `\d <table>`) before writing SQL against it — a spec can be authored from a stale mental model. Fix: CASE-20260710-6EC85C-FIX.
- **`get_control_plane_db()` returns a `ControlPlaneDB`, NOT an asyncpg pool — call raw queries through `.pool` (2026-07-10):** `ControlPlaneDB` (`backend/app/database/control_plane.py`) exposes only a `pool` property plus named CRUD helpers; it has NO `fetchval`/`execute`/`fetch`/`fetchrow`/`fetch_all` methods and no `__getattr__` proxy, so `db.fetchval(...)` raises `AttributeError` at runtime and 500s the endpoint. Use `db.pool.fetchval/execute/fetchrow/fetch`. Extra trap: asyncpg.Pool has NO `fetch_all` method — the multi-row call is `db.pool.fetch(...)` (returns list of Records). Grep every `db.<method>(` in a router and confirm each resolves to a real asyncpg.Pool method before merge. (cobrowse.py write path fixed in CASE-20260710-0C818B; read endpoints in CASE-20260710-CB1FIX.)
- **A "flag for owner review, do NOT run in prod" migration must NOT land in the auto-applied dir; and never DROP a column still referenced by master code (2026-07-11):** CASE-20260711-234F76 was tasked to author a cobrowse_session_id DROP migration for OWNER review only (do not execute). Its branch put v042_drop_cobrowse_session_id.sql under backend/db/migrations/control_plane/ — but backend/app/database/migration_runner.py auto-applies EVERY vNNN_*.sql there at each boot, so merging = auto-DROP on next deploy, the exact opposite of "owner review only". Worse, the "no code writes this column" premise was FALSE: ai_support.py (INSERT+RETURNING+read), cobrowse.py, and support.py still write/read cobrowse_session_id, so the drop would 500 live support flows. Two rules: (1) if a migration is meant to be human-gated, it CANNOT go in an auto-run migrations dir — confirm where the runner picks files up before choosing a path; (2) a DROP COLUMN is safe only after every master reader/writer of that column is removed and shipped first — grep the whole backend for the column name and prove zero references before authoring the drop. Rejected at gate; fix: CASE-20260711-63241C.
- **Postgres multi-line string concatenation: the `E` escape prefix goes ONLY on the FIRST literal of the group (2026-07-11):** `scripts/seed_openreplay_notices.sql` prefixed every continuation line (`E'a\n'` newline `E'b'`) — that is a syntax error, so the merged "run once" seed could never run and shipped broken. Adjacent literals separated by a newline concatenate, but only the first may carry `E`; continuation lines are bare `'...'` (their `\n` still escape via the group's leading `E`). Any seed/utility SQL delivered in a branch must actually be EXECUTED (against prod for idempotent seeds, or at least `db.py -f` syntax-run) before sign-off — "merged" ≠ "runs". Hand-fixed 92ba89cd.
- **NEVER run DDL on a tenant pool at request time — RLS-hardened tenants connect as `app_user`, which has no CREATE on schema public, and Postgres checks that privilege BEFORE the `IF NOT EXISTS` shortcut (2026-07-11):** legacy `_ensure_*` helpers in `apps.py`/`api_keys.py`/`rainbow.py`/`documents.py` ran `CREATE TABLE IF NOT EXISTS`/`ALTER TABLE` on `request.state.tenant_pool`; once a tenant moved to the hardened role every such endpoint 500ed with `InsufficientPrivilegeError` even though the tables already existed — GET /apps died and platform home showed "No apps yet" (no app launchable). Tenant schema belongs in provisioning (`provision_shard.py`/`backfill_rls_roles.py`), never in routers; if you must keep legacy ensure-DDL, route it through `tenant_db.ensure_tenant_ddl()` (swallows only the privilege denial, returns False — don't latch "initialised" flags on False). Emergency fix 51edf492; durable cleanup: CASE-20260712-TENDDL.
- **Migration files must NOT contain explicit `BEGIN;`/`COMMIT;` — the runner already wraps each file in its own `conn.transaction()`, so an inner `COMMIT` commits early and splits the DDL from the ledger INSERT into separate commits (2026-07-13):** CASE-20260713-A9D6F7's `v044_glossary_schema.sql` wrapped its whole body in `BEGIN;...COMMIT;`. asyncpg tolerates the nested `BEGIN` (warns "already a transaction in progress", no-op) and the inner `COMMIT` closes the runner's managed transaction, then the `INSERT INTO schema_migrations` ledger row runs in autocommit as a SEPARATE commit — so on partial failure the DDL can commit without a ledger row (idempotent `IF NOT EXISTS` saved it here, but it's fragile). `backend/db/migrations/README.md` states each file "must run inside a single transaction" — the runner provides it; NO other `vNNN_*.sql` uses BEGIN/COMMIT. Rule: at the gate, grep new migration files for `^\s*(BEGIN|COMMIT|START TRANSACTION)\b` and reject/flag; the transaction is the runner's job. (Merged as-is 2026-07-13 because idempotent + verified non-fatal, but never author it this way.)
- **A "failed"/never-merged case can still have its migration LIVE in prod, poisoning a later canonical migration into a boot-abort — dry-run every pending `vNNN` against the live DB before merging a branch that depends on it (2026-07-13):** confirmed the theoretical poisoning above actually happened. CASE-20260713-E535B8 was marked `failed` and its `v042_object_glossary.sql` never merged to master — BUT that run had already applied the migration directly to the prod control-plane DB, leaving `glossary_libraries/glossary_objects/glossary_synonym_overlays` with the incompatible shape (`slug/canonical_name/category`, NO `is_default/org_id/created_by`). The canonical `v044_glossary_schema.sql` (merged, still PENDING — ledger tops out at v043) then can't reconcile: its `CREATE TABLE IF NOT EXISTS` no-ops over the poisoned tables, and the next statement `CREATE UNIQUE INDEX ... WHERE is_default = true` errors `column "is_default" does not exist` → the single-txn file aborts → `migration_runner.run_migrations()` raises → BOOT ABORTS on the next redeploy. `compileall`/`tsc` and even `git log` show nothing; the live DB state is the only witness. Gate rule: (1) `git status` of a case (failed/superseded) does NOT mean its DDL is absent from prod — a failed run may have applied it. (2) Before merging any branch whose code references columns from a not-yet-applied migration, DRY-RUN that migration against the live control-plane DB inside `BEGIN; ...; ROLLBACK;` and confirm it applies. (3) Fix a poisoned pending migration by making it self-heal — prepend a guarded `DROP TABLE ... CASCADE` of the legacy tables (only when they lack the canonical column) BEFORE the CREATEs; it's editable while unapplied (not in the ledger, so the checksum guard is inert). Review gate 2026-07-13 batch5: held CASE-20260713-09879A (code clean, blocked on live schema), filed P1 CASE-20260713-B84124, DID NOT push (a redeploy would brick boot).
- **Dry-run the WHOLE pending migration file end-to-end, not just the one statement you suspect — a single file can hide MULTIPLE independent boot-abort defects (2026-07-13):** batch5 diagnosed the `v044_glossary_schema.sql` boot landmine by dry-running ONLY the suspect `CREATE UNIQUE INDEX ... WHERE is_default=true` line in isolation, confirmed it errored, and filed the fix — but never ran the rest of the file. Batch6, after prepending the guarded self-heal DROP, dry-ran the ENTIRE file (`BEGIN; <full file minus its own BEGIN/COMMIT>; ROLLBACK;`) against live prod and hit a SECOND, unrelated abort three statements later: `CREATE INDEX ... USING GIN (array_to_string(synonyms,' ') gin_trgm_ops)` → `ERROR: functions in index expression must be marked IMMUTABLE` (`array_to_string(anyarray,text)` is STABLE, not IMMUTABLE). Fixing only landmine #1 would have shipped a still-boot-bricking migration. Gate rule: to validate a migration, pipe the whole file (stripped of any inner BEGIN/COMMIT) into one `BEGIN; ...; ROLLBACK;` with `-v ON_ERROR_STOP=1` against the live DB and confirm it reaches ROLLBACK with zero ERROR lines — never spot-check a single statement. Two valid fixes for the non-IMMUTABLE expression-index case: (a) wrap in an `IMMUTABLE` SQL function the query also calls (`CREATE FUNCTION glossary_synonyms_text(text[]) ... IMMUTABLE ... array_to_string($1,' ')`), or (b) DEFER the index to the case that adds the query (correct without it on a small/empty table). Review gate 2026-07-13 batch6: the parallel-built fix CASE-20260713-B84124 chose (b) and was adopted over the gate's own (a).
- **App-registration migration: `apps.status` is CHECK-constrained to `('voting','building','beta','live','deprecated')` — `'active'` is NOT valid and aborts the migration → boot abort on next redeploy (2026-07-13):** review-gate 2026-07-13 CASE-20260713-C31FDF shipped `v045_object_glossary_app.sql` with `INSERT INTO apps (... status, app_status) VALUES (... 'active','active')`. - **`CREATE POLICY` has NO `IF NOT EXISTS` form in Postgres — an RLS migration using `CREATE POLICY IF NOT EXISTS ...` is a hard syntax error that aborts the whole migration file (2026-07-14):** CASE-20260714-6825BE's `v001_free_stream_core.sql` used `CREATE POLICY IF NOT EXISTS tenant_isolation ON ...`. Postgres (through 16) rejects `IF NOT EXISTS` on `CREATE POLICY` (unlike CREATE TABLE/INDEX/SCHEMA), so the file errors on first parse and the migration_runner boot-applies nothing. `compileall`/`tsc` are blind (SQL). Idempotent-policy pattern that works (used by 1B3898): wrap in `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_policies WHERE schemaname=... AND tablename=... AND policyname=...) THEN CREATE POLICY ...; END IF; END $$;`. Gate rule: grep any new migration for `CREATE POLICY IF NOT EXISTS` (and `CREATE TRIGGER IF NOT EXISTS`, also invalid) — both must use the `pg_policies`/`DROP TRIGGER IF EXISTS`+`CREATE TRIGGER` guard idioms instead.
- **When a feature's tables live in a NAMED Postgres schema (e.g. `free_stream.*`), EVERY SQL reference must be schema-qualified — tenant/app connections do NOT set `search_path` to that schema, so an unqualified `FROM unified_stream_events` 500s with "relation does not exist" on every call (2026-07-15):** review-gate 2026-07-15 CASE-20260715-924BF5 (Free Stream action endpoints) wrote all three endpoints' SQL with bare table names (`unified_stream_events`, `stream_entities`, `stream_companies`, `stream_action_templates`) while the canonical schema (`migrations/apps/free-stream/v001_free_stream_core.sql` + `free_stream_ingest.py`, both qualifying as `free_stream.<table>`) creates them under the `free_stream` schema. `py_compile`/`tsc` are blind (SQL in strings); the failure only appears at request time. Author/gate rule: when a branch adds an app-schema feature, grep its SQL for the table names and confirm each is `<schema>.<table>`-qualified (match the schema-owner migration/service); the app pattern is qualify-everywhere, not per-connection `SET search_path`. Fix filed CASE-20260715-924BFX (also folds the endpoints into the EXISTING 0A5FE7 router — see next lesson).
- **A per-app schema feature is NOT live when its code merges — it is live when every tenant DB has (a) ALL its migration files applied and (b) the app_user GRANTS block; and an ORDER BY on a CTE's outer SELECT cannot use the inner alias (2026-07-15):** owner "cannot open Free Stream" — every `/free-stream/*` endpoint 500'd for ~12s while `/health` returned 200 (it only probes schema existence). ON ALL TABLES` + `ALTER DEFAULT PRIVILEGES`, guarded for missing role) is MANDATORY in every new app-schema migration — fixed via `v003_app_user_grants.sql`. (2) `v002_free_stream_settings.sql` merged but was never APPLIED to tenant DBs, so the router's per-request runtime DDL crashed on `ALTER TABLE free_stream.stream_settings ENABLE ROW LEVEL SECURITY` — `ensure_tenant_ddl` swallows ONLY InsufficientPrivilege; UndefinedTable propagates as a 500 on EVERY endpoint that calls `_ensure_schema`. ON CONFLICT DO NOTHING` for fresh envs), leaving the shipped file byte-identical (2026-07-15):** review-gate 2026-07-15 batch31 took CASE-20260715-F5DE03 (seed pool1 `agent_pool_teams.model_config` from `agents/config.sh` TEAM_MODEL_ENV). Part (a) is a guaranteed boot landmine: v051 is in the ledger, so on next deploy its recomputed checksum ≠ ledger checksum → RuntimeError → boot abort. `compileall`/`tsc` are BLIND (the SQL is valid; the damage is a runtime checksum mismatch). Gate disposition that worked: MERGE ONLY the new v052 file (`git checkout <branch> -- backend/db/migrations/control_plane/v052_*.sql`), DROP the v051 edit entirely (confirm `git diff origin/master -- v051_*.sql` is empty), commit just the new file. An agent following its case spec into a boot-abort is an authoring defect. Changing a url's FORMAT means also setting the `kind` the new format implies. **EXTENDS 2026-07-26 (Setup app, v086_setup_app.sql):** the same boot-abort fires from the OTHER direction — hand-APPLYING a migration and writing the `schema_migrations` row yourself with a checksum you computed ad-hoc. The runner hashes `sql.replace("

NOTE a bare `from app.main import app` boot test CANNOT catch this: it constructs the app but never runs the lifespan, which is where the migration runner executes.
- **The control-plane asyncpg pool registers NO JSONB type codec (grep `set_type_codec` across `backend/` = zero hits; `control_plane.py connect()` calls `asyncpg.create_pool()` with no `init=`/codec) — so a JSONB column READS BACK AS `str` and PASSING A python `dict`/`list` to a jsonb param RAISES `DataError: expected str, got dict/list` (with OR without a `::jsonb` cast). Every jsonb WRITE must be `json.dumps(value)` bound to a `$n::jsonb` placeholder; every jsonb READ must `json.loads(row[col])` (guard `isinstance(str)`). `compileall`/`tsc` are BLIND to this — it's a 100% runtime 500 on the write path and a malformed-string body on the read path (2026-07-15):** review-gate 2026-07-15 merged the agent-pools router (CASE-20260715-44330C, `admin_agent_pools.py`) WITH a fix case (CASE-20260715-AAPJSN) because two of its endpoints hit exactly this: `create_team()`/`update_team()` pass `body.model_config_data` and `body.capacity` (dicts) straight into the `agent_pool_teams` jsonb columns → guaranteed 500 on every call (even the default `{}`); and `_team_row()` returns `row["model_config"]`/`row["capacity"]` verbatim → responses emit JSON *strings* instead of objects. Tell in the SAME file that it's fixable, not fatal: the `tenant_agent_service` upsert in that router DOES it right (`json.dumps(enabled_ids)` + `$4::jsonb`, and `_service_row` does `json.loads` when `isinstance(str)`), and `agent_team_provisioner._clone_pool_for_tenant` (CASE-20260715-CBA9E0, merged same batch) is also correct (`json.dumps(...) + $5::jsonb`, `json.loads` on read). Disposition: merged because the defect neither corrupts data nor breaks auth and the surface is net-new admin-only with no FE consumer yet — foundation value + unblocks the feature > two dark broken endpoints. The IDENTICAL bug is pre-existing on master in `admin_agent_team_templates.py create_template()` (passes `body.agent_seed` list raw into the jsonb `agent_seed` column → 500) — folded into the same fix case. Author rule: any `INSERT/UPDATE ... <jsonb_col> = $n` where the bound value is a python dict/list → wrap `json.dumps()` and cast `$n::jsonb`; any serializer reading a jsonb column → `json.loads` guarded by `isinstance(str)`. Gate rule: for any control-plane branch, grep the diff for dict/list values bound to jsonb params without `json.dumps` (and serializers returning a jsonb column without `json.loads`) — it's invisible to compile/type gates and only shows at runtime. This pool has no codec; do NOT assume asyncpg auto-serializes JSON.
- **A `WHERE col = $1::uuid` (or any `text→uuid`/`::int`/`::timestamptz` cast) applied to a value taken from a loosely-typed TEXT column will HARD-CRASH the request with asyncpg `InvalidTextRepresentationError`/`DataError` (a subclass of `PostgresError`, NOT `RuntimeError`/`ValueError`) the moment the column holds a non-conforming value — and `pipeline_cases.tenant_id` is exactly such a column: `NOT NULL text` where ~98/1961 rows hold ORG-ID strings (`org_01KJ…`), not UUIDs. Validate before casting (`uuid.UUID(v)` try-parse / regex) and fall back, and if you wrap the call in `except`, catch the RIGHT class — `except RuntimeError` will NOT catch a cast failure (2026-07-15):** review-gate 2026-07-15 rejected CASE-20260715-4C38F7 (harden run_env minting in `agent_dispatch.py`). Its revised `_fetch_shared_farm_status()` took a tenant-scoped path whenever `tenant_id` is truthy (`WHERE t.tenant_id = $1::uuid`, passing `pipeline_cases.tenant_id`); but that column is `NOT NULL text` so the tenant path is ALWAYS taken (the org-scoped fallback + multi-tenant collision `RuntimeError` fence is dead code), and for the ~5% of rows whose tenant_id is an org-id string the `$1::uuid` cast raises `InvalidTextRepresentationError`. `dispatch_case` wrapped the call in `except RuntimeError` ONLY — so the PostgresError propagates UNCAUGHT and BREAKS DISPATCH for every non-UUID-tenant case. `compileall`/`tsc` are BLIND (valid SQL, correct signature; the value is wrong at runtime for 98 real rows). Verify with `SELECT count(*) FILTER (WHERE col !~* '^[0-9a-f]{8}-...') FROM t` before trusting a text column is uuid-clean. Fix filed CASE-20260715-4C3FIX (validate tenant_id is a UUID before the tenant-scoped lookup; else fall back to org-scoped; keep the collision fence reachable). Author rule: never cast a text column to a strict type in a WHERE/param without validating the value first; asyncpg cast failures are `PostgresError`, not `RuntimeError`. Gate rule: for any branch adding a `::uuid`/`::int`/`::timestamptz` cast on a param sourced from a text column, `SELECT count(*) FILTER (WHERE NOT <matches format>)` on the real table — nonzero = a runtime-crash landmine invisible to compile/type gates.
- **A standalone column-RENAME migration dropped into `backend/db/migrations/control_plane/` is a BOOT-TIME landmine, not a deferred/manual change: the migration runner (`backend/app/database/migration_runner.py`) globs `control_plane/*.sql` and AUTO-APPLIES every pending file on the NEXT deploy's startup (advisory-locked). So renaming `<table>.<col>` WITHOUT renaming every code reference in the SAME branch crashes the live handler with asyncpg `UndefinedColumnError` ("column <old> does not exist") the instant the app boots — even though nobody ran `db.py` by hand (2026-07-17):** review-gate 2026-07-17 verdicted CASE-20260717-C52B61 as FIX (not merged). Its `v059_quotes_tenant_id_rename.sql` did an idempotent `ALTER TABLE quotes RENAME COLUMN org_id TO tenant_id` (and same on work_orders) with a correct DO-block guard — but master's Quote Machine backend still references `org_id` in 24 places (`quotes.py` `SELECT q.org_id`/`INSERT (quote_number, org_id,...)`/`LEFT JOIN tenants t ON t.tenant_id = q.org_id`; `quote_engine.py` `quote_row.get("org_id")`, work_orders INSERT). v056 created both tables WITH `org_id`, so the code was correct pre-rename; the migration flips the schema out from under it and boot auto-applies it → every quote/work-order query 500s. `compileall`/`tsc` are BLIND (valid SQL, valid Python — the column name is only wrong against the post-migration DB). Fix filed CASE-20260717-C52FIX (couple the rename with renaming all 24 org_id refs to tenant_id in ONE branch, or abandon the rename — the column works as org_id). Author rule: a column rename is a coordinated refactor, never a standalone migration — grep `git grep -n '<oldcol>'` across routers/services/tests and rename every site in the same branch, or don't rename. Gate rule: for ANY branch that RENAMEs/DROPs a column (or changes its type) in a control_plane migration, remember the file auto-applies at boot — grep master for the old column name; ANY surviving reference = a guaranteed live crash on next deploy → FIX, do not merge. (Extends the "referenced column must exist on master schema" rule to its inverse: a migration that removes/renames a column the merged code still uses is just as fatal.)
