- **Verify referenced DB columns against the LIVE schema — task-provided "SCHEMA FACTS" can be wrong (2026-07-10):** 6EC85C built `scripts/pipeline_backlog_report.py` faithfully to a task that asserted `pipeline_dispatch_log` has a `created_at` column; it does NOT (real timestamps: `queued_at` sparse, `dispatched_at` always-populated, `started_at`, `completed_at`), so Section 4 raises asyncpg `UndefinedColumnError` at runtime and crashes the report. Even when a task hands you "SCHEMA FACTS (do not guess others)", confirm every column exists (`information_schema.columns` or `\d <table>`) before writing SQL against it — a spec can be authored from a stale mental model. Fix: CASE-20260710-6EC85C-FIX.
- **`get_control_plane_db()` returns a `ControlPlaneDB`, NOT an asyncpg pool — call raw queries through `.pool` (2026-07-10):** `ControlPlaneDB` (`backend/app/database/control_plane.py`) exposes only a `pool` property plus named CRUD helpers; it has NO `fetchval`/`execute`/`fetch`/`fetchrow`/`fetch_all` methods and no `__getattr__` proxy, so `db.fetchval(...)` raises `AttributeError` at runtime and 500s the endpoint. Use `db.pool.fetchval/execute/fetchrow/fetch`. Extra trap: asyncpg.Pool has NO `fetch_all` method — the multi-row call is `db.pool.fetch(...)` (returns list of Records). Grep every `db.<method>(` in a router and confirm each resolves to a real asyncpg.Pool method before merge. (cobrowse.py write path fixed in CASE-20260710-0C818B; read endpoints in CASE-20260710-CB1FIX.)
- **A "flag for owner review, do NOT run in prod" migration must NOT land in the auto-applied dir; and never DROP a column still referenced by master code (2026-07-11):** CASE-20260711-234F76 was tasked to author a cobrowse_session_id DROP migration for OWNER review only (do not execute). Its branch put v042_drop_cobrowse_session_id.sql under backend/db/migrations/control_plane/ — but backend/app/database/migration_runner.py auto-applies EVERY vNNN_*.sql there at each boot, so merging = auto-DROP on next deploy, the exact opposite of "owner review only". Worse, the "no code writes this column" premise was FALSE: ai_support.py (INSERT+RETURNING+read), cobrowse.py, and support.py still write/read cobrowse_session_id, so the drop would 500 live support flows. Two rules: (1) if a migration is meant to be human-gated, it CANNOT go in an auto-run migrations dir — confirm where the runner picks files up before choosing a path; (2) a DROP COLUMN is safe only after every master reader/writer of that column is removed and shipped first — grep the whole backend for the column name and prove zero references before authoring the drop. Rejected at gate; fix: CASE-20260711-63241C. **INVERSE RECURRENCE 2026-08-11 (review-gate, CASE-20260811-003931 NOT merged → amended in place + requeued): the same "confirm where the runner picks files up" rule fails in the OTHER direction — a real migration authored into a directory nothing runs.** The branch created `backend/migrations/pipeline_case_attachments_scanned_at.sql` holding a correct, idempotent `ALTER TABLE pipeline_case_attachments ADD COLUMN IF NOT EXISTS scanned_at TIMESTAMPTZ NULL` — but `backend/migrations/` has been ARCHIVED since 2026-07-04 and its own README says those files "are NOT applied by anything, are NOT maintained, and MUST NOT be run against any database". Second half of the lesson: **the sub-task BRIEF named the wrong directory** ("Create an idempotent migration in backend/migrations/") and the agent complied faithfully — so this is a decomposition defect, not an authoring slip; a brief that hands down a file PATH is handing down an unverified fact, exactly like the wrong task-provided "SCHEMA FACTS" entry above. Author rule: before writing a migration, prove the target dir is live — for control-plane DDL that means `backend/db/migrations/control_plane/vNNN_*.sql` with N above the highest filename in the `schema_migrations` ledger; if the brief names a different path, correct it and say so in the handback rather than following it. Gate rule: for every new `*.sql` in a branch, name the runner that will execute it — "it is in a migrations directory" is not an answer, since `backend/migrations/` (zero), `backend/db/migrations/control_plane/` (auto at boot) and `migrations/apps/<slug>/` (ingestion-worker + `apps.migrations` array) have completely different execution semantics.
- **Postgres multi-line string concatenation: the `E` escape prefix goes ONLY on the FIRST literal of the group (2026-07-11):** `scripts/seed_openreplay_notices.sql` prefixed every continuation line (`E'a\n'` newline `E'b'`) — that is a syntax error, so the merged "run once" seed could never run and shipped broken. Adjacent literals separated by a newline concatenate, but only the first may carry `E`; continuation lines are bare `'...'` (their `\n` still escape via the group's leading `E`). Any seed/utility SQL delivered in a branch must actually be EXECUTED (against prod for idempotent seeds, or at least `db.py -f` syntax-run) before sign-off — "merged" ≠ "runs". Hand-fixed 92ba89cd.
- **NEVER run DDL on a tenant pool at request time — RLS-hardened tenants connect as `app_user`, which has no CREATE on schema public, and Postgres checks that privilege BEFORE the `IF NOT EXISTS` shortcut (2026-07-11):** legacy `_ensure_*` helpers in `apps.py`/`api_keys.py`/`rainbow.py`/`documents.py` ran `CREATE TABLE IF NOT EXISTS`/`ALTER TABLE` on `request.state.tenant_pool`; once a tenant moved to the hardened role every such endpoint 500ed with `InsufficientPrivilegeError` even though the tables already existed — GET /apps died and platform home showed "No apps yet" (no app launchable). Tenant schema belongs in provisioning (`provision_shard.py`/`backfill_rls_roles.py`), never in routers; if you must keep legacy ensure-DDL, route it through `tenant_db.ensure_tenant_ddl()` (swallows only the privilege denial, returns False — don't latch "initialised" flags on False). Emergency fix 51edf492; durable cleanup: CASE-20260712-TENDDL.
- **Migration files must NOT contain explicit `BEGIN;`/`COMMIT;` — the runner already wraps each file in its own `conn.transaction()`, so an inner `COMMIT` commits early and splits the DDL from the ledger INSERT into separate commits (2026-07-13):** CASE-20260713-A9D6F7's `v044_glossary_schema.sql` wrapped its whole body in `BEGIN;...COMMIT;`. asyncpg tolerates the nested `BEGIN` (warns "already a transaction in progress", no-op) and the inner `COMMIT` closes the runner's managed transaction, then the `INSERT INTO schema_migrations` ledger row runs in autocommit as a SEPARATE commit — so on partial failure the DDL can commit without a ledger row (idempotent `IF NOT EXISTS` saved it here, but it's fragile). `backend/db/migrations/README.md` states each file "must run inside a single transaction" — the runner provides it; NO other `vNNN_*.sql` uses BEGIN/COMMIT. Rule: at the gate, grep new migration files for `^\s*(BEGIN|COMMIT|START TRANSACTION)\b` and reject/flag; the transaction is the runner's job. (Merged as-is 2026-07-13 because idempotent + verified non-fatal, but never author it this way.)

- **Dry-run the WHOLE pending migration file end-to-end, not just the one statement you suspect — a single file can hide MULTIPLE independent boot-abort defects (2026-07-13):** batch5 diagnosed the `v044_glossary_schema.sql` boot landmine by dry-running ONLY the suspect `CREATE UNIQUE INDEX ... WHERE is_default=true` line in isolation, confirmed it errored, and filed the fix — but never ran the rest of the file. USING GIN (array_to_string(synonyms,' ') gin_trgm_ops)` → `ERROR: functions in index expression must be marked IMMUTABLE` (`array_to_string(anyarray,text)` is STABLE, not IMMUTABLE). Fixing only landmine #1 would have shipped a still-boot-bricking migration. IMMUTABLE ... array_to_string($1,' ')`), or (b) DEFER the index to the case that adds the query (correct without it on a small/empty table). - **`CREATE POLICY` has NO `IF NOT EXISTS` form in Postgres — an RLS migration using `CREATE POLICY IF NOT EXISTS ...` is a hard syntax error that aborts the whole migration file (2026-07-14):** CASE-20260714-6825BE's `v001_free_stream_core.sql` used `CREATE POLICY IF NOT EXISTS tenant_isolation ON ...`. Postgres (through 16) rejects `IF NOT EXISTS` on `CREATE POLICY` (unlike CREATE TABLE/INDEX/SCHEMA), so the file errors on first parse and the migration_runner boot-applies nothing. `compileall`/`tsc` are blind (SQL). Idempotent-policy pattern that works (used by 1B3898): wrap in `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_policies WHERE schemaname=... AND tablename=... AND policyname=...) THEN CREATE POLICY ...; END IF; END $$;`. Gate rule: grep any new migration for `CREATE POLICY IF NOT EXISTS` (and `CREATE TRIGGER IF NOT EXISTS`, also invalid) — both must use the `pg_policies`/`DROP TRIGGER IF EXISTS`+`CREATE TRIGGER` guard idioms instead. **The same grep must also catch the BARE `CREATE POLICY` (2026-07-30, review-gate, CASE-20260730-D74AD8 REJECTED):** `v022_interrupted_status.sql` guarded every other statement (`DROP CONSTRAINT IF EXISTS`, `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`) and then ended with an unguarded `CREATE POLICY tenant_isolation ON scantap.rfid_append_idempotency_keys USING (...)`. That parses fine, so it survives the `IF NOT EXISTS` grep above and applies cleanly the FIRST time — it aborts with 42710 "policy already exists" only on a RE-RUN, which is routine for `migrations/apps/<app>/` files after a partial apply or a second tenant pass. A migration whose other statements are all idempotent but whose policy is not is worse than one that is uniformly non-idempotent, because the failure only shows up during recovery. Rule: grep new migrations for `^\s*CREATE POLICY` (no `IF NOT EXISTS` needed in the pattern) and require the `DO $$ ... pg_policies ...` wrapper on every hit — the canonical local example is `migrations/apps/scantap/v017_label_templates.sql:48-57`.
