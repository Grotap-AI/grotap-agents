- Duplicate case cuts of the SAME endpoint (663AF1 + D290F7 both built GET /support/turn-credentials), **or a case filed for a defect that is ALREADY FIXED on master**: before building, `git log origin/master -- <the file your case names>` + grep the router for the route — if a twin case already landed, or the fix is already in, ship a superseded marker doc instead of a second implementation (two `@router.get` defs for one path merge silently and shadow each other). **A case filed AFTER the fix shipped is the dangerous shape: its body still describes the broken behaviour, so the agent "fixes" it by undoing the fix.** CASE-20260726-47DA45 (PIPEFB) was filed ~3h after b14ef604 shipped, decomposed into 5 subtasks, and its BBCEFC subtask reverted that live fix back into prod. Filing a case does not mean the bug is open — check master and the case's own clarification answers for "already applied / do not redo" before decomposing, and close as duplicate rather than re-deriving an approach the shipped fix explicitly rejected. **Generalize past the case's REQUEST to its DO-NOT clauses: "X is correct and working, do not touch it" is a snapshot of live state at FILING time, and cases sit in the queue for hours** — CASE-20260809-DF2B36 was filed 22:26 telling the builder the review gate's queue guard uses `psql` and must be left alone; the deployed guard became `python3 scripts/db.py` at 22:41 (grotap-agents `2346307`), 15 min later and in the OTHER repo, so the noon dispatch would have read a false map of the file it was told not to break. Re-verify every live-state assertion in a case body — the prohibitions too, and across BOTH repos — at build time, and amend the case in place (`jsonb_set` on `raw_input`) rather than filing a twin. Corollary for the gate: **a case rejected for a FALSE PREMISE is not a rejected CHANGE** — 4B3FAC's premise ("the psql call is inert") was disproven by 2648 successful log reads, yet the swap it ordered landed on its own merits minutes later because the added numeric assertion is what stops a query failure reading as queue-0; say which of the two you are rejecting.
- Before decomposing an auto-filed infra incident, search open cases for the same failure signature (repo + error_type + host) and ATTACH — never file a twin parent; children across ALL active parents touching one file set serialize, never parallel; at the gate, twin branches of one fix = merge the best ONE, close the rest superseded (2026-07-09 storm E4AC51+1CCDBD; durable fix CASE-20260709-541957).
- **Client/server feature split across two agents (s1 receiver / s2 sender) MUST pin the exact wire contract, or the halves silently don't compose (2026-07-10):** the agent-06 pickup-trigger feature was built as two cases — sender 7875EC POSTs `{DEPLOY_TRIGGER_URL}/trigger-deploy` with body `{case_id, branch}`; receiver 187629 only handles `POST /trigger-pickup` and requires body `{dispatch_log_id, task_file, server_ip, session}`. Path AND payload diverged (and neither matched the s1 "dispatch.sh for the dispatch_log_id" contract), so a live trigger would fall through to the status handler → 200 (FALSE success) and dispatch.sh never runs. When two agents build the two ends of one HTTP call, ONE side must own an explicit contract (path + method + headers + exact JSON keys) and the other implements against it verbatim; the builder AND the gate must grep both files and diff sender's URL/payload against receiver's route + required-fields validation before merge. Bonus: don't `asyncio.create_task()` a fire-and-forget coroutine without retaining the task ref (GC can cancel it). Fix: CASE-20260710-0798B7.
### ⛔ THE #1 RECURRING DEFECT — parallel work on one shared file, schema, or surface

Merged 2026-07-25 from 13 separate lessons that all had this one root cause. Two or more branches cut from the same base, each independently authoring the same file / table / router / symbol, are UNMERGEABLE in bulk: git shows no conflict (disjoint files, different filenames, or a clean union at a shared anchor) while the COMBINATION is structurally or semantically broken — and `compileall` / `tsc` / the standard gates catch NONE of it.

**Author rule — before you write:**
- `git log --all --oneline -- <file>` plus `git show origin/case-<sibling>` for every file you are about to edit. If a sibling subtask of your parent already added the state/import/callback you need, branch FROM that sibling's branch, or report that you are blocked on it — never re-declare it. (Parent CASE-20260724-C4E7B2 subtasks 5262C2 / 71798E / F47522 each re-added the same `readerState` useState + `ReaderServiceState` import + `svc.start(ingest,onError,setReaderState)` 3rd arg to `scan.tsx`; two also rendered different status widgets into the same `phase === 'scanning'` slot. 71798E was REJECTED on an unresolvable same-anchor conflict → CASE-20260725-SCANFX. Adding a second widget to a slot a sibling already fills is a defect even when both branches compile.)
- Before adding a router/service file, `git grep` master for its `APIRouter(prefix="/x")` and its `include_router` line. If it exists, ADD your endpoint to it and reuse its guard — never `new file` a second copy, and never re-add the import/include a sibling already wired. (0F071D re-created `security.py` containing ONLY its turnstile endpoint after f1374e92 had landed blocklist/overview, AND re-added the duplicate import + `include_router` → double-registration → CASE-20260719-TURNFX.)
- Build ONLY your own deliverable. If your task depends on an API/endpoint/schema owned by ANOTHER unmerged case, STOP and report the missing dependency — never implement your own copy of it.

**Decomposer rule — subtasks that share anything are ONE task or a sequential chain:**
- Two subtasks must NEVER be expected to edit the same file, screen, module, router or table. Same-file work is ONE case, or a STACK (`awaiting_deps` on the predecessor) — never a parallel fan-out. A per-defect split of one rejected case across one shared file is the worst form: 4FBFIX → 021A62 / 033EAE / 145964 / 430215 plus a parallel full-rebuild D0BD81 produced five rival rewrites of one `scantap-scheduled-sync.ts`, each with a different cron schedule, discovery query and trigger mechanism (three of them inert — no consumer of `scantap/sync.*` events exists), all superseded by CASE-20260721-D0BDFX. WIDENED 2026-07-29 (review-gate, CASE-20260729-67E390 + CASE-20260729-4156FA, both merged): **"fix file X" + "audit all OTHER call sites of the same pattern" is a same-file fan-out in disguise — the word "other" is not enforceable, because the sweep agent's first act is a `grep` that finds X.** 67E390 converted `test_scantap_sync_flows.py` to `IsolatedAsyncioTestCase`; its sibling 4156FA, told to sweep "all other `get_event_loop().run_until_complete()` sites", rewrote that same file's `_run` helper to `asyncio.run()` — two different remedies for one line, a guaranteed merge conflict (benign here only because one side DELETES what the other EDITS and no callers remain, so the deletion is the whole resolution). Decomposer rule: a sweep sibling must name the excluded path in its own text ("exclude `<file>` — owned by CASE-…") or stack `awaiting_deps` behind the specific case and rebase; never rely on "other" to scope a grep. Gate rule: when two queued cases describe the same PATTERN rather than the same file, still diff them against each other — pattern-scoped siblings collide on whichever file matches both.
- Anything 2+ siblings CONSUME is a foundation subtask that lands FIRST, with every consumer declaring `depends_on` it. Four foundation kinds, all observed:
  - **Shared schema** — exactly ONE migration owns the tables. batch29 (agents.grotap.ai per-company agent service): 0AE58E / 8C3DCC / 8FB536 each created their own `v051_agent_pools*.sql`, two with the SAME filename, with DISAGREEING schemas (`agent_pool_teams` PK `team_id` + `capacity INT` vs PK `id` + `capacity JSONB`, different status CHECKs). Because every migration is `CREATE TABLE IF NOT EXISTS`, whichever lands first SILENTLY wins and the loser's router then references columns that don't exist — a boot/500 landmine no `compileall`/`tsc` catches. Merged the superset (8FB536), rejected the two colliding admin branches → CASE-20260715-A91FC0.
  - **Shared low-level helper** — divergent param NAMES alone make it unmergeable. Parent B492E0: 25FDC8 added a response-body param to `loadtest/metrics.py` `_format_event()`/`record()` as `response_body`, A56C6B as `body`; 25FDC8 merged first, then A56C6B collided on both rewritten functions AND the shared `ml.record(...)` call site → CASE-20260719-A56CF1.
  - **Shared router/module file** — 772F9E / A318A4 / DB9B58 (one RequestLogMiddleware split three ways) EACH authored the whole new `backend/app/middleware/request_log.py` — 137/132/144 lines, divergent bodies (batched-executemany vs per-request-execute vs bounded-buffer) → merged A318A4 alone, CASE-20260719-RQLBAT to fold in the rest.
  - **Shared frontend surface** — a multi-SCREEN app is TWO foundations: the schema AND the shared `api/*.ts` + `types/*.ts` + `App.tsx` + stub-page surface. Quote Machine (parent CASE-20260717-524B03, 6 branches off one base `3d13f0a8`) collided on a rival `product_catalog.py` with a different shape, two routers both registering `GET /quotes/public/{token}` under the same `APIRouter(prefix="/quotes")` with divergent payloads (cents/int vs dollars/float), two rewrites of one page stub, an `App.tsx` that HIJACKED the `/quote-machine` dashboard route, and a wizard calling `POST /quotes` + `GET /quotes/model-options` + `POST /quotes/{id}/send-configure-link` that NO branch shipped. Even when the schema already landed, the router + shared-FE files are a SECOND shared foundation.
- A BRAND-NEW feature must have ONE ratified schema + service-signature contract BEFORE parallel dispatch, or each agent invents its own. Free Stream: three cases (60EB18 / 6825BE / 1B3898) each created `migrations/apps/free-stream/v001_free_stream_core.sql` with mutually-incompatible column contracts, two each created `free_stream.py`, `free_stream_ingest.py`, and `FreeStreamPage.tsx` → CASE-20260714-FS0INT. Gate tell for which foundation is canonical: the one an ALREADY-MERGED consumer's call signatures match exactly (D62068's `ingest_event(source_system=,event_action=,external_ref=)` + `set/clear_entity_status_modifier` pinned 1B3898 over the thinner two).
- Merge dependency order is **schema → service → tap/consumer → frontend.** NEVER merge a tap/consumer before the module it imports exists on master: D62068 was merged first and master then imported a nonexistent `app.services.free_stream_ingest`. It only avoided bricking prod because the tap is a fire-and-forget `asyncio.create_task` with a bare `try/except` around a lazy import — so the ImportError was swallowed, every event silently dropped, the feature 100% inert and invisible to `compileall`/`tsc`.
- Prefer FEWER, larger subtasks. An over-split that collides costs far more than a subtask that is slightly too big.

**Gate disposition ladder — never hand-weave two full-file rewrites:**
1. Diff queued branches **against each other**, not just against master, for same-symbol redefinition, `new file mode` on one path, and shared-helper contract drift. 449C80 + EC0865 both added `openreplay_provider.get_similar_sessions()` with incompatible signatures (`k=` search-based on the OLD `type=USER_EMAIL` filter format vs `limit=` on the CE `/similar` endpoint) — Python keeps only the LAST def, silently killing the other plus its tests. Worse, sibling 444866 merged the same batch had already proved that old filter format broken on CE v1.27, so 449C80 was dead-on-arrival. A branch whose foundation another in-flight branch is rewriting must be rebased onto the winner or skipped, never merged as-authored → CASE-20260719-ORSMFX.
2. Reason about the **combined migration set**, which git cannot see. Grep every new `*.sql` in the batch for `CREATE TABLE` on the same table name. The runner applies files in sorted FILENAME order: `v044_glossary_schema.sql` (g) created the Object Glossary tables, then `v044_object_glossary.sql` (o) — bare `CREATE TABLE`, no `IF NOT EXISTS` — errored "relation already exists" and ABORTED the runner, boot-failing every deploy; and a third incompatible `v042_object_glossary.sql` sorts BEFORE both, creating the tables in the WRONG shape first and poisoning the canonical file's `IF NOT EXISTS` plus the already-merged seed script. Merged A9D6F7, filed CASE-20260713-C31FDF, superseded E535B8. Every schema migration uses `CREATE TABLE IF NOT EXISTS`.
3. If a branch "adds" a migration whose filename ALREADY exists on master, `diff <(git show origin/case-X:PATH) <(git show origin/master:PATH)`. Different body → DROP the branch copy (the applied canonical is authoritative; overwriting it is a checksum-mismatch BOOT ABORT via `migration_runner.run_migrations`) and re-verify the branch's CODE against `information_schema.columns`, never against its own migration. 44E02E and 53DD04 each re-added `v045_voice_calls.sql` with `id UUID PRIMARY KEY` when the live table's PK is `call_sid` with NO `id` column — 44E02E's `_CONTACT_SELECT` (`vc.id AS vc_id`) would 500 the live authed `GET /contact` and 53DD04's `_find_known_number` every outbound call → CASE-20260713-44E0FX + -53DDFX.
4. Before merging any branch that REWRITES a function, `git grep` master for the symbols its diff references. Master renamed/restructured them → the branch is STALE: file a rebase case, do NOT hand-weave. Three cases targeted `agents/team-run.sh` at once; master's 3508fd78 replaced the flat `_run_attempt 1/2/3` ladder with `_run_rung_with_retries <rung>`, stranding D41872 and A39F15 on now-deleted symbols → one combined CASE-20260712-B39D41. Where a branch's diff would REGRESS a value master has since changed, keep master's current value and take ONLY the net-new addition (`agents/config.sh` 4E28E5 vs the team2 `TEAM_MODEL_STRONG` deepseek-chat→grok-4.5 swap).
5. Then pick disposition by severity:
   - **Cleanly separable** (each branch owns its own files) → merge them, union-resolving only true append points: `main.py` `include_router` at one anchor, additive `api/*.ts` functions. (Quote Machine: merged F052B5 canonical catalog + 9A73C7 work_orders + DBA395 admin quotes/public viewer/v057, fix-cased the three colliders as 842FX2 / 0CBFX2 / 20DFX2.)
   - **2+ siblings `new file mode` the same path** → identify the superset/canonical, merge THAT ALONE, fix-case the rest. Never merge a partial "base" fragment first: doing that on 4FBFIX (021A62, which still carried DEFECT-3) left every sibling colliding against it AND each other.
   - **Semantic disagreement with a physical or live consequence** → merge NONE, reject ALL, file ONE consolidation that re-implements the union in sequence with every conflict explicitly resolved (citing the source branches so the agent cherry-picks the good code). Eight cases fanned onto `platform/mobile/scantap/services/CS463TcpReaderService.ts` rewrote `_encSetReaderConfig` three ways (0x01+KeepAlive@5000 vs 0x01+KeepAlive@10000 vs 0x00-no-reset-no-keepalive) and gave `C1G2SingulationControl`'s session byte two contradictory bit layouts (`session<<6` bits[7:6] spec-correct vs the old `0x04` bits[2:1]); the CORRECT answer — 0x00 AND a keepalive — existed on NO single branch. Picking wrong writes malformed LLRP frames to physical CS463 hardware and scanning silently breaks; `tsc` and the backend/orch/frontend gates don't even cover scantap mobile → CASE-20260724-LLRPCX. Treat `CS463TcpReaderService.ts`, `readerConfig.ts` and `services/llrp/src/*` as a SINGLE-OWNER touch surface.
6. A rebase/fix case must be scoped to REUSE what merged — drop A56C6B's whole `metrics.py` diff and keep only its `__main__.py` novel-status logic reading the merged `response_body` key — and must NAME what is already on master so the agent doesn't rebuild it. Salvage a stale branch's genuinely additive hunks (0F071D's `config.py` + `shared_state.py` were fine; only the router + wiring collided).
7. **RUN the existing test file for every source file in the diff — a branch that leaves a green suite RED is a REVERT, not a fix, and `compileall`/`tsc` are blind to it (2026-07-26, CASE-20260726-BBCEFC + -7AB496 under duplicate parent -47DA45):** BBCEFC re-implemented `team1_requeue_webhook` the exact way b14ef604 had explicitly rejected hours earlier — mint a `pending` dispatch row + commit a task file for `dispatch-poller.sh`, which runs on NO fleet host — reverting a LIVE fix: that pending row is precisely what hides the case from the assign loop's `NOT EXISTS pending/active`, and it also dropped `status='plan_approved'`, deadlocking the case by status too. It touched ONLY `pipeline.py` and left `backend/tests/test_team1_requeue.py` untouched and RED (8 of 12 failing, including `test_writes_no_dispatch_row` and `test_leaves_no_row_that_hides_the_case`) — it merged anyway and shipped to prod. Gate rule: for each `<file>` in the diff, locate its `tests/test_<file>.py` and RUN it; if the branch neither passes it nor updates it, reject. Corollary — **a branch that REWRITES an existing test file to match its own diff is asserting its implementation, not the requirement**: sibling 7AB496 landed 5 min after the hand-revert and rewrote that same suite (+388/-54) to assert the reverted behaviour, leaving master red a second time. Always diff the test file too and check WHICH behaviour the new assertions encode against master's shipped code; salvage only the implementation-independent classes (here `TestAssignLoopTeam1Case`) and drop the rest. GENERALISED 2026-07-26 (review-gate rg11, CASE-20260726-873C0F REJECTED → CASE-20260726-MANIVL) — **a test-only branch is not automatically safe to merge: when the case asks a test to "clarify expected behaviour", an agent may answer it by declaring master's CURRENT behaviour "intended by design", which turns a live defect into a green assertion that future fixes must delete.** The case named the requirement ("must not silently move a manual-only flow onto a schedule"); the 630-line suite instead asserted the opposite in 4 places with docstrings reading "by design — not a bug", and all 25 tests passed because they were derived FROM the implementation. The consumer contract settled it in the branch's favour of nothing: a sibling merged 20 min earlier (A6D184) had just documented `ingestion-worker/.../scantap-scheduled-sync.ts` as the SINGLE CONSUMER of the stored `settings.flows`, where an explicit `'manual'` is honoured as never-scheduled ("a real choice"), so the convergence write-back it blessed permanently erases that choice and starts polling. Author rule: a case's open behavioural question is answered by the REQUIREMENT text plus the consumer's documented contract — never by "this is what the code does today"; if the two disagree you have found the bug you were sent to test for, and the deliverable is a defect report, not an assertion. Gate rule: for a tests-only diff, do not stop at "N passed" — read the assertions of the scenario the case flagged as open, and reject if they codify behaviour that contradicts the requirement or another component's contract (100% pass rate is the expected symptom, not evidence). EXTENDED 2026-07-29 (review-gate, CASE-20260726-AEAFED MERGED → follow-up CASE-20260729-CVINV1) — **"N passed" also hides the opposite failure: a test that CANNOT FAIL. An assertion wrapped in a condition read off the value under test (`if resolved[flow]["inherited"]: assertEqual(...)`) passes VACUOUSLY the moment that flag regresses, so the test named as the guard for an invariant is precisely the test that will not catch it.** AEAFED's `test_inherited_true_always_means_interval_equals_sync_interval_all` loops over six `sync_interval_all` values but asserts nothing when `inherited` is False — and it is the ONLY test touching `"15m"`, `"30m"` and `"daily"`, so for those three defaults the suite asserts nothing at all. Proven in one command by MUTATION: replacing `inherited = raw_interval in (None, "", "inherit")` with `inherited = False` in `backend/app/services/scantap_sync.py` left that test GREEN (1 passed, 6 subtests) while 11 other tests in `tests/services` went red. Gate rule: for every NEW test in a diff, mutate the line of production code it claims to protect and confirm the test goes RED — a new test that stays green under the mutation is documentation, not coverage, and the mutation costs one edit plus one `pytest -k` (same discipline as "mutation-test the guard by deleting each UA line" in `wiring-contracts.md`). Author rule: assert the flag UNCONDITIONALLY first (`assertTrue(...)`), then the implication — an `if` in a test body is usually a missing assertion wearing a guard's clothes. Counting rule that pairs with this: record the baseline (`tests/services` = 71 on master here, 74 with the branch) so "added 3 tests, removed none" is an audit fact, not an impression. EXTENDED 2026-07-30 (review-gate, CASE-20260729-6B6E3B REJECTED → CASE-20260730-IDEMTS) — **the cheapest cannot-fail test is the one that builds BOTH sides of the comparison from the same literal: `f(x) === f(x)` re-proves the function is pure and says nothing about the system the case asked about.** Told to "simulate a failed send with app restart and verify the resend uses the identical idempotency_key", the branch added two tests that hand-write two IDENTICAL `ChunkingIdentity` object literals and assert `buildIdempotencyKey(UUID, p, a) === buildIdempotencyKey(UUID, p, b)` — with the "restart" existing only in a comment. The file ALREADY had a purity test, and nothing in either new test touches persistence or `app/(tabs)/send.tsx`, where the real risk lives (`chunkSize = batch.synced_parts > 0 && batch.synced_chunk_size != null ? batch.synced_chunk_size : MAX_RECORDS_PER_REQUEST`) — mutate that line and both tests stay green. Reviewer tell: read where each side of the assertion COMES FROM; if the expected value was constructed in the test body rather than re-derived through the code path the case named, the test is a tautology no matter how detailed its comments. Author rule for any "survives a restart/retry/redeploy" case: the second derivation must re-read PERSISTED state through the production helper — extract that helper if it is inlined in a screen — never re-type the inputs. SAME ROOT CAUSE, DOCS EDITION (CASE-20260729-EDFA5A REJECTED → CASE-20260730-DOCLOO): a case asking you to replace a STALE rationale with the current one is asking for an experiment, not a plausible mechanism. The branch rewrote four `run()` docstrings to blame `asyncio.run()` for "redis.asyncio client connections … raising 'Event loop is closed' in `__del__`" — but all four helpers already end in `finally: loop.close()` (so "closes the loop" cannot distinguish the two patterns), none of the four modules references redis, and substituting `return asyncio.run(coro)` into ALL FOUR and running them together gives `180 passed` with `grep -c PytestUnraisableExceptionWarning` = 0 and `grep -c 'Event loop is closed'` = 0. The original rationale was indeed stale — the two surviving bare `asyncio.get_event_loop()` sites are inside async functions, so they resolve the RUNNING loop and are immune to a nulled global slot — but a confident FALSE mechanism is worse than the stale comment it replaces, because the next reader will act on it. Author rule: run the experiment, paste the command and its output into the run summary, and if nothing reproduces, write that ("retained as a defensive convention; asyncio.run() measured equivalent on <date> over these files") instead of inventing a cause. **MIRROR CASE 2026-07-30 (review-gate batch2, CASE-20260730-D85B71 REJECTED → CASE-20260730-B6C701): a TESTS-ONLY branch can leave the suite red too — and the tell is that the case's PREMISE was false.** The case said "add a test verifying `reconcileUnsentBatches()` correctly awaits `dbReady`". It does not: `platform/mobile/scantap/services/reconciliation.ts` imports only `{ listBatches, markBatchSyncedAt }` and `_run()` calls `listBatches()` immediately. `dbReady` existed (exported by an earlier commit) but nothing consumed it — the promise was PUBLISHED, never AWAITED, which is exactly the shape that makes a premise read as already-true. So the agent wrote a genuinely good 124-line suite, never ran it, and shipped `3 failed, 1 passed`. Author rule: when a case says "add a test that verifies X", OPEN THE CODE AND CONFIRM X IS IMPLEMENTED before writing the test — if it is not, the deliverable is the guard PLUS the test, and say so; a red test is not evidence of diligence. Then RUN IT: a tests-only diff has no excuse, there is nothing else to judge it by. Reviewer rule: for any diff that is 100%% test files, execute the suite — do not infer from the standard gates, which pass over red tests by construction, and remember whole trees (`platform/mobile/**`, `agent/**`, `scripts/**`) have NO gate at all. Separate PRE-EXISTING red from branch-introduced red by running the same suite on a pristine `git worktree` of origin/master (here `test/database.test.ts` was already 4-failed/4-passed on master and had nothing to do with the branch). Finally, when the fix is small, PROVE it in a scratch tree and put the measured before/after in the fix case — two lines (`import { dbReady, … }` + `await dbReady;`) took this suite to `4 passed` — but revert the scratch patch and route the change through an agent; never hand-patch the branch.

**Reviewer tells — any ONE of these is a structural collision, not a feature:**
- Two `case-*` branches with the same `parent_case_id` and identical file lists in `git diff --stat`.
- Two branches both `create mode 100644` the same path.
- Two `v0NN_*.sql` files creating the same table with differing column definitions.
- Two routers sharing an `APIRouter(prefix=...)` plus the same sub-path (→ ambiguous double route).
- A page/component calling `api.post(<path>)` for a route that is not on master.
- A second `include_router(X)` for an already-wired router.
- A "wire X in main.py" diff that REPLACES rather than ADDS a registration: DB9B58 swapped `from app.middleware.request_id import RequestIdMiddleware` → `...request_log import RequestLogMiddleware` and dropped `add_middleware(RequestIdMiddleware)` entirely, silently deleting request_id correlation and the `X-Request-Id` echo. `compileall` is blind — both imports are valid.
- Verify every merged router's columns against the LIVE schema before trusting the spec: the Quote Machine F052B5 spec's column names (`setup_fee_cents`/`monthly_cents`/`brand_type`) were WRONG and the agent's code-vs-schema check was right. Trust the live schema over spec prose.
