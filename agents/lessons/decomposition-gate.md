# Lessons — Decomposition, review & gate

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** you are DECOMPOSING a case into subtasks, REVIEWING a branch, or running the MERGE GATE. Also read it before you fan any work out in parallel.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,
> claim-first, with the case id. Before appending, check whether an existing line already
> covers it — generalize that line instead of adding a near-duplicate.

- Duplicate case cuts of the SAME endpoint (663AF1 + D290F7 both built GET /support/turn-credentials): before building, `git log origin/master` + grep the router for the route — if a twin case already landed, ship a superseded marker doc instead of a second implementation (two `@router.get` defs for one path merge silently and shadow each other).
- Before decomposing an auto-filed infra incident, search open cases for the same failure signature (repo + error_type + host) and ATTACH — never file a twin parent; children across ALL active parents touching one file set serialize, never parallel; at the gate, twin branches of one fix = merge the best ONE, close the rest superseded (2026-07-09 storm E4AC51+1CCDBD; durable fix CASE-20260709-541957).
- **Client/server feature split across two agents (s1 receiver / s2 sender) MUST pin the exact wire contract, or the halves silently don't compose (2026-07-10):** the agent-06 pickup-trigger feature was built as two cases — sender 7875EC POSTs `{DEPLOY_TRIGGER_URL}/trigger-deploy` with body `{case_id, branch}`; receiver 187629 only handles `POST /trigger-pickup` and requires body `{dispatch_log_id, task_file, server_ip, session}`. Path AND payload diverged (and neither matched the s1 "dispatch.sh for the dispatch_log_id" contract), so a live trigger would fall through to the status handler → 200 (FALSE success) and dispatch.sh never runs. When two agents build the two ends of one HTTP call, ONE side must own an explicit contract (path + method + headers + exact JSON keys) and the other implements against it verbatim; the builder AND the gate must grep both files and diff sender's URL/payload against receiver's route + required-fields validation before merge. Bonus: don't `asyncio.create_task()` a fire-and-forget coroutine without retaining the task ref (GC can cancel it). Fix: CASE-20260710-0798B7.
- **Parallel branches that each rewrite the SAME control-flow function go stale the moment master refactors that function's structure — merging them then means hand-weaving two incompatible rewrites, which the gate must refuse (2026-07-12):** three cases targeted `agents/team-run.sh` at once. Master merged CASE-...-F27E64 (commit 3508fd78) which replaced the flat `_run_attempt 1/2/3` escalation ladder with `_run_rung_with_retries <rung>` (per-rung retry cap + circuit-breaker). Two OTHER in-flight branches — CASE-20260712-D41872 (prompt-cache prefix invariant) and CASE-20260712-A39F15 (bounded retry context) — had both been cut from the OLD ladder and each rewrote the same message-assembly flow; after the refactor landed, both referenced now-deleted symbols (`_run_attempt`, the "Attempt 1/2/3" sections) and conflicted structurally with master AND with each other. The gate merged neither and filed ONE combined rebase case (CASE-20260712-B39D41) carrying both intents forward onto the current `_run_rung_with_retries` structure. Lessons: (a) COALESCE cases that touch the same file's core control flow onto ONE sequential branch — never dispatch them as independent parallel branches; the last ones to land are unmergeable. (b) At the gate, before merging any branch that rewrites a function, grep master for the symbol names the branch's diff references (`_run_attempt` etc.); if master renamed/restructured them, the branch is stale → file a rebase case, do NOT hand-weave. (c) Same stale-base trap hit `agents/config.sh` in the same batch: CASE-...-4E28E5 was cut before master swapped team2 `TEAM_MODEL_STRONG` deepseek-chat->grok-4.5, so its merge tried to regress that line — resolve by keeping master's current value and taking ONLY the branch's net-new addition (team3).
- **A feature split across cases must have exactly ONE schema migration — sibling API/frontend cases must depend on it, never ship their own copy of the same tables; duplicate migrations collide at RUNTIME by filename-sort order and crash boot, and git cannot see it (2026-07-13):** the Object Glossary feature arrived as 4+ cases. CASE-20260713-A9D6F7 shipped the canonical `v044_glossary_schema.sql` (the one the already-merged `scripts/seed_object_glossary.py` depends on: `glossary_objects(explanation, synonyms text[], md_refs)` + seeded default libraries). But CASE-20260713-C3E1FD (the search API) ALSO shipped `v044_object_glossary.sql` that `CREATE TABLE`s the SAME three tables, and CASE-20260713-E535B8 shipped a THIRD, incompatible `v042_object_glossary.sql` (`canonical_name/category/metadata`, single `synonym` col). Two runtime traps the merge gate's `compileall`/`tsc` never catch: (a) the runner applies files in sorted filename order, so `v044_glossary_schema.sql` (g) creates the tables, then `v044_object_glossary.sql` (o) — using bare `CREATE TABLE` with NO `IF NOT EXISTS` — errors "relation already exists" and ABORTS the migration runner → every deploy boot-fails; (b) `v042_*` sorts BEFORE `v044_*`, so the incompatible E535B8 schema would create the tables with the WRONG shape first, poisoning the canonical migration's `CREATE TABLE IF NOT EXISTS` (no-ops on the bad tables) AND breaking the seed script + default-library INSERTs. Git shows NO conflict (different filenames, disjoint files) — the gate must reason about the *combined* migration set. Rule: at the gate, when >1 branch in a batch adds control_plane migrations, grep every new `*.sql` for `CREATE TABLE` and check for the same table name across files; merge only the ONE canonical schema, and file rebase cases for the siblings to (i) DELETE their duplicate schema migration and (ii) move any app-registration/data INSERTs into a NEW `vNNN` file. Every schema migration must use `CREATE TABLE IF NOT EXISTS`. Review gate 2026-07-13: merged A9D6F7, filed CASE-20260713-C31FDF (rebase C3E1FD), superseded E535B8.
- **Filing a fix case (review gate or ad-hoc) = set the reporter in BOTH the `reporter` column AND `case_data.reporter` — the POLSUB policy guard only reads `case_data->>'reporter'` (2026-07-13):** batch5 filed P1 CASE-20260713-B84124 with only the column set to `review-gate`; the async `pipeline/policy.complete` callback then yanked it from `submitted` back to `awaiting_human` within ~2 min of EVERY resubmit (guard at `backend/app/routers/pipeline.py` ~371 saw no JSON key → not gate-exempt), stranding the P1 during a redeploy freeze with no hold row to signal it. Siblings filed WITH the JSON key (C31FDF, B39D41) were untouched. Recovery: `jsonb_set(case_data,'{reporter}','"review-gate"')` + flip to `submitted`. Durable fix (guard checks column OR JSON key): CASE-20260713-D6F50F.
- **When the schema a feature-cluster depends on ALREADY landed on master (a prior batch merged the canonical `vNNN`), sibling API/frontend branches forked BEFORE it still carry their OWN copy of that migration — the 3-dot diff shows it as "added", but merging it OVERWRITES the applied canonical file with a different body → checksum-mismatch BOOT ABORT; AND their code assumes THEIR migration's shape, not the deployed one (2026-07-13):** review-gate batch7 — master already had canonical `backend/db/migrations/control_plane/v045_voice_calls.sql` (PK `call_sid`, NO `id` column; the live table matches). CASE-20260713-44E02E and -53DD04 each re-added `v045_voice_calls.sql` at the SAME canonical path with a DIFFERENT body (`id UUID PRIMARY KEY`, `call_sid` merely UNIQUE). `migration_runner.run_migrations` records a sha256 per file and, when a ledger filename's checksum no longer matches, RAISES → boot aborts on the next redeploy. Worse, both branches' CODE assumed their own shape: 44E02E's `_CONTACT_SELECT` used `vc.id AS vc_id` and 53DD04's `_find_known_number` ran `SELECT id FROM voice_calls` — but the deployed table has no `id` column, so 44E02E 500s the LIVE authed `GET /contact` and 53DD04 500s every outbound call once provisioned. `git` shows both files as clean adds; only a byte-compare vs master's current file + a column check against the live DB reveal it. Gate rule: (1) for any migration a branch "adds" whose filename ALREADY exists on master, `diff <(git show origin/case-X:PATH) <(git show origin/master:PATH)` — if it differs, DROP the branch copy (never overwrite an applied migration; the canonical is authoritative) and re-verify the branch code against the LIVE column list (`information_schema.columns`), not the branch's own migration. (2) A voice/PK table using `call_sid` as PRIMARY KEY has NO surrogate `id` — grep merged endpoint code for `voice_calls` `id` references. Both branches rejected; fixes filed CASE-20260713-44E0FX + -53DDFX (drop the dup migration, use `call_sid`/`SELECT 1`, and FOLD -53DDFX's `/voice/outbound` into the existing `voice.py` under the shared router — 128C90 already created that file).
- **An agent told to "MODIFY endpoint X" from a stale base often RE-CREATES the whole router file instead — merging it silently REGRESSES the version a prior case already landed (different impl + different response shape) and re-adds a duplicate `main.py` mount (2026-07-13):** CASE-20260713-A18BBF was scoped to add a `contact_card` to the existing `GET /products/presentation`, but it forked before CASE-20260713-7E36FE landed `backend/app/routers/products.py` on master and shipped a full-file re-creation: a different category source (`request.state.lead_category`, never set by middleware, vs master's `_extract_category` JWT decode) and a different `_AGENTS_OVERVIEW` structure, plus a duplicate `from app.routers.products import ...` + `include_router` in `main.py` (already present on master). `tsc`/`compileall` pass; the regression only shows by reading master's current file. Gate rule: when a branch's diff shows a NEW file (`new file mode`) for a path that ALREADY exists on master, treat it as a stale-base re-creation, NOT an add — reject and file a rebase case that MODIFIES master's current file (here: keep `_extract_category` + `_AGENTS_OVERVIEW`, add only `contact_card` from `TWILIO_FROM_NUMBER`/`VOICE_CONTACT_NAME`/`VOICE_CONTACT_TITLE` env vars; do not touch `main.py`). Fix filed CASE-20260713-A18BFX.
- **A "delete the duplicate migration" fix case can be pointed at the CANONICAL file: if the fix branch's base already carries the single good copy (the dup only ever existed on the rejected parent branch, never on this lineage), the agent deletes the real source-of-truth — removing the table's only creator, so fresh provisioning silently loses it (2026-07-13):** CASE-20260713-53DDFX was told "DELETE the re-added `v045_voice_calls.sql` (canonical already applied/live)" — correct advice for the parent 53DD04 branch that shipped a divergent copy, but this FIX branch forked from a base that already had the canonical `v045_voice_calls.sql` (byte-identical to master's applied file) and NO second copy. The agent `git rm`'d it anyway; merging as-is would delete master's sole `CREATE TABLE voice_calls` (existing prod DB unaffected since it's already applied, but any fresh control-plane provision loses the table). Gate rule before honoring a "delete the dup" instruction: confirm a dup actually EXISTS on this branch — `git cat-file -e base:PATH` and byte-compare vs `origin/master:PATH`; only delete when the branch's copy DIFFERS from the applied canonical. If the branch's file == master's applied file, there is no dup — keep it. Gate-fixed by restoring master's `v045_voice_calls.sql` in the merge; kept only the branch's `voice.py`/`tenant_auth.py`/test additions.
- **One case's branch can bundle a DIFFERENT case's work (scope bleed) — merge each case to its own scope, not the whole commit: co-merging duplicates the other case's files and collides when that case lands on its own (2026-07-13):** CASE-20260713-53DDFX (voice `/outbound`) was built as a single commit `feat(voice+products): ... (CASE-53DDFX + A18BFX)` that ALSO re-implemented A18BFX's `products.py contact_card` (a different, cleaner version than A18BFX's own branch). While reviewing, the orchestrator merged A18BFX's dedicated branch to master. Merging 53DDFX whole would have re-conflicted `products.py`/`test_products_presentation.py` and landed a competing contact_card impl. Gate rule: when a branch touches files outside its case's stated scope AND another queued/merged case owns those files, do a `--no-commit` merge and resolve the out-of-scope files to `HEAD` (`git checkout HEAD -- <path>`), keeping only the files the case actually owns; note the scope correction in the merge message.
- **Before rewriting a SHARED control-flow gate, check whether master already generalized the SAME flow via a peer commit that landed after your branch was cut — two parallel solutions to one gate collide as a STRUCTURAL merge conflict, and yours may be the redundant/inferior one (2026-07-13):** B9FFCA rewrote dispatch.sh's team-routing gate as `[[ "$DISPATCH_TEAM" != "team1" ]]`, but master commit 514db03d had already generalized the identical gate via `get_team_runtime "$DISPATCH_TEAM" == "agents/team-run.sh"` (config-driven, strictly better — it honors `TEAM_RUNTIME_SCRIPT`). Merge hit a structural conflict; the branch's routing half was fully superseded while only its per-team-cap half retained value. Gate rule: don't hand-weave — abort, and file a rebase case that keeps ONLY the branch's non-superseded delta re-applied onto master's current structure (here: drop the `!= team1` gate, re-apply just the `TEAM_DAILY_CAP` per-team cap onto master's `_team2_daily_cap_ok`/`get_team_runtime` code, + fix the companion test). Fix filed CASE-20260713-B9FFFX.
- **Decomposing a NEW feature across parallel agents WITHOUT a ratified schema/service contract makes each agent invent its own incompatible schema, router, and service — the pieces then cannot be integrated and the whole cluster stalls at the gate (2026-07-14):** review-gate 2026-07-14 found the "Free Stream" feature split into ~8 parallel cases where THREE (CASE-20260714-{60EB18,6825BE,1B3898}) each created `migrations/apps/free-stream/v001_free_stream_core.sql` with mutually-incompatible column contracts (`entity_id/entity_type/event_type/payload` vs `id/source_system/event_action/external_ref/status_modifier/current_classification`), TWO created `free_stream.py` routers, TWO created `free_stream_ingest.py`, and TWO created `FreeStreamPage.tsx` — none mergeable together. Worse, a dependent TAP (CASE-20260714-D62068, Stripe billing → Customer events) was merged FIRST (by the orchestrator) while its `app.services.free_stream_ingest` module was still unmerged: master now imports a module that doesn't exist. It didn't brick prod only because the tap is `asyncio.create_task(...)` fire-and-forget with a bare `try/except` around a lazy import — so the ImportError is swallowed and every event is silently dropped (feature 100% inert, invisible to `compileall`/`tsc`). Rules: (1) a feature decomposition MUST ratify ONE canonical schema + service-signature contract BEFORE parallel dispatch — the schema/ingest-owner case defines it, dependents import it; don't let N agents each scaffold their own `v001`. (2) Merge dependency order is schema→service→tap→frontend; NEVER merge a tap/consumer before the service module it imports exists on master (grep the branch for `import ...<new_module>` and confirm the module is live or merged in the same batch). (3) At the gate, the tell that a "foundation" case is really the canonical one: an already-merged consumer's call signatures match it exactly (D62068's `ingest_event(source_system=,event_action=,external_ref=)` + `set/clear_entity_status_modifier` pinned 1B3898 as canonical over the thinner 60EB18/6825BE). When a cluster has incompatible parallel foundations, don't hand-weave — file ONE integration/rebase case naming the canonical and the outliers-to-rebase (filed CASE-20260714-FS0INT), and hold every cluster branch.
- **Within a coalesced cluster, two agents can pick DIVERGENT data models for the SAME feature (a new dedicated table vs. columns bolted onto an existing table) — merge the branch that carries the actual consumer/worker, reject the branch whose table nothing reads, and confirm any dark-launch enable command UPDATEs the exact table/column the worker gates on (2026-07-15):** review-gate 2026-07-15 batch7, Free Stream Gmail sync (FSA-E) split into CASE-20260714-6541F8 (the worker `gmail_sync.py`) and CASE-20260714-41B930 (setup hold + dark-launch docs). 6541F8 gated each account on `loop_engine.connected_accounts.gmail_sync_enabled` (columns added by `v006_gmail_sync_cursor.sql`, reusing loop-engine's existing OAuth tokens); 41B930 instead created a brand-new `free_stream.stream_gmail_accounts` table with its own `sync_enabled`, and its operator hold said `UPDATE free_stream.stream_gmail_accounts SET sync_enabled=true` — which the worker NEVER reads, so flipping it does nothing and the feature can never be un-darked via the documented path (orphan table + inert dark-launch). `compileall`/`tsc` are blind (the table exists, the SQL is valid — it's just the wrong table). Gate rule: for a dark-launch/feature-flag branch, grep the actual consumer for the flag it reads (`SELECT ... WHERE <flag>`) and confirm the enable command targets THAT table+column; when two cluster branches model the same state differently, merge the one with the live consumer and file a fix case to rebuild the docs/hold against it (merged 6541F8, closed 41B930 superseded, filed CASE-20260715-FSDLFX).
- **A full-component REWRITE branched before a peer commit added a small mount/wiring into that same component will structurally conflict and, if force-resolved toward the branch, silently DROP the peer's just-landed integration — abort and rebase, never take-theirs (2026-07-15):** review-gate 2026-07-15 batch8 CASE-20260715-B7D70C rewrote `StreamWorkspace.tsx` into the full workspace but was cut from `daeddea1`, BEFORE master `5540959d` replaced the FSA-D seam with `<PromptBar event={event} />`. The branch has ZERO PromptBar reference; a `-X theirs` or blind take-branch merge would delete master's mount, orphaning `PromptBar.tsx` and defeating its own test case. Gate tell: `git show <branch>:<file> | grep <symbol-master-just-added>` returns nothing → the branch predates the wiring. Rule: file a rebase case that re-applies the branch's rewrite onto current master AND re-inserts the peer's mount in the right pane; hold the branch. Filed CASE-20260715-WSRBFX.
- **Decomposing a BRAND-NEW feature that introduces a shared schema/router/file into parallel cases dispatched off a base that lacks it makes every slice independently CREATE that same file+tables — a guaranteed structural collision; land the shared foundation FIRST (or coalesce onto one branch), never fan out slices that each `CREATE TABLE`/create-the-same-router in isolation (2026-07-15):** review-gate 2026-07-15 batch29, the agents.grotap.ai per-company agent-service feature was split into CASE-20260715-0AE58E (admin Companies grid + tenant-service PUT), CASE-20260715-8C3DCC (pool CRUD/clone API), CASE-20260715-8FB536 (customer read-only view). All three were built off a master with NO `agent_pools`/`agent_pool_teams`/`tenant_agent_service` tables and NO `backend/app/routers/admin_agent_pools.py`, so each branch created its own `v051_agent_pools*.sql` (0AE58E and 8C3DCC even used the SAME filename `v051_agent_pools.sql`) AND 0AE58E+8C3DCC both created the SAME file `admin_agent_pools.py` with different content. Worse, the three schemas DISAGREED: 8C3DCC used `agent_pool_teams` PK `team_id` + `capacity INT` + `daily_cap` + status CHECK `active/inactive`, while 0AE58E/8FB536 used PK `id` + `capacity JSONB` + status `active/provisioning/suspended/deleted`. Because every migration is `CREATE TABLE IF NOT EXISTS`, whichever lands first SILENTLY wins and the loser's router then references columns that don't exist (a boot/500 landmine that no `compileall`/`tsc` catches). Gate disposition that worked: identify the SUPERSET/canonical branch (8FB536's `v051_agent_pools_service.sql` created all three tables with the richer schema + the customer view + graceful `{configured:false}` endpoint), MERGE it to establish canonical tables on master, then REJECT the two colliding admin branches and file ONE reconciliation case (CASE-20260715-A91FC0) that rebuilds a single `admin_agent_pools.py` UNIONing both routers on top of the now-present schema (rewriting the outlier 8C3DCC to canonical column names). Never hand-weave two full-file rewrites of the same router in the gate. Author/orchestrator rule: when a feature needs a new shared migration or a new shared router file, dispatch that foundation as its own case that lands FIRST, then fan out consumers off the updated master — or coalesce the whole feature onto one branch. Reviewer tell: two `case-*` branches both `create mode 100644` the same path, or two `v0NN_*.sql` files creating the same table with differing column definitions → structural collision, pick the superset, reject the rest, file one reconciliation case.
- **Fanning out a multi-SCREEN app (Quote Machine: catalog CRUD + quotes admin + work orders + builder wizard + product matrix + public configure) into parallel case-branches off ONE base makes sibling slices independently (a) build a RIVAL copy of the same net-new router file, (b) each edit the SAME shared frontend files (`api/quotes.ts`, `types/quote.ts`, `App.tsx`, and the same stub page), and (c) call CREATE/support endpoints that no slice actually ships — every one is a merge-time collision or a runtime dead-end invisible to `tsc`; even when the shared SCHEMA already landed, the ROUTER + shared-FE files are a second shared foundation that must be single-sourced (2026-07-17):** review-gate 2026-07-17 processed a 6-case Quote Machine coalesced cluster (parent CASE-20260717-524B03) dispatched as 6 separate branches off `3d13f0a8`. Collisions found: CASE-20260717-F052B5 AND -20DAEB BOTH `create mode 100644 backend/app/routers/product_catalog.py` with DIFFERENT shapes (F052B5 = canonical CRUD spec w/ POST+brand_type filter+status='active'+`_is_grotap_user`; 20DAEB = its own GET/PATCH w/ richer row `pricing_display`/`is_quote_on_request`/`active`/`service_level` that ONLY its ProductMatrixPage consumes); CASE-20260717-DBA395's `quotes.py` and -0CBD74's `quotes_public.py` BOTH register `GET /quotes/public/{token}` (same `APIRouter(prefix="/quotes")`, divergent shapes — cents/int vs dollars/float+mode+model_options) → ambiguous double route; -842F35 and -DBA395 both rewrite the same `QuoteMachineQuotesPage.tsx` stub; -20DAEB's `App.tsx` HIJACKS the `/quote-machine` dashboard route (replaces `<QuoteMachineDashboardPage/>`); -842F35's `QuoteBuilderWizard.tsx` calls `POST /quotes`, `GET /quotes/model-options`, `POST /quotes/{id}/send-configure-link` that NO branch ships (DBA395 has only list/detail/patch/send). Disposition that worked: MERGE the cleanly-separable, schema-verified backends + their own-file pages ({F052B5 canonical catalog, 9A73C7 work_orders, DBA395 admin quotes+public viewer+v057}), union-resolving only `main.py` (all add `include_router` at one anchor) and `api/quotes.ts` (HEAD public accept/decline + DBA395 admin fns are ADDITIVE — keep both). REJECT/supersede the 3 colliding branches with FIX cases (842FX2 build the wizard's missing endpoints + rebase page; 0CBFX2 dedupe the public route to one owner + reapply configure FE; 20DFX2 drop rival router, rebuild ProductMatrixPage against canonical router + add a dedicated /quote-machine/products route, restore dashboard). Verify every backend router's columns against the LIVE schema first (`information_schema.columns` for product_catalog/quotes/quote_line_items/work_orders/agent_team_templates) — the F052B5 spec's column names (`setup_fee_cents`/`monthly_cents`/`brand_type` on product_catalog) were WRONG; the agent correctly used the real 14-col schema, so trust the code-vs-schema check over the spec prose. Author/orchestrator rule: a multi-screen app is TWO shared foundations (schema AND the shared router/api/types/App.tsx surface) — land both on one branch (or a foundation-first branch) before fanning out page slices; never dispatch sibling pages that each create-the-same-router or edit the same `api.ts`/`types.ts`/`App.tsx`, and never dispatch a page whose CREATE/support endpoints aren't already on master. Gate tell: two `case-*` branches both `create mode 100644` the same router path, or two routers sharing an `APIRouter(prefix=...)` + same sub-path, or a page calling `api.post(<path>)` whose route isn't on master → structural collision, merge the superset/canonical + own-file pages, FIX the rest. (Reuses the batch29 "land shared foundation first" + the "FE consumes endpoint not on master" lessons; new angle = the shared FE files + rival-router copies are the collision even after the schema exists.)
- **A verify-and-merge (gate-shaped) case going `done` does NOT mean the TARGET branch merged — the orchestrator merges the CASE'S OWN branch, so a D6848A-style "verification doc + hand off to gate" branch merges cleanly while the coordinated payload branch (case-F5CFF1, migration+code rename) stays unmerged and the whole chain silently loses its deliverable (2026-07-17):** CASE-20260717-D6848A (verify + merge gate for the v059 org_id→tenant_id rename) pushed only `docs/CASE-…-verification.md`, was orchestrator-merged and stamped done; `v059_quotes_tenant_id_rename.sql` and the 24 code renames were still absent from master until a human gate-keeper merged case-F5CFF1 by hand (f45b6fd6). Rules: (1) a gate-shaped case's deliverable is the MERGE OF THE NAMED TARGET BRANCH — its success check is `git log origin/master` containing the payload commits, not its own branch merging; (2) after any chain whose last case is verify/merge-shaped goes done, grep master for the chain's actual files before rolling up; (3) when decomposing, put the target-branch name in the merge case's body AND make its no-commit success path assert the target merge happened. (Extends the FXGATE no-commit-success-path + 66DC98 narration-commit lessons.)
- **A "dead code / never wired" diagnosis must be proven against the FULL wiring file — a `grep | head` that truncates before the registration line manufactures a false positive (2026-07-18, CORRECTED):** the routing-drift scheduler (0F7343) was flagged as "never registered in background_loops.py" and fix case CASE-20260718-7E9223 filed — but the wiring had existed since 424634f1; the reviewing session's `grep ... | head` cut off at line 39 and the import was at line 40. The dispatched agent correctly re-verified, found the wiring present, and shipped only the genuinely-missing piece (a registry-iterating `EXPECTED_LOOP_NAMES` test so any future unregistered loop fails CI). Rules: (1) before filing a "not wired/dead code" case, grep the whole file unfiltered and quote the line numbers checked; (2) agents receiving a fix case must re-verify the stated defect before implementing — a spec can be wrong, and the correct deliverable is what's actually missing; (3) periodic-loop deliverables still need the registration edit + registry test in the SAME branch, and acceptance = the boot log line on deploy, not pytest alone.
- **Two independently-dispatched branches that both add the SAME-named function to one file are a two-branch STRUCTURAL conflict even when each auto-merges cleanly — and a branch built on a filter/API contract that a SIBLING branch is simultaneously CORRECTING is dead-on-arrival (2026-07-19, review-gate SKIP of CASE-20260719-449C80 + EC0865):** both branches added `openreplay_provider.get_similar_sessions()` with incompatible signatures (449C80 `k=`, search-based via `_post_session_search` using the OLD `type=USER_EMAIL/USID` filter format; EC0865 `limit=`, GET `.../similar` CE endpoint) — merging both leaves Python using only the last def, silently killing the other + its tests. Worse, sibling CASE-20260719-444866 (merged same batch) had already proved that OLD filter format broken on CE v1.27 (Go service needs `name=userId`/`dataType`, `/v2/api` base, 1-based paging), so 449C80's calls would malform against the newly-fixed `_post_session_search`. Both also duplicated functionality already on master (pgvector `/sessions/{id}/similar` + explain-error).
