- Duplicate case cuts of the SAME endpoint (663AF1 + D290F7 both built GET /support/turn-credentials), **or a case filed for a defect that is ALREADY FIXED on master**: before building, `git log origin/master -- <the file your case names>` + grep the router for the route — if a twin case already landed, or the fix is already in, ship a superseded marker doc instead of a second implementation (two `@router.get` defs for one path merge silently and shadow each other). **A case filed AFTER the fix shipped is the dangerous shape: its body still describes the broken behaviour, so the agent "fixes" it by undoing the fix.** CASE-20260726-47DA45 (PIPEFB) was filed ~3h after b14ef604 shipped, decomposed into 5 subtasks, and its BBCEFC subtask reverted that live fix back into prod. Filing a case does not mean the bug is open — check master and the case's own clarification answers for "already applied / do not redo" before decomposing, and close as duplicate rather than re-deriving an approach the shipped fix explicitly rejected.
- Before decomposing an auto-filed infra incident, search open cases for the same failure signature (repo + error_type + host) and ATTACH — never file a twin parent; children across ALL active parents touching one file set serialize, never parallel; at the gate, twin branches of one fix = merge the best ONE, close the rest superseded (2026-07-09 storm E4AC51+1CCDBD; durable fix CASE-20260709-541957).
- **Client/server feature split across two agents (s1 receiver / s2 sender) MUST pin the exact wire contract, or the halves silently don't compose (2026-07-10):** the agent-06 pickup-trigger feature was built as two cases — sender 7875EC POSTs `{DEPLOY_TRIGGER_URL}/trigger-deploy` with body `{case_id, branch}`; receiver 187629 only handles `POST /trigger-pickup` and requires body `{dispatch_log_id, task_file, server_ip, session}`. Path AND payload diverged (and neither matched the s1 "dispatch.sh for the dispatch_log_id" contract), so a live trigger would fall through to the status handler → 200 (FALSE success) and dispatch.sh never runs. When two agents build the two ends of one HTTP call, ONE side must own an explicit contract (path + method + headers + exact JSON keys) and the other implements against it verbatim; the builder AND the gate must grep both files and diff sender's URL/payload against receiver's route + required-fields validation before merge. Bonus: don't `asyncio.create_task()` a fire-and-forget coroutine without retaining the task ref (GC can cancel it). Fix: CASE-20260710-0798B7.
### ⛔ THE #1 RECURRING DEFECT — parallel work on one shared file, schema, or surface

Merged 2026-07-25 from 13 separate lessons that all had this one root cause. Two or more branches cut from the same base, each independently authoring the same file / table / router / symbol, are UNMERGEABLE in bulk: git shows no conflict (disjoint files, different filenames, or a clean union at a shared anchor) while the COMBINATION is structurally or semantically broken — and `compileall` / `tsc` / the standard gates catch NONE of it.

**Author rule — before you write:**
- `git log --all --oneline -- <file>` plus `git show origin/case-<sibling>` for every file you are about to edit. If a sibling subtask of your parent already added the state/import/callback you need, branch FROM that sibling's branch, or report that you are blocked on it — never re-declare it. (Parent CASE-20260724-C4E7B2 subtasks 5262C2 / 71798E / F47522 each re-added the same `readerState` useState + `ReaderServiceState` import + `svc.start(ingest,onError,setReaderState)` 3rd arg to `scan.tsx`; two also rendered different status widgets into the same `phase === 'scanning'` slot. 71798E was REJECTED on an unresolvable same-anchor conflict → CASE-20260725-SCANFX. Adding a second widget to a slot a sibling already fills is a defect even when both branches compile.)
- Before adding a router/service file, `git grep` master for its `APIRouter(prefix="/x")` and its `include_router` line. If it exists, ADD your endpoint to it and reuse its guard — never `new file` a second copy, and never re-add the import/include a sibling already wired. (0F071D re-created `security.py` containing ONLY its turnstile endpoint after f1374e92 had landed blocklist/overview, AND re-added the duplicate import + `include_router` → double-registration → CASE-20260719-TURNFX.)
- Build ONLY your own deliverable. If your task depends on an API/endpoint/schema owned by ANOTHER unmerged case, STOP and report the missing dependency — never implement your own copy of it.

**Decomposer rule — subtasks that share anything are ONE task or a sequential chain:**
- Two subtasks must NEVER be expected to edit the same file, screen, module, router or table. Same-file work is ONE case, or a STACK (`awaiting_deps` on the predecessor) — never a parallel fan-out. A per-defect split of one rejected case across one shared file is the worst form: 4FBFIX → 021A62 / 033EAE / 145964 / 430215 plus a parallel full-rebuild D0BD81 produced five rival rewrites of one `scantap-scheduled-sync.ts`, each with a different cron schedule, discovery query and trigger mechanism (three of them inert — no consumer of `scantap/sync.*` events exists), all superseded by CASE-20260721-D0BDFX.
- Anything 2+ siblings CONSUME is a foundation subtask that lands FIRST, with every consumer declaring `depends_on` it. Four foundation kinds, all observed:
  - **Shared schema** — exactly ONE migration owns the tables. batch29 (agents.grotap.ai per-company agent service): 0AE58E / 8C3DCC / 8FB536 each created their own `v051_agent_pools*.sql`, two with the SAME filename, with DISAGREEING schemas (`agent_pool_teams` PK `team_id` + `capacity INT` vs PK `id` + `capacity JSONB`, different status CHECKs). Because every migration is `CREATE TABLE IF NOT EXISTS`, whichever lands first SILENTLY wins and the loser's router then references columns that don't exist — a boot/500 landmine no `compileall`/`tsc` catches. Merged the superset (8FB536), rejected the two colliding admin branches → CASE-20260715-A91FC0.
  - **Shared low-level helper** — divergent param NAMES alone make it unmergeable. Parent B492E0: 25FDC8 added a response-body param to `loadtest/metrics.py` `_format_event()`/`record()` as `response_body`, A56C6B as `body`; 25FDC8 merged first, then A56C6B collided on both rewritten functions AND the shared `ml.record(...)` call site → CASE-20260719-A56CF1.
  - **Shared router/module file** — 772F9E / A318A4 / DB9B58 (one RequestLogMiddleware split three ways) EACH authored the whole new `backend/app/middleware/request_log.py` — 137/132/144 lines, divergent bodies (batched-executemany vs per-request-execute vs bounded-buffer) → merged A318A4 alone, CASE-20260719-RQLBAT to fold in the rest.
  - **Shared frontend surface** — a multi-SCREEN app is TWO foundations: the schema AND the shared `api/*.ts` + `types/*.ts` + `App.tsx` + stub-page surface. Quote Machine (parent CASE-20260717-524B03, 6 branches off one base `3d13f0a8`) collided on a rival `product_catalog.py` with a different shape, two routers both registering `GET /quotes/public/{token}` under the same `APIRouter(prefix="/quotes")` with divergent payloads (cents/int vs dollars/float), two rewrites of one page stub, an `App.tsx` that HIJACKED the `/quote-machine` dashboard route, and a wizard calling `POST /quotes` + `GET /quotes/model-options` + `POST /quotes/{id}/send-configure-link` that NO branch shipped. Even when the schema already landed, the router + shared-FE files are a SECOND shared foundation.
- A BRAND-NEW feature must have ONE ratified schema + service-signature contract BEFORE parallel dispatch, or each agent invents its own. Free Stream: three cases (60EB18 / 6825BE / 1B3898) each created `migrations/apps/free-stream/v001_free_stream_core.sql` with mutually-incompatible column contracts, two each created `free_stream.py`, `free_stream_ingest.py`, and `FreeStreamPage.tsx` → CASE-20260714-FS0INT. Gate tell for which foundation is canonical: the one an ALREADY-MERGED consumer's call signatures match exactly (D62068's `ingest_event(source_system=,event_action=,external_ref=)` + `set/clear_entity_status_modifier` pinned 1B3898 over the thinner two).
- Merge dependency order is **schema → service → tap/consumer → frontend.** NEVER merge a tap/consumer before the module it imports exists on master: D62068 was merged first and master then imported a nonexistent `app.services.free_stream_ingest`. It only avoided bricking prod because the tap is a fire-and-forget `asyncio.create_task` with a bare `try/except` around a lazy import — so the ImportError was swallowed, every event silently dropped, the feature 100% inert and invisible to `compileall`/`tsc`.
- Prefer FEWER, larger subtasks. An over-split that collides costs far more than a subtask that is slightly too big.

**Gate disposition ladder — never hand-weave two full-file rewrites:**
1. Diff queued branches **against each other**, not just against master, for same-symbol redefinition, `new file mode` on one path, and shared-helper contract drift. 449C80 + EC0865 both added `openreplay_provider.get_similar_sessions()` with incompatible signatures (`k=` search-based on the OLD `type=USER_EMAIL` filter format vs `limit=` on the CE `/similar` endpoint) — Python keeps only the LAST def, silently killing the other plus its tests. Worse, sibling 444866 merged the same batch had already proved that old filter format broken on CE v1.27, so 449C80 was dead-on-arrival. A branch whose foundation another in-flight branch is rewriting must be rebased onto the winner or skipped, never merged as-authored → CASE-20260719-ORSMFX.
2. Reason about the **combined migration set**, which git cannot see. Grep every new `*.sql` in the batch for `CREATE TABLE` on the same table name. The runner applies files in sorted FILENAME order: `v044_glossary_schema.sql` (g) created the Object Glossary tables, then `v044_object_glossary.sql` (o) — bare `CREATE TABLE`, no `IF NOT EXISTS` — errored "relation already exists" and ABORTED the runner, boot-failing every deploy; and a third incompatible `v042_object_glossary.sql` sorts BEFORE both, creating the tables in the WRONG shape first and poisoning the canonical file's `IF NOT EXISTS` plus the already-merged seed script. Merged A9D6F7, filed CASE-20260713-C31FDF, superseded E535B8. Every schema migration uses `CREATE TABLE IF NOT EXISTS`.
3. If a branch "adds" a migration whose filename ALREADY exists on master, `diff <(git show origin/case-X:PATH) <(git show origin/master:PATH)`. Different body → DROP the branch copy (the applied canonical is authoritative; overwriting it is a checksum-mismatch BOOT ABORT via `migration_runner.run_migrations`) and re-verify the branch's CODE against `information_schema.columns`, never against its own migration. 44E02E and 53DD04 each re-added `v045_voice_calls.sql` with `id UUID PRIMARY KEY` when the live table's PK is `call_sid` with NO `id` column — 44E02E's `_CONTACT_SELECT` (`vc.id AS vc_id`) would 500 the live authed `GET /contact` and 53DD04's `_find_known_number` every outbound call → CASE-20260713-44E0FX + -53DDFX.
4. Before merging any branch that REWRITES a function, `git grep` master for the symbols its diff references. Master renamed/restructured them → the branch is STALE: file a rebase case, do NOT hand-weave. Three cases targeted `agents/team-run.sh` at once; master's 3508fd78 replaced the flat `_run_attempt 1/2/3` ladder with `_run_rung_with_retries <rung>`, stranding D41872 and A39F15 on now-deleted symbols → one combined CASE-20260712-B39D41. Where a branch's diff would REGRESS a value master has since changed, keep master's current value and take ONLY the net-new addition (`agents/config.sh` 4E28E5 vs the team2 `TEAM_MODEL_STRONG` deepseek-chat→grok-4.5 swap).
5. Then pick disposition by severity:
   - **Cleanly separable** (each branch owns its own files) → merge them, union-resolving only true append points: `main.py` `include_router` at one anchor, additive `api/*.ts` functions. (Quote Machine: merged F052B5 canonical catalog + 9A73C7 work_orders + DBA395 admin quotes/public viewer/v057, fix-cased the three colliders as 842FX2 / 0CBFX2 / 20DFX2.)
   - **2+ siblings `new file mode` the same path** → identify the superset/canonical, merge THAT ALONE, fix-case the rest. Never merge a partial "base" fragment first: doing that on 4FBFIX (021A62, which still carried DEFECT-3) left every sibling colliding against it AND each other.
   - **Semantic disagreement with a physical or live consequence** → merge NONE, reject ALL, file ONE consolidation that re-implements the union in sequence with every conflict explicitly resolved (citing the source branches so the agent cherry-picks the good code). Eight cases fanned onto `platform/mobile/scantap/services/CS463TcpReaderService.ts` rewrote `_encSetReaderConfig` three ways (0x01+KeepAlive@5000 vs 0x01+KeepAlive@10000 vs 0x00-no-reset-no-keepalive) and gave `C1G2SingulationControl`'s session byte two contradictory bit layouts (`session<<6` bits[7:6] spec-correct vs the old `0x04` bits[2:1]); the CORRECT answer — 0x00 AND a keepalive — existed on NO single branch. Picking wrong writes malformed LLRP frames to physical CS463 hardware and scanning silently breaks; `tsc` and the backend/orch/frontend gates don't even cover scantap mobile → CASE-20260724-LLRPCX. Treat `CS463TcpReaderService.ts`, `readerConfig.ts` and `services/llrp/src/*` as a SINGLE-OWNER touch surface.
6. A rebase/fix case must be scoped to REUSE what merged — drop A56C6B's whole `metrics.py` diff and keep only its `__main__.py` novel-status logic reading the merged `response_body` key — and must NAME what is already on master so the agent doesn't rebuild it. Salvage a stale branch's genuinely additive hunks (0F071D's `config.py` + `shared_state.py` were fine; only the router + wiring collided).
7. **RUN the existing test file for every source file in the diff — a branch that leaves a green suite RED is a REVERT, not a fix, and `compileall`/`tsc` are blind to it (2026-07-26, CASE-20260726-BBCEFC + -7AB496 under duplicate parent -47DA45):** BBCEFC re-implemented `team1_requeue_webhook` the exact way b14ef604 had explicitly rejected hours earlier — mint a `pending` dispatch row + commit a task file for `dispatch-poller.sh`, which runs on NO fleet host — reverting a LIVE fix: that pending row is precisely what hides the case from the assign loop's `NOT EXISTS pending/active`, and it also dropped `status='plan_approved'`, deadlocking the case by status too. It touched ONLY `pipeline.py` and left `backend/tests/test_team1_requeue.py` untouched and RED (8 of 12 failing, including `test_writes_no_dispatch_row` and `test_leaves_no_row_that_hides_the_case`) — it merged anyway and shipped to prod. Gate rule: for each `<file>` in the diff, locate its `tests/test_<file>.py` and RUN it; if the branch neither passes it nor updates it, reject. Corollary — **a branch that REWRITES an existing test file to match its own diff is asserting its implementation, not the requirement**: sibling 7AB496 landed 5 min after the hand-revert and rewrote that same suite (+388/-54) to assert the reverted behaviour, leaving master red a second time. Always diff the test file too and check WHICH behaviour the new assertions encode against master's shipped code; salvage only the implementation-independent classes (here `TestAssignLoopTeam1Case`) and drop the rest. GENERALISED 2026-07-26 (review-gate rg11, CASE-20260726-873C0F REJECTED → CASE-20260726-MANIVL) — **a test-only branch is not automatically safe to merge: when the case asks a test to "clarify expected behaviour", an agent may answer it by declaring master's CURRENT behaviour "intended by design", which turns a live defect into a green assertion that future fixes must delete.** The case named the requirement ("must not silently move a manual-only flow onto a schedule"); the 630-line suite instead asserted the opposite in 4 places with docstrings reading "by design — not a bug", and all 25 tests passed because they were derived FROM the implementation. The consumer contract settled it in the branch's favour of nothing: a sibling merged 20 min earlier (A6D184) had just documented `ingestion-worker/.../scantap-scheduled-sync.ts` as the SINGLE CONSUMER of the stored `settings.flows`, where an explicit `'manual'` is honoured as never-scheduled ("a real choice"), so the convergence write-back it blessed permanently erases that choice and starts polling. Author rule: a case's open behavioural question is answered by the REQUIREMENT text plus the consumer's documented contract — never by "this is what the code does today"; if the two disagree you have found the bug you were sent to test for, and the deliverable is a defect report, not an assertion. Gate rule: for a tests-only diff, do not stop at "N passed" — read the assertions of the scenario the case flagged as open, and reject if they codify behaviour that contradicts the requirement or another component's contract (100% pass rate is the expected symptom, not evidence).

**Reviewer tells — any ONE of these is a structural collision, not a feature:**
- Two `case-*` branches with the same `parent_case_id` and identical file lists in `git diff --stat`.
- Two branches both `create mode 100644` the same path.
- Two `v0NN_*.sql` files creating the same table with differing column definitions.
- Two routers sharing an `APIRouter(prefix=...)` plus the same sub-path (→ ambiguous double route).
- A page/component calling `api.post(<path>)` for a route that is not on master.
- A second `include_router(X)` for an already-wired router.
- A "wire X in main.py" diff that REPLACES rather than ADDS a registration: DB9B58 swapped `from app.middleware.request_id import RequestIdMiddleware` → `...request_log import RequestLogMiddleware` and dropped `add_middleware(RequestIdMiddleware)` entirely, silently deleting request_id correlation and the `X-Request-Id` echo. `compileall` is blind — both imports are valid.
- Verify every merged router's columns against the LIVE schema before trusting the spec: the Quote Machine F052B5 spec's column names (`setup_fee_cents`/`monthly_cents`/`brand_type`) were WRONG and the agent's code-vs-schema check was right. Trust the live schema over spec prose.

- **Filing a fix case (review gate or ad-hoc) = set the reporter in BOTH the `reporter` column AND `case_data.reporter` — the POLSUB policy guard only reads `case_data->>'reporter'` (2026-07-13):** batch5 filed P1 CASE-20260713-B84124 with only the column set to `review-gate`; the async `pipeline/policy.complete` callback then yanked it from `submitted` back to `awaiting_human` within ~2 min of EVERY resubmit (guard at `backend/app/routers/pipeline.py` ~371 saw no JSON key → not gate-exempt), stranding the P1 during a redeploy freeze with no hold row to signal it. Siblings filed WITH the JSON key (C31FDF, B39D41) were untouched. Recovery: `jsonb_set(case_data,'{reporter}','"review-gate"')` + flip to `submitted`. Durable fix (guard checks column OR JSON key): CASE-20260713-D6F50F.
- **An agent told to "MODIFY endpoint X" from a stale base often RE-CREATES the whole router file instead — merging it silently REGRESSES the version a prior case already landed (different impl + different response shape) and re-adds a duplicate `main.py` mount (2026-07-13):** CASE-20260713-A18BBF was scoped to add a `contact_card` to the existing `GET /products/presentation`, but it forked before CASE-20260713-7E36FE landed `backend/app/routers/products.py` on master and shipped a full-file re-creation: a different category source (`request.state.lead_category`, never set by middleware, vs master's `_extract_category` JWT decode) and a different `_AGENTS_OVERVIEW` structure, plus a duplicate `from app.routers.products import ...` + `include_router` in `main.py` (already present on master). `tsc`/`compileall` pass; the regression only shows by reading master's current file. Gate rule: when a branch's diff shows a NEW file (`new file mode`) for a path that ALREADY exists on master, treat it as a stale-base re-creation, NOT an add — reject and file a rebase case that MODIFIES master's current file (here: keep `_extract_category` + `_AGENTS_OVERVIEW`, add only `contact_card` from `TWILIO_FROM_NUMBER`/`VOICE_CONTACT_NAME`/`VOICE_CONTACT_TITLE` env vars; do not touch `main.py`). Fix filed CASE-20260713-A18BFX.
- **A "delete the duplicate migration" fix case can be pointed at the CANONICAL file: if the fix branch's base already carries the single good copy (the dup only ever existed on the rejected parent branch, never on this lineage), the agent deletes the real source-of-truth — removing the table's only creator, so fresh provisioning silently loses it (2026-07-13):** CASE-20260713-53DDFX was told "DELETE the re-added `v045_voice_calls.sql` (canonical already applied/live)" — correct advice for the parent 53DD04 branch that shipped a divergent copy, but this FIX branch forked from a base that already had the canonical `v045_voice_calls.sql` (byte-identical to master's applied file) and NO second copy. The agent `git rm`'d it anyway; merging as-is would delete master's sole `CREATE TABLE voice_calls` (existing prod DB unaffected since it's already applied, but any fresh control-plane provision loses the table). Gate rule before honoring a "delete the dup" instruction: confirm a dup actually EXISTS on this branch — `git cat-file -e base:PATH` and byte-compare vs `origin/master:PATH`; only delete when the branch's copy DIFFERS from the applied canonical. If the branch's file == master's applied file, there is no dup — keep it. Gate-fixed by restoring master's `v045_voice_calls.sql` in the merge; kept only the branch's `voice.py`/`tenant_auth.py`/test additions.
- **One case's branch can bundle a DIFFERENT case's work (scope bleed) — merge each case to its own scope, not the whole commit: co-merging duplicates the other case's files and collides when that case lands on its own (2026-07-13):** CASE-20260713-53DDFX (voice `/outbound`) was built as a single commit `feat(voice+products): ... (CASE-53DDFX + A18BFX)` that ALSO re-implemented A18BFX's `products.py contact_card` (a different, cleaner version than A18BFX's own branch). While reviewing, the orchestrator merged A18BFX's dedicated branch to master. Merging 53DDFX whole would have re-conflicted `products.py`/`test_products_presentation.py` and landed a competing contact_card impl. Gate rule: when a branch touches files outside its case's stated scope AND another queued/merged case owns those files, do a `--no-commit` merge and resolve the out-of-scope files to `HEAD` (`git checkout HEAD -- <path>`), keeping only the files the case actually owns; note the scope correction in the merge message.
- **Before rewriting a SHARED control-flow gate, check whether master already generalized the SAME flow via a peer commit that landed after your branch was cut — two parallel solutions to one gate collide as a STRUCTURAL merge conflict, and yours may be the redundant/inferior one (2026-07-13):** B9FFCA rewrote dispatch.sh's team-routing gate as `[[ "$DISPATCH_TEAM" != "team1" ]]`, but master commit 514db03d had already generalized the identical gate via `get_team_runtime "$DISPATCH_TEAM" == "agents/team-run.sh"` (config-driven, strictly better — it honors `TEAM_RUNTIME_SCRIPT`). Merge hit a structural conflict; the branch's routing half was fully superseded while only its per-team-cap half retained value. Gate rule: don't hand-weave — abort, and file a rebase case that keeps ONLY the branch's non-superseded delta re-applied onto master's current structure (here: drop the `!= team1` gate, re-apply just the `TEAM_DAILY_CAP` per-team cap onto master's `_team2_daily_cap_ok`/`get_team_runtime` code, + fix the companion test). Fix filed CASE-20260713-B9FFFX.
- **Within a coalesced cluster, two agents can pick DIVERGENT data models for the SAME feature (a new dedicated table vs. columns bolted onto an existing table) — merge the branch that carries the actual consumer/worker, reject the branch whose table nothing reads, and confirm any dark-launch enable command UPDATEs the exact table/column the worker gates on (2026-07-15):** review-gate 2026-07-15 batch7, Free Stream Gmail sync (FSA-E) split into CASE-20260714-6541F8 (the worker `gmail_sync.py`) and CASE-20260714-41B930 (setup hold + dark-launch docs). 6541F8 gated each account on `loop_engine.connected_accounts.gmail_sync_enabled` (columns added by `v006_gmail_sync_cursor.sql`, reusing loop-engine's existing OAuth tokens); 41B930 instead created a brand-new `free_stream.stream_gmail_accounts` table with its own `sync_enabled`, and its operator hold said `UPDATE free_stream.stream_gmail_accounts SET sync_enabled=true` — which the worker NEVER reads, so flipping it does nothing and the feature can never be un-darked via the documented path (orphan table + inert dark-launch). `compileall`/`tsc` are blind (the table exists, the SQL is valid — it's just the wrong table). Gate rule: for a dark-launch/feature-flag branch, grep the actual consumer for the flag it reads (`SELECT ...
