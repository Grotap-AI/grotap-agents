# Lessons — State machines & jobs

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** your diff touches a status transition, webhook/event handler, idempotency guard, background loop, or a two-sided protocol.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,

- **Side-effects on a state transition must fire off the rows your UPDATE actually flipped (RETURNING), not the pre-UPDATE candidate SELECT (2026-07-10):** 0FB344 added Slack "case unblocked" notifications by looping over the pre-UPDATE `release`/`toRelease` candidate list in `run_dep_release_for_org` + `on_child_done`. But the Inngest dep-check (`dependencyCheck.ts`, cron every 5 min AND `pipeline/case.status.changed` event) races those backend paths on the SAME `awaiting_deps→plan_approved` transition — both can SELECT the case as a candidate before either commits, so both notify → duplicate ops-channel spam. When N independent paths can perform the same idempotent transition, do the side-effect off `UPDATE ... WHERE status='<old>' ... RETURNING case_id` and act only on the returned rows — only the one path whose UPDATE actually flipped the row wins, giving exactly-once even under full concurrency. Fix: CASE-20260710-FB3F01.
- **A webhook/event-handler idempotency claim keyed on `WHERE <col> IS NULL` (or `<col> = <expected>`) is DEAD if an EARLIER step in the same flow already populated `<col>` — the guard never matches, so the "first event" branch (mark paid / trigger fulfilment) NEVER runs. Key the idempotency claim on the STATE TRANSITION you are guarding, not on a side-channel column that another step writes (2026-07-17):** review-gate 2026-07-17 merged CASE-20260717-845475 (QM-B quote engine backend) WITH fix case CASE-20260717-QMBFIX. The `accept_public_quote()` endpoint creates the Stripe checkout session and immediately persists `UPDATE quotes SET stripe_checkout_session_id=session.id`. The billing webhook's `kind=="quote"` branch then tried to claim-and-fulfil with `UPDATE quotes SET status='paid', stripe_checkout_session_id=$1 WHERE quote_id=$2 AND stripe_checkout_session_id IS NULL RETURNING quote_id` — but accept already set that column, so `WHERE ... IS NULL` matches ZERO rows, `updated` is None, the handler logs "duplicate — skipped", and `fulfil()` (work_order + pipeline case + human_holds + provisioning) is NEVER called for any paid quote. `compileall` is BLIND (valid SQL); only end-to-end (accept → simulated checkout.session.completed) exposes it, and the branch's own unittest stubbed a quote with a NULL session id — i.e. it tested a state the real flow never produces. Merged anyway (app internal/dark: QM-C/QM-D UIs unshipped → no live trigger; no bad data; ~3-line fix). Correct pattern: claim on the transition — `WHERE quote_id=$2::uuid AND status <> 'paid' RETURNING quote_id` — first event flips accepted→paid + fires fulfil, duplicates find status already 'paid' and no-op; keep a second idempotency backstop in fulfil() itself (it already guarded on work_order existence). Author rule: an idempotency guard must test the very state you flip (status), never a column a prior step in the same happy path also writes. Gate rule: for any webhook/retry-safe handler, trace whether the column in its `WHERE ... IS NULL`/`= expected` claim is written EARLIER in the same flow — if so the guard is dead and the fulfilment branch never runs; and distrust a unittest that seeds a state (NULL session id) the production path can't reach.
- **A fallback/default helper's sentinel value is for PERSISTING a safe default, NOT for gating a hard rejection — coupling `if result == FALLBACK: raise HTTPException(422)` to a derive-a-default helper turns valid inputs into errors and is scope creep the spec never asked for (2026-07-18):** review-gate 2026-07-18 merged CASE-20260718-CD6506 (case_title.derive_case_title helper + stamp every INSERT INTO pipeline_cases) WITH fix case CASE-20260718-CD6FIX. The helper's raw_input branch correctly SKIPS markdown headers/horizontal-rules/blanks, and the spec explicitly wanted the final fallback string ("Untitled case — needs description") PERSISTED ("empty input -> fallback"). But `submit_case` in `backend/app/routers/pipeline.py` added, unrequested, `if case_data["title"] == FALLBACK_TITLE: raise HTTPException(422)` — so a legitimate submission whose raw_input is header-only (e.g. `raw_input="## Fix login bug"`) derives FALLBACK and gets 422 on the platform's PRIMARY case-intake endpoint (POST /pipeline/cases), rejecting a previously-valid filing. The branch's own test `test_only_headers_and_blanks_falls_through` proves header-only input falls through to FALLBACK; `compileall`/`tsc` are blind (valid code, contract change only). Merged (no data corruption, no auth break, feature otherwise correct + 42 tests). Author rule: a "derive a default / guaranteed non-empty value" helper's job is to always RETURN something safe to store — never wire its sentinel to a raise; if a real emptiness guard is wanted, gate it on the raw INPUT being empty/whitespace (`not body.raw_input.strip()`), not on the derived-title sentinel (which also fires for header-only prose). Gate rule: when a title/slug/default-derivation change adds a rejection path, check whether the sentinel can be reached by legitimate input the spec intended to ACCEPT — if so it's a regression, FIX (merge only if it doesn't corrupt data / break auth).
- **A status-transition that a dedup/idempotency SELECT doesn't include re-fires every cycle — widen the open-row lookup to cover the new terminal-ish status (2026-07-19, review-gate batch24, same CASE-20260719-703B04):** the branch flipped an abuse_flags row to `status='escalated'`, but the once-per-15-min dedup guard `_SELECT_OPEN_FLAG` matches only `WHERE status='open'`. So the next run no longer finds the escalated row, INSERTs a fresh `open` one, and re-escalates forever (non-unique index → row + side-effect bloat). Rule: when you add a new status value that a job sets, grep every dedup/"find existing open row" SELECT in that service and broaden it (`status IN ('open','escalated')`) so the invariant "at most one row per subject" still holds; a new status the guard can't see breaks the guard.
- **When two agents build the two sides of a protocol/state-machine (client + mock/server), verify the state machines INTERLOCK: every message one side AWAITS a response for, the other side must PRODUCE (2026-07-22, review-gate, CASE-20260722-CFC998 reader MERGED, CASE-20260722-3C2ACA mock REJECTED → 3C2F01):** the LLRP reader begins init with DELETE_ROSPEC(21) and blocks awaiting DELETE_ROSPEC_RESPONSE(31); the mock acked SET_READER_CONFIG/ADD/ENABLE/START but NOT DELETE_ROSPEC, so the reader never reached `running` and emitted zero tags — the mock could not drive the very reader it exists to test. Each side compiled and matched its own case spec; the specs were written inconsistently (mock's ack list omitted DELETE). Author rule: a mock/server case for a client state machine must enumerate acks from the CLIENT's actual sequence, not a hand-listed subset. Reviewer tell: diff the client's awaited-response set against the server's produced-response set; any client `await_*` phase with no matching server reply is a stall defect.
- **A hardcoded cadence must never win over an inherited/user-chosen schedule setting — pinning a job to a constant on the "inherit" branch silently overrides `manual` and puts a flow on a schedule the tenant switched OFF; and before coding any "these two ran at different intervals" fix, prove which code path actually produces the divergence (2026-07-26, parent CASE-20260726-BE134F subtask CASE-20260726-8F98E7, REJECTED → CASE-20260726-SYNCIV):** to align `inventory_detail` (hourly) with `committed_qtys` (15m) the branch forced both to a new `STOCK_SYNC_INTERVAL = "15m"` in `resolve_flows` (`backend/app/services/scantap_sync.py`) + its `resolveFlows` mirror (`ingestion-worker/src/functions/scantap-scheduled-sync.ts`), but ONLY when the flow's interval was inherited. Two failures, both provable by calling the function: (1) on master an inherited flow takes `settings.sync_interval_all`, the SAME value for every flow, so the inherit path can never diverge — the reported skew lives only in EXPLICIT `settings.flows[<flow>].interval` values, the one path left untouched, so the fix fixed nothing; (2) with every flow inherited (exactly what the Sync Manager's `apply_to_all` writes — `if body.apply_to_all: entry["interval"] = None`), `sync_interval_all='manual'` yielded `interval_minutes=None` for four flows but **15** for the two pinned ones → "Manual only" hitting the tenant's ERP 96x/day, the very incident the scheduler file's own header comment already documented; `'5m'` forced them SLOWER than asked and created fresh skew against the other four. Compounding tell: `resolve_flows` returned `inherited: True` alongside the overridden interval, and the UI renders that flag as `Same as all (<interval_all>)` (`ScanTapSyncManagerPage.tsx` L459/L473) — so the screen reported "Same as all (Manual only)" for a flow running every 15 minutes. Author rules: implement "X and Y always share an interval" as MIRRORING at the WRITE path (setting either writes both), so reads stay special-case-free, `inherited` stays truthful and the scheduler needs no per-flow logic; never return a resolved value that contradicts the flag describing where it came from; and treat an inherited `manual`/off as sacred. Reviewer tells: for any "align/consolidate the schedules" branch, construct the REPORTED state and call the resolver — if it still returns the two old numbers, the branch is a no-op on the actual bug; then sweep the new constant across every value of the setting it bypasses (`manual`, the fastest, the slowest), because the existing tests pass when they happen to exercise other flows (all 20 in `tests/services/test_scantap_sync_flows.py` passed here, using only `locations`/`inventory_items` as the inherit examples).

- **"The handler already tolerates this" is a CLAIM about an error path — verify it by EXECUTING the classifier against the REAL error text the vendor/CLI actually emits, because a proprietary mode may never produce the string you grep for and a CLI's multi-line retry+summary stderr defeats any "no other lines" test (2026-07-26, review-gate rg14, CASE-20260726-98C24D → CASE-20260726-PRUN37; the caller-guard half is CASE-20260726-AB3E1B):** `wasabi_prune` in `scripts/backup/lib.sh` classifies rclone failures by `lock_lines=$(grep -i "object.lock\|object protected\|ObjectLock")` vs `other_lines=$(grep -iv <same>)`, then returns 1 `if [ -n "$other_lines" ] || [ -z "$lock_lines" ]`. A branch documented this as "detects the lock error, logs a warning, and continues without failing" and used that to justify leaving a zero-margin prune horizon. Both halves are false, and BOTH were provable in minutes: (1) `platform-backups` uses Wasabi's **proprietary bucket Compliance**, not S3 Object Lock (`get_object_lock_configuration` → `ObjectLockConfigurationNotFoundError`, while `GET /<bucket>?compliance` → `Status=enabled RetentionDays=30`), and a delete inside retention is denied with plain **403 AccessDenied** — matching none of the three greps, so `lock_lines` is EMPTY and the function returns 1; (2) even with lock-worded text, a real `rclone delete` writes MULTI-LINE stderr — executed on a permission-denied local remote it produced 8 lines (a `NOTICE` config line, 3× `ERROR : <file>: Couldn't delete:`, 3× `ERROR : Attempt n/3 failed with 2 errors`, and a trailing `Failed to delete with 2 errors: last error was:`) — so `other_lines` is ALWAYS non-empty and the graceful `return 0` path is effectively **unreachable**. Under `set -euo pipefail` with bare call sites that non-zero aborts the caller AFTER the dump but BEFORE `heartbeat`/`notify`, i.e. it converts a successful backup into a watchdog "MISSED RUN" false alarm. Reviewer technique to copy: lift the classifier verbatim into a scratch script, feed it (a) the vendor's actual error text and (b) the CLI's real stderr captured from a deliberately-failed run, and print which branch it takes — this turns "looks fine" into an audit fact in one command, and it is the same discipline as executing a route matcher rather than reading it. Author rules: classify on the signal the vendor really sends (403/AccessDenied here), ignore the CLI's own `Attempt n/m` / `Failed to … with N errors` summary lines when deciding whether an error is "other", and count distinct OBJECT KEYS not matched LINES (`wc -l` over 3 retries reports one object as three). Corollary: never let a *retention/horizon* decision rest on a downstream handler being forgiving — set the margin so the error never happens (`RetentionTime` here is exactly `PUT + RetentionDays` to the second, so an `rclone --min-age 30d` against a 30-day lock is a ZERO-second margin gated only on clock skew).
