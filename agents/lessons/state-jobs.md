> actually shipped. **Read this file when:** your diff touches a status transition, webhook/event handler, idempotency guard, background loop, or a two-sided protocol.

- **Side-effects on a state transition must fire off the rows your UPDATE actually flipped (RETURNING), not the pre-UPDATE candidate SELECT (2026-07-10):** 0FB344 added Slack "case unblocked" notifications by looping over the pre-UPDATE `release`/`toRelease` candidate list in `run_dep_release_for_org` + `on_child_done`. But the Inngest dep-check (`dependencyCheck.ts`, cron every 5 min AND `pipeline/case.status.changed` event) races those backend paths on the SAME `awaiting_deps→plan_approved` transition — both can SELECT the case as a candidate before either commits, so both notify → duplicate ops-channel spam. When N independent paths can perform the same idempotent transition, do the side-effect off `UPDATE ... WHERE status='<old>' ... RETURNING case_id` and act only on the returned rows — only the one path whose UPDATE actually flipped the row wins, giving exactly-once even under full concurrency. Fix: CASE-20260710-FB3F01.
- **A webhook/event-handler idempotency claim keyed on `WHERE <col> IS NULL` (or `<col> = <expected>`) is DEAD if an EARLIER step in the same flow already populated `<col>` — the guard never matches, so the "first event" branch (mark paid / trigger fulfilment) NEVER runs. Key the idempotency claim on the STATE TRANSITION you are guarding, not on a side-channel column that another step writes (2026-07-17):** review-gate 2026-07-17 merged CASE-20260717-845475 (QM-B quote engine backend) WITH fix case CASE-20260717-QMBFIX. The `accept_public_quote()` endpoint creates the Stripe checkout session and immediately persists `UPDATE quotes SET stripe_checkout_session_id=session.id`. The billing webhook's `kind=="quote"` branch then tried to claim-and-fulfil with `UPDATE quotes SET status='paid', stripe_checkout_session_id=$1 WHERE quote_id=$2 AND stripe_checkout_session_id IS NULL RETURNING quote_id` — but accept already set that column, so `WHERE ... IS NULL` matches ZERO rows, `updated` is None, the handler logs "duplicate — skipped", and `fulfil()` (work_order + pipeline case + human_holds + provisioning) is NEVER called for any paid quote. `compileall` is BLIND (valid SQL); only end-to-end (accept → simulated checkout.session.completed) exposes it, and the branch's own unittest stubbed a quote with a NULL session id — i.e. it tested a state the real flow never produces. Merged anyway (app internal/dark: QM-C/QM-D UIs unshipped → no live trigger; no bad data; ~3-line fix). Correct pattern: claim on the transition — `WHERE quote_id=$2::uuid AND status <> 'paid' RETURNING quote_id` — first event flips accepted→paid + fires fulfil, duplicates find status already 'paid' and no-op; keep a second idempotency backstop in fulfil() itself (it already guarded on work_order existence). Author rule: an idempotency guard must test the very state you flip (status), never a column a prior step in the same happy path also writes. Gate rule: for any webhook/retry-safe handler, trace whether the column in its `WHERE ... IS NULL`/`= expected` claim is written EARLIER in the same flow — if so the guard is dead and the fulfilment branch never runs; and distrust a unittest that seeds a state (NULL session id) the production path can't reach.
- **A fallback/default helper's sentinel value is for PERSISTING a safe default, NOT for gating a hard rejection — coupling `if result == FALLBACK: raise HTTPException(422)` to a derive-a-default helper turns valid inputs into errors and is scope creep the spec never asked for (2026-07-18):** review-gate 2026-07-18 merged CASE-20260718-CD6506 (case_title.derive_case_title helper + stamp every INSERT INTO pipeline_cases) WITH fix case CASE-20260718-CD6FIX. The helper's raw_input branch correctly SKIPS markdown headers/horizontal-rules/blanks, and the spec explicitly wanted the final fallback string ("Untitled case — needs description") PERSISTED ("empty input -> fallback"). But `submit_case` in `backend/app/routers/pipeline.py` added, unrequested, `if case_data["title"] == FALLBACK_TITLE: raise HTTPException(422)` — so a legitimate submission whose raw_input is header-only (e.g. `raw_input="## Fix login bug"`) derives FALLBACK and gets 422 on the platform's PRIMARY case-intake endpoint (POST /pipeline/cases), rejecting a previously-valid filing. The branch's own test `test_only_headers_and_blanks_falls_through` proves header-only input falls through to FALLBACK; `compileall`/`tsc` are blind (valid code, contract change only). Merged (no data corruption, no auth break, feature otherwise correct + 42 tests). Author rule: a "derive a default / guaranteed non-empty value" helper's job is to always RETURN something safe to store — never wire its sentinel to a raise; if a real emptiness guard is wanted, gate it on the raw INPUT being empty/whitespace (`not body.raw_input.strip()`), not on the derived-title sentinel (which also fires for header-only prose). Gate rule: when a title/slug/default-derivation change adds a rejection path, check whether the sentinel can be reached by legitimate input the spec intended to ACCEPT — if so it's a regression, FIX (merge only if it doesn't corrupt data / break auth).
- **A status-transition that a dedup/idempotency SELECT doesn't include re-fires every cycle — widen the open-row lookup to cover the new terminal-ish status (2026-07-19, review-gate batch24, same CASE-20260719-703B04):** the branch flipped an abuse_flags row to `status='escalated'`, but the once-per-15-min dedup guard `_SELECT_OPEN_FLAG` matches only `WHERE status='open'`. So the next run no longer finds the escalated row, INSERTs a fresh `open` one, and re-escalates forever (non-unique index → row + side-effect bloat). Rule: when you add a new status value that a job sets, grep every dedup/"find existing open row" SELECT in that service and broaden it (`status IN ('open','escalated')`) so the invariant "at most one row per subject" still holds; a new status the guard can't see breaks the guard. **RECURRENCE 2026-08-10 (review-gate, CASE-20260809-A76861 REJECTED → CASE-20260810-CANFIX) — the mirror image: not a guard that can't SEE a status, but a HANDLER subscribed to only ONE of the producer's statuses.** The canary auto-recovery branch installed a credential pause that extends `pause_expiry` to NOW()+24h when it arms a probe, and cleared that pause only from `_check_canary_done()` (`if body.status == "done"`) plus the `failed_infra` branch. But `agent_progress_callback`'s own `valid` set lists 19 statuses, and the NORMAL successful outcome of an agent build in this pipeline is `change_review` (or `awaiting_human`) — never `done`. So a healthy credential whose probe SUCCEEDED kept dispatch blocked for its tenant for 24h, where the pre-branch behaviour self-expired in ≤60min: the recovery path was unreachable on the common path, turning a bounded pause into a long outage. Rule: when you hook a handler to a completion/progress webhook, read the handler's OWN validation set (`valid = {...}`) and enumerate every terminal status it accepts, then decide explicitly for each one — `== "done"` is an assumption about which outcome is normal, and in a build pipeline it is the WRONG one. Same for the inverse (a block/pause you install): whatever installs a bound must have a release path reachable from EVERY way the work can end, including the ways that never post a webhook at all — give it a stale-timeout reclaim, and never let the un-armed window (24h) exceed the bound it replaced (60min). **Third defect in the SAME branch, found by the second reviewer and independent of the status-set bug — it survives fixing it (CASE-20260810-CANFIX DEFECT 6): a table KEYED by one column but ENFORCED through a denormalised NON-UNIQUE one turns every `fetchrow`/single-row UPDATE into a silent partial write.** `dispatch_pause` is PK'd on `credential_id`, but the assign filter blocks on `tenant_id`, and `resolve_credential_ids()` returns one row PER PROVIDER — so the ordinary tenant with an Anthropic *and* an OpenRouter BYO key has TWO pause rows under one `tenant_id`. The arming loop hands BOTH the same probe case (arming writes no dispatch row, so the "oldest plan_approved with no pending/active dispatch" query returns the same case on the second pass), but the clear path is `get_credential_for_canary_case()` -> `pool.fetchrow(... WHERE canary_case_id = $1)` — ONE row. The survivor keeps `canary_case_id` set with the 24h expiry, so every other case for that tenant stays blocked, and it can never re-arm because `get_expired_pauses_for_arm` requires `canary_case_id IS NULL`. A *successful* recovery therefore still costs the full 24h. Rule: whenever the column you FILTER on is not the column you KEY on, every operation whose intent is "all rows for this subject" must be set-based — `fetchrow` and single-row UPDATE are the bug, and they pass every single-credential test, which is why fan-out cardinality (1 credential vs 2) belongs in the fixture, not the happy path. Reviewer tell that settled it in one command: seed scratch tables with the N>1 state and EXECUTE the real filter SQL against Postgres (`BEGIN; CREATE TEMP TABLE …; ROLLBACK;`) rather than reasoning about the NOT EXISTS — it showed directly that after clearing one row the second case was still blocked and zero rows remained re-armable. **RECURRENCE 2026-08-14 (review-gate, CASE-20260814-E39013/402184 MERGED + fix case CASE-20260814-B6C339) — the release path existed but a WHERE clause carved rows out of it.** `print_cloud_computer_sweep._sweep_computers()` pass 1b sets `print_cloud.printers.state='offline'` for every printer under an offline computer, but the ONLY writer that sets it back — `report_printers()` in `backend/app/routers/print_cloud_agent.py` — ends with `WHERE NOT print_cloud.printers.managed`, so hand-registered network printers (`managed=TRUE`, the TCP label printers Print Cloud exists for) can be swept offline and never restored, even after their host resumes heartbeating; the UI ANDs the two states (`online: p.state==='online' && p.computer_state==='online'`) so they show "(offline)" forever and stop being auto-selected as default. Rule: before a job writes a state column, find the writer that undoes it and read its WHERE clause — a restore path that filters on ownership/source (`managed`, `is_manual`, `created_by`) does not cover the rows the sweeper does, and "there is a recovery path" is only true for the subset that path selects. If a sweeper cannot restore a row, it must not modify it (`AND NOT managed`) — one-way writes belong only on columns the same subsystem owns end to end. Reviewer tell: for any new UPDATE of a state/status column, grep every `SET <col> =` for the inverse value and diff the two WHERE clauses — asymmetry there is the bug, and it is invisible to compileall/tsc and to tests that only exercise agent-discovered rows. **RECURRENCE 2026-08-31 (review-gate, CASE-20260831-F1C1C9 NOT MERGED → CASE-20260831-RGF1C1) — same sweep, same restore path, and the restore was narrowed by the VALUE it writes rather than by a WHERE clause, so the WHERE-diff tell above misses it.** To add per-printer TCP reachability the branch made the restore conditional on an OPTIONAL field: `state = 'online'` became `state = COALESCE($6::text, print_cloud.printers.state)`, where `$6` is a new optional `PrinterIn.state` the agent stamps only on printers carrying `capabilities.host_address`. The stated rule — "a missing observation means unchanged" — is right for tcp printers and catastrophic for every other printer, because `report_printers()` is still the ONLY writer that ever sets a discovered printer back to 'online'. Net effect: any USB/local queue swept offline by the ordinary overnight-shutdown path is reported again with no `state`, COALESCE keeps 'offline', and it is stranded FOREVER — gone from every picker with no way back short of editing the DB. Generalized rule: a restore path is disabled just as effectively by making its WRITTEN VALUE conditional as by filtering its rows — when you convert an unconditional `SET <col> = <recovered>` into a COALESCE/CASE on a new optional input, enumerate which subjects will supply that input and which will not, and confirm the have-nots still recover. Corollary for the producer side: if omission means "unchanged", the sender must stamp a value for every subject it CAN reason about and omit only where it genuinely has no opinion — here the agent should stamp 'online' for non-tcp printers (enumerating the queue on a live host is exactly the evidence the old unconditional 'online' rested on) and omit only for tcp printers its per-cycle probe budget could not reach. Reviewer tell that catches both shapes: for the inverse-value writer, ask not only "which rows does it still match" but "which rows still receive the recovered VALUE" — and note the branch's own unit test named the trap (`test_missing_state_is_passed_as_none_so_stored_state_is_unchanged` used a FILE:-port "PDF Writer", i.e. a non-tcp printer, as its example of a legitimately stateless report); a test that asserts the stranding as intended behaviour is a spec misread, not coverage.
- **When two agents build the two sides of a protocol/state-machine (client + mock/server), verify the state machines INTERLOCK: every message one side AWAITS a response for, the other side must PRODUCE (2026-07-22, review-gate, CASE-20260722-CFC998 reader MERGED, CASE-20260722-3C2ACA mock REJECTED → 3C2F01):** the LLRP reader begins init with DELETE_ROSPEC(21) and blocks awaiting DELETE_ROSPEC_RESPONSE(31); the mock acked SET_READER_CONFIG/ADD/ENABLE/START but NOT DELETE_ROSPEC, so the reader never reached `running` and emitted zero tags — the mock could not drive the very reader it exists to test. Each side compiled and matched its own case spec; the specs were written inconsistently (mock's ack list omitted DELETE). Author rule: a mock/server case for a client state machine must enumerate acks from the CLIENT's actual sequence, not a hand-listed subset. Reviewer tell: diff the client's awaited-response set against the server's produced-response set; any client `await_*` phase with no matching server reply is a stall defect.
- **A hardcoded cadence must never win over an inherited/user-chosen schedule setting — pinning a job to a constant on the "inherit" branch silently overrides `manual` and puts a flow on a schedule the tenant switched OFF; and before coding any "these two ran at different intervals" fix, prove which code path actually produces the divergence (2026-07-26, parent CASE-20260726-BE134F subtask CASE-20260726-8F98E7, REJECTED → CASE-20260726-SYNCIV):** to align `inventory_detail` (hourly) with `committed_qtys` (15m) the branch forced both to a new `STOCK_SYNC_INTERVAL = "15m"` in `resolve_flows` (`backend/app/services/scantap_sync.py`) + its `resolveFlows` mirror (`ingestion-worker/src/functions/scantap-scheduled-sync.ts`), but ONLY when the flow's interval was inherited. Two failures, both provable by calling the function: (1) on master an inherited flow takes `settings.sync_interval_all`, the SAME value for every flow, so the inherit path can never diverge — the reported skew lives only in EXPLICIT `settings.flows[<flow>].interval` values, the one path left untouched, so the fix fixed nothing; (2) with every flow inherited (exactly what the Sync Manager's `apply_to_all` writes — `if body.apply_to_all: entry["interval"] = None`), `sync_interval_all='manual'` yielded `interval_minutes=None` for four flows but **15** for the two pinned ones → "Manual only" hitting the tenant's ERP 96x/day, the very incident the scheduler file's own header comment already documented; `'5m'` forced them SLOWER than asked and created fresh skew against the other four. Compounding tell: `resolve_flows` returned `inherited: True` alongside the overridden interval, and the UI renders that flag as `Same as all (<interval_all>)` (`ScanTapSyncManagerPage.tsx` L459/L473) — so the screen reported "Same as all (Manual only)" for a flow running every 15 minutes. Author rules: implement "X and Y always share an interval" as MIRRORING at the WRITE path (setting either writes both), so reads stay special-case-free, `inherited` stays truthful and the scheduler needs no per-flow logic; never return a resolved value that contradicts the flag describing where it came from; and treat an inherited `manual`/off as sacred. Reviewer tells: for any "align/consolidate the schedules" branch, construct the REPORTED state and call the resolver — if it still returns the two old numbers, the branch is a no-op on the actual bug; then sweep the new constant across every value of the setting it bypasses (`manual`, the fastest, the slowest), because the existing tests pass when they happen to exercise other flows (all 20 in `tests/services/test_scantap_sync_flows.py` passed here, using only `locations`/`inventory_items` as the inherit examples).

- **"The handler already tolerates this" is a CLAIM about an error path — verify it by EXECUTING the classifier against the REAL error text the vendor/CLI actually emits, because a proprietary mode may never produce the string you grep for and a CLI's multi-line retry+summary stderr defeats any "no other lines" test (2026-07-26, review-gate rg14, CASE-20260726-98C24D → CASE-20260726-PRUN37; the caller-guard half is CASE-20260726-AB3E1B):** `wasabi_prune` in `scripts/backup/lib.sh` classifies rclone failures by `lock_lines=$(grep -i "object.lock\|object protected\|ObjectLock")` vs `other_lines=$(grep -iv <same>)`, then returns 1 `if [ -n "$other_lines" ] || [ -z "$lock_lines" ]`. A branch documented this as "detects the lock error, logs a warning, and continues without failing" and used that to justify leaving a zero-margin prune horizon. Both halves are false, and BOTH were provable in minutes: (1) `platform-backups` uses Wasabi's **proprietary bucket Compliance**, not S3 Object Lock (`get_object_lock_configuration` → `ObjectLockConfigurationNotFoundError`, while `GET /<bucket>?compliance` → `Status=enabled RetentionDays=30`), and a delete inside retention is denied with plain **403 AccessDenied** — matching none of the three greps, so `lock_lines` is EMPTY and the function returns 1; (2) even with lock-worded text, a real `rclone delete` writes MULTI-LINE stderr — executed on a permission-denied local remote it produced 8 lines (a `NOTICE` config line, 3× `ERROR : <file>: Couldn't delete:`, 3× `ERROR : Attempt n/3 failed with 2 errors`, and a trailing `Failed to delete with 2 errors: last error was:`) — so `other_lines` is ALWAYS non-empty and the graceful `return 0` path is effectively **unreachable**. Under `set -euo pipefail` with bare call sites that non-zero aborts the caller AFTER the dump but BEFORE `heartbeat`/`notify`, i.e. it converts a successful backup into a watchdog "MISSED RUN" false alarm. Reviewer technique to copy: lift the classifier verbatim into a scratch script, feed it (a) the vendor's actual error text and (b) the CLI's real stderr captured from a deliberately-failed run, and print which branch it takes — this turns "looks fine" into an audit fact in one command, and it is the same discipline as executing a route matcher rather than reading it. Author rules: classify on the signal the vendor really sends (403/AccessDenied here), ignore the CLI's own `Attempt n/m` / `Failed to … with N errors` summary lines when deciding whether an error is "other", and count distinct OBJECT KEYS not matched LINES (`wc -l` over 3 retries reports one object as three). Corollary: never let a *retention/horizon* decision rest on a downstream handler being forgiving — set the margin so the error never happens (`RetentionTime` here is exactly `PUT + RetentionDays` to the second, so an `rclone --min-age 30d` against a 30-day lock is a ZERO-second margin gated only on clock skew).

- **A READ-ONLY diagnostic added to a sweep must be exception-guarded AND placed AFTER the work it observes — an unguarded observer at the TOP of the function aborts the sweep it was added to watch, and adding any DB call changes the function's observable fetch SEQUENCE, which turns a green mocked suite RED (2026-07-29, review-gate, CASE-20260727-DFA001 REJECTED → CASE-20260729-DPDLK1):** the case asked for deadlock VISIBILITY, and the query itself was correct — I ran it read-only against prod and it returns the one real edge (`CASE-20260726-SYNCIV` `decomposed` → `CASE-20260726-6EF868` `awaiting_deps`). The branch put it, unguarded, as the FIRST statement of `run_dep_release_for_org` (`backend/app/services/pipeline_automation.py:~658`) ahead of all release work, so anything that can make a purely observational query or its logging loop raise — schema drift, a renamed column, a statement timeout — aborts dep-release for that org and strands every dependent at `awaiting_deps` fleet-wide. A visibility tool must never be able to break the thing it observes: extract it to `async def _log_deadlocked_dep_edges(db, org_id)`, wrap the WHOLE body in `try/except Exception -> logger.warning; return`, and call it after the releases. Second, independent mechanism worth internalising: `backend/tests/test_dep_release_slack.py` went **13 passed on master → 4 FAILED** because those tests fake `db.pool.fetch` with a fixed RESPONSE SEQUENCE — the new query consumed the first response, so the logging loop iterated the SELECT's rows (`case_id/open_deps/rejected_deps`) and died on `KeyError: 'blocker_id'`. So an "additive, read-only, cannot-break-anything" diff broke 4 tests and the sweep. Reviewer rule: for ANY diff that adds a DB call to an existing function, run that function's own test file before reading another line — and when you see per-item `try/except` already inside the loop ("one bad case must not stop the batch"), check whether the new code sits OUTSIDE that guard, which is exactly where this one sat. Author rule: keep the query's `AND <table>.org_id = $1` scoping and read Records with `edge["col"]`, never `.get()`; note `pipeline_cases.org_id` is a TEXT `org_...` id, NOT a tenant UUID — scoping a diagnostic with a tenant UUID returns 0 rows and reads as "no deadlocks", the same false all-clear as a negative audit from the wrong API.
- **An anomaly detector's trigger condition must be evaluated against the HEALTHY STEADY STATE before the failure it imagines — a "backstop" whose predicate matches normal operation fires a high-priority false alarm on every real incident and trains operators to ignore it (2026-07-29, review-gate, CASE-20260728-578B47 REJECTED → CASE-20260729-SWPBFP):** the case asked for a backstop that catches `run_stale_submitted_sweep_for_org` (`backend/app/services/pipeline_automation.py`) silently failing to flag flaggable cases, and the branch fired it when `matched >= 1 and flagged == 0` persisted for 3 consecutive passes. But `flagged` counts only INSERTs that actually inserted — the hold INSERT carries `WHERE NOT EXISTS (SELECT 1 FROM human_holds WHERE task_id=$1 AND status NOT IN ('resolved','dismissed'))` and increments only when the command tag does not end in `" 0"` — and the sweep is idempotent by design and (its own docstring) "never changes case status". So a genuinely stuck case KEEPS MATCHING on every later pass while its hold stays open: `matched>=1 && flagged==0` IS the correct steady state from pass 2 onward. One real stale case therefore manufactures a `priority='high'` hold reading "the sweep may be silently failing" on pass 3, while the sweep is working perfectly and the hold it correctly raised sits open right beside it; the sweep runs once per automation cycle from BOTH `run_now()` and the `start_pipeline_automation()` loop, so it recurs forever, and because the branch never cleared its per-org history the false hold is re-raised on the very next pass the moment a human resolves it. Note the branch DID obey the prior DFA001/DPDLK1 lesson — exception-guarded, placed after the work, correct columns — so guarding is necessary but not sufficient: the PREDICATE is the other half. Author rule: for any "detect that X silently failed" ask, first enumerate what the healthy system emits each pass and prove your condition is false for all of it; distinguish "no new hold needed" (already-held, the suppression path) from "a hold was needed and did not land" (the `except` branch), and reset the counter after firing so a resolved hold cannot instantly re-raise. Reviewer rule: for every new counter-threshold alert, hand-simulate 3 passes of the ordinary case before reading the SQL — an idempotent writer's second pass is where these die.
- **Every retry/reconnect path must tear down the resource it is abandoning BEFORE re-acquiring — a handle replaced by reassignment is not a handle released, and the orphan keeps holding the exclusive lock forever (2026-07-28, commit 380155dd):** in Scan M's CS463 LLRP client three of six `_scheduleReconnect()` call sites (protocol ERROR_MESSAGE, non-zero status response, "session in use" event) scheduled a reconnect without closing the socket they were giving up on; `_connect()` then overwrote `this._socket`, and the orphaned socket sat ESTABLISHED for the life of the process, squatting the reader's single-client slot so every subsequent connect got ECONNREFUSED — user-visible as "Reader Not Responding" on every scan after the first, curable only by force-stopping the app. Reviewer tell: for any object with a supersede guard (`if (this._x !== x) return`), grep EVERY path that reassigns `this._x` and confirm each one destroys the old value first — the guard makes the leak SILENT by design, because the orphan's own close/error handlers are deliberately ignored. Centralize the teardown in the retry scheduler rather than repeating it per call site, and null the reference BEFORE destroy() so the resource's own close handler sees itself superseded and cannot schedule a second retry. Diagnostic signature of this class of bug: the OS says the resource is held (ESTABLISHED socket, open fd, held lock) while the app reports it as unreachable.

- **A reachability PROBE against a single-client resource is itself a client — never "check if it's up" by connecting; let the real connect be the test. And confirm the leak from the RESOURCE's side, because the client's own socket table under-reports it (2026-07-29, bench-verified on the CS463, commits c2497150 + 6e277421):** Scan M's Setup tab ran a silent pre-check before auto-connecting — probe `:5084`, then dial `:5084`. Two connects for a reader that accepts exactly one. The probe's socket was destroyed client-side but the READER kept it `ESTABLISHED` with no peer, forever (the daemon sends no keepalive, so nothing reaps it), owning the only LLRP slot until `CS463LLRPDaemon` was restarted; every later connect — including the real scan — got `ECONNREFUSED`, surfacing as the familiar "Reader Not Responding". Second, subtler trap: probing the appliance's *other* ports is not free either — `:80` on the CS463 is the web app served by the GlassFish java process that is the LLRP daemon's PARENT pid, so opening and abruptly destroying that connection got the daemon restarted, tearing down the session the app was building in the very next step (~6 connects per visit, all `CLOSE_WAIT`, listener blinking out). Measurement rule, and the reason this shipped as "invisible": throughout all of it the tablet's own `/proc/net/tcp` showed NOTHING on :5084 — the orphan is only visible in `netstat -tanp` ON the reader (serial console COM7 115200 root/`csl`). A clean client-side socket table is NOT evidence that the far end released the resource; for anything exclusive, assert on the far end's view. Isolating move that found it: press the manual Connect button — the same code path minus the probes — and see it connect first try and hold. Complements the teardown rule above: that one is about releasing what you took, this one is about not taking it twice.

- **A gate that suppresses its own input is self-reinforcing — bound its evidence window by AGE as well as by COUNT, or the first bad streak is permanent (2026-08-13, `backend/app/services/team_autofeed.py`):** team auto-feed suspended team2/team3 on a rolling "last N terminal cases" pass-rate metric, and suspension stops feeding that team. With no new cases the window can never refresh, so the same 4 fallbacks from 2026-07-24 still held team2 suspended on 08-09 and team3 on 08-11 — and because the dedupe checked only `status NOT IN ('resolved','dismissed')`, resolving the HI notice refiled a byte-identical one on the next loop (3 copies of the same `6/16 62%` text). Rules: (1) any rolling metric that gates the supply of its own samples needs an age bound (`updated_at >= now() - make_interval(days => $n)`), which drains the window and resumes the subject on probation; (2) pair every auto-filed notice with an auto-RESOLVE on the same condition — a notice that outlives its condition is board noise forever; (3) give dedupe a time cooldown, not just an open-row check, or a human resolving it is the trigger to refile; (4) an auto-filed notice must name the failing ids and the split by failure mode — "6/16 fell back" was not even true (4 fell back, 2 were rejected); (5) self-healing state is a LOG, not a hold — the notice now ships behind `AUTOFEED_SUSPENSION_HOLDS`, default off.
