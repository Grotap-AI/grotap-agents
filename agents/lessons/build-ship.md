# Lessons — Build, tests & ship

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** you add or change tests, change a function/handler signature, rename a module, touch app startup, or the suite/CI is red.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,
> claim-first, with the case id. Before appending, check whether an existing line already

- Bash harness under `set -euo pipefail`: a helper must NOT end with a bare `[[ cond ]] && cmd` — false cond → rc=1 → `set -e` aborts the whole script with ZERO output (61647F ran 0 of 10 tests). Use `if…fi` or `return 0`; RUN shipped tests in default no-flag mode before claiming green.
- **Changing an INSERT/model/function signature means updating its tests in the SAME branch — a signature change without test updates leaves master's suite red, and the py_compile-only merge gate won't catch it (2026-07-11):** master commit a64ffd12 removed `cobrowse_session_id` from `ai_support.py` (CreateSessionRequest model + the `ai_support_sessions` INSERT, dropping it from 7 positional params to 6 so `openreplay_session_id` moved from `$4`/`args[3]` to `$3`/`args[2]`) but touched no test files, so 4 tests in `test_openreplay_feature_gating.py` / `test_ai_support_openreplay_plumbing.py` (asserting `"cb-123" in insert_args`, `insert_args[3] is None`, fake-pool `openreplay=args[3]`) began failing on master and stayed red because nothing runs pytest at merge. When you alter a SQL column list, a Pydantic model, or any positional-arg contract, grep the tests for the old shape (column name, positional index, fake-pool arg map) and fix them in the same branch; the reviewer only runs `python -m compileall` + `tsc`, so a red pytest ships silently. Also: `git diff A...B` (three-dot) diffs vs the merge base and HIDES changes that landed on master after you branched — a stale branch can look net-new while actually regressing already-landed work; confirm with two-dot `git diff origin/master..branch`. Found by review gate 2026-07-11; fix: CASE-20260711-AISTST. **RECURRED 2026-07-30 (CASE-20260730-13CBBA, review-gate REJECT → CASE-20260730-BRFIX1), and it shows the victim you will not think to grep for:** a SEVEN-line change adding the `branch` column to both `_log_dispatch` INSERTs in `backend/app/services/agent_dispatch.py` (5→6 and 6→7 positional args) turned 70 green into 9 failures across FOUR files, because `tests/test_dispatch_log_team_meta.py::_insert_args()` returns the recorded call and its callers do a FIXED-ARITY tuple unpack (`sql, case_id, task_number, filename, content, meta = ...` → `ValueError: too many values to unpack (expected 6)`), with `test_agent_dispatch_coalesced.py` / `test_dispatch_team_routing.py` asserting the same recorded shape. A test HELPER that destructures a recorded call is as much a consumer of your signature as a real call site: grep tests for the function name AND for tuple-unpacks/indexing of its recorded args, and actually run those modules — `compileall` is green on all nine. Reviewer rule: for any signature/column-list diff, run the touched test modules at BOTH origin/master and the merged tree and compare counts; "small diff" is not evidence. **Same one-line change also carried a value-format defect:** it wrote `origin/case-<CASE-ID>` into the column because the case TEXT spelled it that way, while the SAME file's `_build_task_fields` (L161) already defines the canonical `"branch": f"case-{case_id}"` that goes to the orchestrator payload, the task frontmatter and `fire_and_forget_trigger_pickup` — and `merge-verify.ts` prefixes `refs/remotes/origin/` itself, so the stored value double-prefixes. A literal quoted in a case description is NOT authoritative: derive a value's format from the constant the rest of the file/system already uses, and reuse that expression rather than re-deriving the string. **THIRD occurrence 2026-07-30 (`1b50152a`, CASE-20260729-002566) — and it names the ONE indexing style that survives an append and the one that dies:** appending `title` as the FINAL positional arg across eight `pipeline_cases` INSERT sites left every front-indexed (`args[3]`) assertion untouched, but broke three test modules that located the `case_data` blob as `args[-1]` — they began calling `json.loads()` on the title string — 14 tests, red on master 27+ hours. Never locate a recorded argument by INDEX (positive or negative); locate it by CONTENT — scan the recorded args for the one that `json.loads` into a dict, or match on the column name in the recorded SQL text — so appending a column cannot move it. And the same commit added a thorough NEW test module that was front-indexed and therefore immune: it went green while its neighbours went red, so "I added tests and they pass" is evidence about your file only — run the whole suite, not the module you wrote. **FOURTH occurrence 2026-08-01 (CASE-20260730-BDD2D8, merged by a peer review-gate run; master red ~40 min until `38351738`) — it widens the rule past INSERTs to any SELECT, and names the victim shape that fails on the READ side:** adding one `COUNT(*) FILTER (...) AS failed_deps` aggregate to `run_dep_release_for_org`'s SELECT and reading `r["failed_deps"]` broke 4 tests in `test_dep_release_slack.py`, whose `_FakeRecord(dict)` fixtures are built from explicit kwargs (`_FakeRecord(case_id=..., open_deps=0, rejected_deps=0)`). A keyword-constructed fake Record is not an assertion you can grep for — it raises `KeyError` the moment the production line reads the new key, so it kills EVERY test that merely drives that code path, including ones with nothing to say about the new column. Grep for the fake's CONSTRUCTOR, not just its assertions: any `Fake*Record(**kwargs)` / dict-literal row fixture feeding the function you touched must gain the new key in the same branch. Author rule: choose tests by what your change IMPORTS, not by what files are named, and close with `pytest tests/ --collect-only -q` (~5 min for 6592 tests) — it catches every import break at once and is the only cheap check that covers the quarantined modules' import path too. **Same family, third form — the harness itself hands your test a DIFFERENT module object than the code under test uses, and nothing errors (2026-07-30, review-gate, CASE-20260726-SYNCWR):** `backend/conftest.py` snapshots `sys.modules` AFTER each test file's import (`_file_snapshots[fspath] = dict(sys.modules)`) and `_restore_to()` DELETES every key not in that snapshot before each test — so a module first imported INSIDE a test body is "extra", gets evicted, and is re-executed fresh for every test in the file. For `app.context.tenant` that means a BRAND-NEW ContextVar object per test while the router under test still holds the original: the test writes one variable and the code reads another, silently, with no import error and no failure message pointing anywhere near the cause. Applies to any module-level singleton whose IDENTITY matters — ContextVars, registries, caches, connection pools. The conftest already special-cases `cryptography`/`OpenSSL` for the same reason ("duplicate class identities that break isinstance checks"), so the hazard was known but never generalized. Author rule: import at MODULE level in the test file, never lazily inside a test, whenever the thing imported carries identity; if a test asserting a ContextVar/singleton behaves as though the setter did nothing, suspect eviction before you suspect the product code.

Two packaging corollaries, both of which cost a rebuild here: (a) **`build/spec/*.spec` files are build OUTPUT** — `build.ps1` does `Remove-Item -Recurse $Spec` and PyInstaller regenerates them, so a `hiddenimports` edit survives exactly until the next build; declare it as `--hidden-import` in the build SCRIPT and assert on the script, never on the generated spec. (b) a lazy `import x` inside a function is the shape PyInstaller analysis is least reliable about and a file-path loader (`Path(__file__).parent / "x.py"`) is guaranteed WRONG in a frozen exe — there are no loose `.py` files to find, so an "optional" module resolves to `None` and the feature is silently absent in the field while working perfectly from source. Verify with the archive, not a string grep: `ZlibArchiveReader(build/work/<name>/PYZ-00.pyz).toc` — the module NAME appears in the exe bytes either way.
- **`re.escape()` in Python 3.7+ does NOT escape `:` — code that strips a leading `\:` from an escaped pattern silently never matches, quietly breaking `:param` route matching (2026-07-13):** the SCTX screen-context resolver's `_pattern_to_regex` (`backend/app/services/screen_context.py`) did `re.sub(r"\\:([A-Za-z_]\w*)", r"[^/]+", re.escape(pattern))` to turn `/users/:id` into `/users/[^/]+`. Since 3.7 `re.escape` only escapes regex metacharacters and `:` is NOT one, the escaped string is `/users/:id` (no backslash), so the `\\:` sub matched nothing → the pattern stayed literal `^/users/:id$` and matched ONLY the literal string `/users/:id`, never `/users/42`. Exact-match tier still worked, so the bug hid until a unit test exercised the parameterised tier. Match the raw token `re.sub(r":([A-Za-z_]\w*)", ...)` (colon is literal in the escaped output), or don't pre-escape. Surfaced+fixed by CASE-20260713-10C11D. Rule: when regex-transforming an `re.escape()`d string, remember which chars 3.7+ leaves unescaped (`: / - space , = ! " % ' / < > @ ` _ backtick ~`) — don't assume a `\<char>` will be present.

- **A React component test MUST drive controlled inputs through React's own event path — raw `el.dispatchEvent(new Event('change'/'input'))` after setting `el.value` does NOT fire React's `onChange`, so state never updates and every downstream assertion fails; and the `[attr!="x"]` attribute selector is jQuery-only, not valid CSS, so `querySelector(All)` throws a SyntaxError in jsdom (2026-07-15):** review-gate 2026-07-15 batch8 CASE-20260714-659A0E shipped `PromptBar.test.tsx` with 14/26 tests FAILING for exactly these two reasons — React 18 tracks an input's value via its own prototype descriptor, so a native event dispatched without the native value setter is seen as a no-op change; and `button[aria-label!="Undo last draft"]` threw `Invalid selector`. `tsc`/`compileall` are BLIND to both (types are fine, selectors are strings) — the failures only appear when vitest actually runs, which the review-gate's mandated gates do NOT include. Gate rule: for any branch whose PURPOSE is tests (or that adds a `*.test.tsx`), actually RUN `npx vitest run <file>` before merging — a green tsc is not evidence the tests pass. - **Order `except` clauses subclass-BEFORE-parent, or the specific handler is DEAD CODE — Python matches the first clause whose type is a base of the raised exception, and `PermissionError`/`ConnectionError`/`TimeoutError` are all subclasses of `OSError` (2026-07-21, review-gate batch3 FIX, CASE-20260721-35F273 → CASE-20260721-35FFIX):** the provisioner's BYO-cred try added `except (asyncio.TimeoutError, TimeoutError, OSError, ConnectionError)` ABOVE a dedicated `except PermissionError` that was supposed to file an HI hold + `needs_human=True` Freestream alert. Because `PermissionError` subclasses `OSError`, the tuple clause always wins → the permission-specific handler never runs, so permission failures are silently treated as transient (no hold, needs_human=False) — exactly the human-routing the case required, gone. (`ConnectionError` in the tuple is also redundant with `OSError`.) Rule: when adding a narrow `except SpecificError` alongside a broad `except (…, OSError, …)`, put the specific one FIRST; before merging any multi-clause except, check the MRO — if an earlier clause's type is a base class of a later clause's type, the later one is unreachable. Reviewer tell: two `except` clauses in one try where a later clause names a subclass of a type already caught earlier.

- **`0.0` is not “long ago” for a `time.monotonic()` stamp — its zero point is roughly host boot, so any `if now - _last_ts < WINDOW` guard initialised to `0.0` reads as *just happened* for the first WINDOW of uptime and silently disables the thing it gates; every CI runner is minutes old, so the bug shows up there and nowhere else (2026-07-26, master red 3 days, fixed by hand alongside review-gate rg3):** `api_health_monitor._last_alert_ts = 0.0` put the 1h alert cooldown around host boot, so the FIRST degradation alert after a restart was suppressed; `claude_app._models_cache_ts = 0.0` made the empty OpenRouter catalog look fresh for 1h, so `/claude-app/models` served the pinned default alone. Both surfaced as three “flaky” Backend CI failures (`test_api_health_monitor::test_s8/_s9b`, `test_claude_app_models::test_stale_cache_calls_fetch_models`) that pass on any dev box, because a workstation has hours of uptime and a runner has minutes.
