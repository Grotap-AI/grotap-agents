# Lessons — Build, tests & ship

> Incident lessons split out of `agents/GLOBAL.md` (2026-07-25). Each line is a defect that
> actually shipped. **Read this file when:** you add or change tests, change a function/handler signature, rename a module, touch app startup, or the suite/CI is red.
>
> New lessons for this surface are appended HERE, not to GLOBAL.md. Keep entries one line,
> claim-first, with the case id. Before appending, check whether an existing line already
> covers it — generalize that line instead of adding a near-duplicate.

- Bash harness under `set -euo pipefail`: a helper must NOT end with a bare `[[ cond ]] && cmd` — false cond → rc=1 → `set -e` aborts the whole script with ZERO output (61647F ran 0 of 10 tests). Use `if…fi` or `return 0`; RUN shipped tests in default no-flag mode before claiming green.
- **Changing an INSERT/model/function signature means updating its tests in the SAME branch — a signature change without test updates leaves master's suite red, and the py_compile-only merge gate won't catch it (2026-07-11):** master commit a64ffd12 removed `cobrowse_session_id` from `ai_support.py` (CreateSessionRequest model + the `ai_support_sessions` INSERT, dropping it from 7 positional params to 6 so `openreplay_session_id` moved from `$4`/`args[3]` to `$3`/`args[2]`) but touched no test files, so 4 tests in `test_openreplay_feature_gating.py` / `test_ai_support_openreplay_plumbing.py` (asserting `"cb-123" in insert_args`, `insert_args[3] is None`, fake-pool `openreplay=args[3]`) began failing on master and stayed red because nothing runs pytest at merge. When you alter a SQL column list, a Pydantic model, or any positional-arg contract, grep the tests for the old shape (column name, positional index, fake-pool arg map) and fix them in the same branch; the reviewer only runs `python -m compileall` + `tsc`, so a red pytest ships silently. Also: `git diff A...B` (three-dot) diffs vs the merge base and HIDES changes that landed on master after you branched — a stale branch can look net-new while actually regressing already-landed work; confirm with two-dot `git diff origin/master..branch`. Found by review gate 2026-07-11; fix: CASE-20260711-AISTST.
- **Adding a module-level import to a router breaks every test that stubs that dependency — update the stubs in the SAME branch (2026-07-12):** de11fd40 added `File`/`UploadFile` (fastapi), `RedirectResponse` (fastapi.responses) and `Field` (pydantic) to `claude_app.py`, but `tests/providers/test_anthropic_provider.py` builds in-memory stub modules for fastapi/pydantic that listed only the OLD names — collection died with `ImportError: cannot import name 'File' from 'fastapi' (unknown location)` and EVERY backend-touching CI run failed for 3 days, silently blocking Railway backend auto-deploys (deploy gates on CI; docs-only commits skip backend tests, so CI "looked" intermittently green). ~8 test files stub fastapi this way (`test_billing_webhooks.py` etc.). When you add ANY module-level import to a router/service, grep tests/ for `_stub_module(` + the module name and extend every stub that shadows it; `(unknown location)` in an ImportError = a bare `types.ModuleType` stub, not a broken install. Hand-fixed e5b33818.
- **Renaming/deleting a module means fixing every `mock.patch("old.module.path...")` STRING target too — `compileall`/`tsc` never see inside patch strings, and stale targets raise `AttributeError` only at test run (2026-07-12):** CASE-20260710-3E9B12 renamed `backend/app/providers/cobrowse_provider.py` -> `assist_provider.py` (`CobrowseProvider`->`AssistProvider`, `get_cobrowse_provider`->`get_assist_provider`) and correctly updated its own test file, but left `tests/test_ai_support_openreplay_plumbing.py` and `tests/test_openreplay_feature_gating.py` patching `"app.providers.cobrowse_provider.get_cobrowse_provider"`. `unittest.mock.patch` resolves that dotted string lazily at `__enter__`, so the now-deleted module import blows up with `AttributeError: module 'app.providers' has no attribute 'cobrowse_provider'` — 5 tests failed. A grep of `import` statements misses these because the old name lives inside a patch string, not an import. After ANY module/symbol rename, grep the WHOLE tree (not just imports) for the old dotted path in string literals — `grep -rn "old_module_name" backend` including tests — and confirm zero hits before sign-off; the review gate's `compileall`+`tsc` gate cannot catch a patch-string typo. The case's own "grep-verify no stale references" constraint would have caught it. Rejected at gate; fix: CASE-20260712-ASSPRV.
- **`re.escape()` in Python 3.7+ does NOT escape `:` — code that strips a leading `\:` from an escaped pattern silently never matches, quietly breaking `:param` route matching (2026-07-13):** the SCTX screen-context resolver's `_pattern_to_regex` (`backend/app/services/screen_context.py`) did `re.sub(r"\\:([A-Za-z_]\w*)", r"[^/]+", re.escape(pattern))` to turn `/users/:id` into `/users/[^/]+`. Since 3.7 `re.escape` only escapes regex metacharacters and `:` is NOT one, the escaped string is `/users/:id` (no backslash), so the `\\:` sub matched nothing → the pattern stayed literal `^/users/:id$` and matched ONLY the literal string `/users/:id`, never `/users/42`. Exact-match tier still worked, so the bug hid until a unit test exercised the parameterised tier. Match the raw token `re.sub(r":([A-Za-z_]\w*)", ...)` (colon is literal in the escaped output), or don't pre-escape. Surfaced+fixed by CASE-20260713-10C11D. Rule: when regex-transforming an `re.escape()`d string, remember which chars 3.7+ leaves unescaped (`: / - space , = ! " % ' / < > @ ` _ backtick ~`) — don't assume a `\<char>` will be present.
- **A refactor that renames a shell function/var OR changes a log/output string MUST update its companion test assertions in the SAME branch — a passing `tsc`/`compileall` gate is blind to bash test breakage, so the stale test only surfaces when someone runs it (2026-07-13):** review-gate 2026-07-13 CASE-20260713-B9FFCA generalized `_team2_daily_cap_ok`→`_team_daily_cap_ok <team>` in `agents/dispatch.sh` and changed the fallback log from `TEAM2_DAILY_CAP=10` to `TEAM_DAILY_CAP[team2]=10` and removed the `TEAM2_DAILY_CAP` env override — but left `agents/tests/test_dispatch_team_routing.sh` T11 asserting the old string and the old env override, silently breaking the suite (no CI workflow runs it, so it fails only for whoever runs it manually). Author/gate rule: when a diff touches a code path with an obvious companion test (grep the tests dir for the renamed symbol / the old output string), the test MUST change in lockstep; a diff that renames the thing under test but doesn't touch the test file is a defect signal, not a clean change.
- **A React component test MUST drive controlled inputs through React's own event path — raw `el.dispatchEvent(new Event('change'/'input'))` after setting `el.value` does NOT fire React's `onChange`, so state never updates and every downstream assertion fails; and the `[attr!="x"]` attribute selector is jQuery-only, not valid CSS, so `querySelector(All)` throws a SyntaxError in jsdom (2026-07-15):** review-gate 2026-07-15 batch8 CASE-20260714-659A0E shipped `PromptBar.test.tsx` with 14/26 tests FAILING for exactly these two reasons — React 18 tracks an input's value via its own prototype descriptor, so a native event dispatched without the native value setter is seen as a no-op change; and `button[aria-label!="Undo last draft"]` threw `Invalid selector`. `tsc`/`compileall` are BLIND to both (types are fine, selectors are strings) — the failures only appear when vitest actually runs, which the review-gate's mandated gates do NOT include. Gate rule: for any branch whose PURPOSE is tests (or that adds a `*.test.tsx`), actually RUN `npx vitest run <file>` before merging — a green tsc is not evidence the tests pass. Author rule: set controlled-input values via `Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype,'value').set.call(el,v)` then dispatch `input`, or use `@testing-library/react` `fireEvent.change`/`userEvent`; never use `!=`/`^=`(non-standard) jQuery selector extensions in `querySelectorAll`. A test file that fails is a defect, not a "small latent" merge-with-fix — reject it. Fix filed CASE-20260715-FSTFIX.
- **Mocked-binary tests prove runner LOGIC, never the CLI INTERFACE — validate flags + config schema against the REAL pinned binary on the target box before a runner ships (2026-07-18, 264ABC pilot):** codex-run.sh shipped with invented `codex exec` flags (`--approval-mode/--quiet/--task-file` — none exist in codex-cli 0.144.5; instant exit 2 on every attempt) and setup-team2-box.sh wrote a pre-0.144 config schema (`provider`/`[providers.*]`/`wire_api="chat"`) that codex SILENTLY ignores — falling back to the default OpenAI provider; only `--strict-config` surfaces it. Third failure layer: Ubuntu 24.04 AppArmor blocks unprivileged user namespaces, so codex's bundled bwrap sandbox dies on every model-issued command (`bwrap: loopback: Failed RTM_NEWADDR`) — fixed via `/etc/sysctl.d/60-codex-userns.conf` (now in setup-team2-box.sh). Gate rule: any branch adding/altering an external-CLI runner must include evidence of a LIVE smoke on the target box (real binary, `--strict-config` where supported, one end-to-end model call) — stubbed test suites passing is not acceptance. Fixes: platform 60f8b716 + f5967273.
- **A refactor that changes a handler's SIGNATURE (removes helpers AND re-adds/reorders params) leaves the test suite RED until the tests are updated in LOCKSTEP — and a "confirm CI green" / stale-test-cleanup fix must diff the tests against the CURRENT router signature, not assume the shape it remembers (2026-07-19, review-gate SKIP of CASE-20260719-1F3FBC + two fresh master-red defects):** commit 77cbc262 "re-add Request param, wire Turnstile validation" deleted `_ip_hits`/`_check_ip_throttle` from registration.py AND made `submit_registration(body, background, request)` (request REQUIRED, used by check_turnstile via get_client_ip) — but never updated the tests, so master pytest fails at COLLECTION (`ImportError: cannot import name '_check_ip_throttle'`) and `test_free_stream_events.py` calls it with `(body, req, bg)` (background/request SWAPPED). Branch 1F3FBC ("confirm CI green") correctly dropped the dead `_ip_hits` imports but ALSO stripped the `request` positional from every call — trading one break for `TypeError: submit_registration() missing 1 required positional argument: 'request'` (proven by running it against master). It was also stale on a SECOND axis: master had already renamed `RATE_LIMIT_RPM`→`RATE_LIMIT_IP_RPM` (default 300), so the branch's test_rate_limit_rpm_env.py was superseded (merge conflict). Author rule: any signature-changing refactor of a handler must update its tests in the SAME commit — grep tests for the symbol names you remove AND the call sites of the function you re-parametrize. A test-cleanup fix must `git grep` the CURRENT def line and re-run the affected modules to green, never merge on import-success or a single assumption about which param was dropped. Gate rule: for a "make/confirm CI green" or stale-test case, actually RUN the touched test modules against real master before merging; if the branch removes a param the current signature still requires, it's a stale-base FIX. Fix CASE-20260719-CIRGFX (P1, master is currently red).
- **`py_compile`/`tsc` are BLIND to a NameError inside a function body — any diff that touches app STARTUP (lifespan, database init/connect, migration runner, middleware wiring) is unverified until the doppler dev FastAPI BOOT TEST actually runs the startup path; skipping it can brick every subsequent prod deploy (2026-07-21):** CASE-20260721-0C2810 (shared Fernet util) added `_encrypt_existing_urls()` to `ControlPlaneDB.initialize()` calling `_get_fernet()` — a symbol the module never imported (only `encrypt_secret`/`decrypt_secret` were). `py_compile` passes (valid syntax; NameError is runtime), the orchestrator merged, and the lifespan NameError made EVERY Railway backend deploy FAIL from 02:54Z — prod froze on the last good image and all later merges (AIML classifier, /lanes endpoint) sat dark until a hand P1 (CASE-20260721-BA317C, one-line import fix 87bbda9d). Author rule: if your diff adds/changes code that runs during startup, you MUST run the boot test (`doppler -c dev` boot of app.main, or directly exercise `connect()`/lifespan) and paste the OK line into your evidence — "compiles" is not evidence for startup code. Gate rule: a branch touching `app/main.py` lifespan, `app/database/*` init paths, or middleware order does not merge without boot-test evidence; also grep new function bodies for names absent from the module's imports (a 5-second check that catches this class outright).
- **Order `except` clauses subclass-BEFORE-parent, or the specific handler is DEAD CODE — Python matches the first clause whose type is a base of the raised exception, and `PermissionError`/`ConnectionError`/`TimeoutError` are all subclasses of `OSError` (2026-07-21, review-gate batch3 FIX, CASE-20260721-35F273 → CASE-20260721-35FFIX):** the provisioner's BYO-cred try added `except (asyncio.TimeoutError, TimeoutError, OSError, ConnectionError)` ABOVE a dedicated `except PermissionError` that was supposed to file an HI hold + `needs_human=True` Freestream alert. Because `PermissionError` subclasses `OSError`, the tuple clause always wins → the permission-specific handler never runs, so permission failures are silently treated as transient (no hold, needs_human=False) — exactly the human-routing the case required, gone. (`ConnectionError` in the tuple is also redundant with `OSError`.) Rule: when adding a narrow `except SpecificError` alongside a broad `except (…, OSError, …)`, put the specific one FIRST; before merging any multi-clause except, check the MRO — if an earlier clause's type is a base class of a later clause's type, the later one is unreachable. Reviewer tell: two `except` clauses in one try where a later clause names a subclass of a type already caught earlier.
- **A branch that deliberately REWRITES a pinned string/shape (SQL text, response key set, error message) MUST update the contract test that pins it IN THE SAME BRANCH — the rewrite is correct, the stale assertion is what turns master red, and because the break is in a test file the branch's own `py_compile`/`tsc` gates and any targeted test run stay green (2026-07-25, review-gate rg3, CASE-20260725-86AB4E):** the /machine/summary perf case (commit 42d8a1d4) rewrote `_HI_BLOCKING_SQL` in `backend/app/routers/machine_status.py` from an OR-JOIN `COUNT(DISTINCT h.hold_id)` into `SELECT COUNT(*) FROM ( ... ) deduped` (a UNION of two index-friendly join arms, behaviour-equivalent) but left `backend/tests/test_machine_summary_hi_blocking.py::test_sql_shape_matches_contract` asserting the OLD literal `"COUNT(DISTINCT h.hold_id)" in sql`. Backend CI went red on that merge and STAYED red on every subsequent push to master (4 failed / 6304 passed), which also masked three unrelated order-dependent pollution failures in the same runs. Author rule: after changing any literal that a test asserts with `in`/`==` against source text, grep the test tree for a distinctive fragment of the OLD literal and update those assertions in the same diff — pin the BEHAVIOUR (dedup performed, both join arms present, status filters, `c.org_id = $1` scoping) rather than the exact SQL text, so the next optimisation does not break it again. Gate rule: a perf/refactor branch whose diff touches a module that a `test_*_contract`/`test_*_shape` file pins does not merge without that test file in the same diff or an explicit note that it was checked; and when triaging a red master, split failures into DETERMINISTIC (reproduce on a clean worktree at the master commit) vs ORDER-DEPENDENT (passes in isolation, fails only in full-suite order) before assigning a root cause — here 1 of the 4 was this stale assertion; the other 3 were NOT pollution at all but real environment-dependent product bugs whose fix DID belong in product code — see the `time.monotonic()` sentinel lesson below.
- **`0.0` is not “long ago” for a `time.monotonic()` stamp — its zero point is roughly host boot, so any `if now - _last_ts < WINDOW` guard initialised to `0.0` reads as *just happened* for the first WINDOW of uptime and silently disables the thing it gates; every CI runner is minutes old, so the bug shows up there and nowhere else (2026-07-26, master red 3 days, fixed by hand alongside review-gate rg3):** `api_health_monitor._last_alert_ts = 0.0` put the 1h alert cooldown around host boot, so the FIRST degradation alert after a restart was suppressed; `claude_app._models_cache_ts = 0.0` made the empty OpenRouter catalog look fresh for 1h, so `/claude-app/models` served the pinned default alone. Both surfaced as three “flaky” Backend CI failures (`test_api_health_monitor::test_s8/_s9b`, `test_claude_app_models::test_stale_cache_calls_fetch_models`) that pass on any dev box, because a workstation has hours of uptime and a runner has minutes. Author rule: a never-happened-yet monotonic stamp is `None` and the guard tests `is not None` first — never `0.0`, and never `time.time()` mixed with `time.monotonic()`; in tests write an honest elapsed stamp (`time.monotonic() - TTL - 1`) or `None`, never `0.0`. Reproduce/pin it by faking a freshly-booted host (`patch("time.monotonic", return_value=60.0)`) so the regression test fails on every host, not just CI.
- **“Passes locally, fails in CI” is an ENVIRONMENT difference, not test-order pollution — Backend CI runs `pytest --forked`, so each test executes in its own fork and cannot inherit another test's module mutations; and a GREEN Backend CI run often means the suite never ran at all (2026-07-26):** commit 958e25e4 diagnosed the three failures above as ring-buffer/cache pollution and added autouse reset fixtures that re-asserted the same `0.0` assumption — master stayed red, and the two green runs that seemed to prove the fix were ingestion-worker-only commits where `detect-changes` set `backend=false` and every backend step was skipped. Triage rule: before blaming ordering, confirm the suite is not forked, and confirm a green run actually EXECUTED the step (`gh run view <id> --log | grep 'Run backend tests'`); then look for host invariants the runner does not share with a dev box — uptime (`time.monotonic()`), wall clock/TZ, core count, locale, `$HOME`, network egress.
- **Two build-ship rules from the 7/26 red master (root cause itself is filed in `sql-migrations.md` — additive migration vs hand-built fake rows; do not re-file it here):** (a) after fixing a red master, RE-READ the new failure list in full — the next run is not a verdict on your fix. Here the run that cleared 3 monotonic-sentinel failures came back red with 34 completely different ones (`test_print_cloud_integration.py`) that had landed meanwhile, so "still red" did NOT mean "fix didn't work"; diff the failure SETS, don't compare pass/fail. (b) A hermetic subprocess test that filters env down to `PATH/HOME/PYTHONPATH` must also pass **SYSTEMROOT** — without it Windows cannot initialise Winsock, so `import socket` (hence `import app.main`) dies with `OSError: [WinError 10106]` and the test is unverifiable on a dev box while Linux CI stays green (platform e999a674).
