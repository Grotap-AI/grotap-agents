- **Never assign `window.name` for per-tab state (2026-07-10):** 88162F used `window.name = 'grotap-win-'+rand` as a window-scope discriminator, but the platform uses `window.name` as the `window.open` TARGET NAME so app tiles refocus instead of stacking (`WorkspaceContext.openApp` names windows by app slug; `ClaudeCodePage` uses `'claude-code-seat'`). Clobbering it made every app open a duplicate window after AI support ran in it. To distinguish a same-tab reload from a `window.open` sessionStorage copy, use a discriminator that does NOT hijack `window.name` (and note plain sessionStorage keys ARE copied by `window.open`). Fix: CASE-20260710-72AF65.
- **A branch that adds a REQUIRED field to a shared TS interface breaks every sibling branch that CONSTRUCTS that type — both pass `tsc` alone, only the COMBINATION fails (2026-07-12):** CASE-20260712-695BAD added `assigned_team_id: string | null` and `location_visibility: LocationVisibility` as non-optional fields to the ranch-plan `Task` interface (`frontend/src/pages/ranch-plan-types.ts`). CASE-20260712-E5E41B (built in parallel against the OLD type) constructs 5 `DEMO_TASKS` object literals of type `Task`; once 695BAD merged, those literals failed `npx tsc --noEmit` with TS2739 (missing the two new required props). Each branch was individually green, so neither agent nor per-branch review caught it — the review gate only saw it at the post-merge combined tsc and had to merge 695BAD solo + route E5E41B's fixtures back (CASE-20260712-E5FX1B). Mitigations: (a) COALESCE a type-defining case with its type-consuming siblings onto ONE branch so the combined tsc runs before sign-off; (b) prefer adding new interface fields as OPTIONAL (`?:`) when existing code/fixtures construct the type, tightening to required only once all constructors are updated; (c) at the gate, always run the FULL combined-tree tsc after merging sibling frontend branches, never trust per-branch green.

- **An Android app reaching a device on a SECONDARY interface (USB-Ethernet/eth0, USB-tether, a second WiFi) must bind its socket to that interface's `android.net.Network` — Android per-app routing is by network fwmark, NOT source IP, so detecting the NIC and/or setting `localAddress` is NOT enough; while WiFi is the validated default network every unbound socket egresses via WiFi and times out (2026-07-23, bench-verified, CASE-20260723-E70B1D):** ScanTap's CS463 LLRP transport + Connection Doctor opened `react-native-tcp-socket` to `192.168.25.160:5084` with no Network binding. The tablet had WiFi (validated → default) AND eth0 (192.168.25.100, NOT validated because the reader gives no internet, so Android never promotes it to default). WiFi's routing table has no route to 192.168.25.0/24, so every connect timed out — even though `ping -I eth0` worked and the reader's LLRP was live (pushes a 32-byte READER_EVENT_NOTIFICATION, msg type 63, on connect). The `EthernetNetworking` native module only DETECTED the NIC (`listEthernetInterfaces`/`isEthernetAvailable`); it never bound. Proof: dropping WiFi makes eth0 the default and the identical socket reaches the reader. Fix pattern: capture the `Network` from the `ConnectivityManager.NetworkCallback.onAvailable(Network)`, and `cm.bindProcessToNetwork(ethNet)` before opening the socket (rebind on every reconnect to survive an eth0 flap — the USB-Ethernet adapter RE-ENUMERATES when a charger is plugged into a pass-through jack), `bindProcessToNetwork(null)` on stop so the app regains internet for API sync (local-first capture to SQLite makes the no-internet scan window fine). Do NOT rely on Android making eth0 the default — a reader/appliance is not an internet gateway, so its network never validates. `tsc`/`expo config` are BLIND to this (pure runtime routing); only a real device with WiFi UP exposes it. Author/reviewer rule: any mobile feature that talks to hardware on a non-default interface must bind to that `Network`, and must be bench-tested with the phone's normal WiFi still connected — testing with WiFi off hides the bug.

- **A cancel/supersede guard (boolean flag OR monotonic generation token) must guard every WRITE in the stale-bail path by IDENTITY — `myRun !== current` gates only WHETHER you bail, not WHAT you may clobber; an unconditional `someRef.current = null` / `setX(null)` in that path wipes the NEWER run's live handle, so the resource it owned is never released (2026-07-26, review-gate, CASE-20260726-F4902E merged-with-defect → CASE-20260726-SCANGEN):** scantap `scan.tsx` correctly replaced `preflightCancelledRef` with `preflightRunRef` generation counter, but both stale-bail sites still did bare `readerRef.current = null; setReaderState(null)`. Repro: preflight A → Cancel → Start again within `READER_CONNECT_TIMEOUT_MS` (5s); run B sets `readerRef.current = svcB`, then A's connect promise times out, sees itself stale, and nulls the ref pointing at *svcB* — so `captureScans()`/unmount read null, never call `svc.stop()`/`clearActiveReader(svc)`, and the CS463's single LLRP slot leaks (the exact CLOSE_WAIT wedge `activeReader.ts` exists to prevent). The correct pattern was already in the same codebase: `clearActiveReader(svc)` is written `if (_active === svc) _active = null` — copy that guard (`if (readerRef.current === svc) ...`) to every ref/state write a superseded run performs. Corollary: also generation-guard the ASYNC CALLBACK, not just post-`await` steps — an abandoned run's `svc.start(...)` status callback kept calling `setReaderState(state)`, which became user-visible the moment a sibling case rendered `readerState` on the idle screen (state a stale run writes is harmless only until someone renders it). Author rule: when you introduce a generation token, list every write the losing run can still perform and identity-guard each one. Reviewer tell: a stale-bail block whose condition is generation-checked but whose body assigns to shared refs/state unconditionally — and note `tsc` plus both siblings' own diffs are BLIND to it (git auto-merged these two file-sharing siblings with NO conflict; verify merged SEMANTICS, not the absence of conflict markers). **Gate disposition rule for the LATER siblings of such a group (2026-07-26, same 4-way fan-out onto `scan.tsx`: 4AF604+F4902E landed, stranding 0C079F and AC011F on the pre-token base):** when the token/primitive lands first, a straggler branch does not merely conflict — it still SPEAKS THE REPLACED PRIMITIVE, so force-resolving its conflict silently DELETES the protection the earlier sibling added. Triage by what the straggler's hunk does to that primitive: hunks that are ADDITIVE around it are salvageable by union resolution at the gate (0C079F wrapped `beginBatch`→`startScanning(svc?)`; kept master's post-await stale guard, gates green, MERGED); hunks that DELETE OR RENAME it must be REJECTED to a rebase fix case, never hand-woven (AC011F still wrote `preflightCancelledRef.current = true` — a symbol master no longer has → TS2304 *and*, since it never bumps the generation, the exact LLRP-slot leak faf1d7fc was landed to fix; its conflict also wanted to drop `const myRun = ++preflightRunRef.current`). Corollary for the fix-case body: spell out the primitive's OLD and NEW names and which sibling now owns the flow, or the rebase agent re-derives the stale version. Also: `setCheckingConn` vs `checkingConn` — a case-SENSITIVE grep for a `useState` name misses every `setX` call site, so "dead state" can look already-deleted when three writes remain. **Scope limit of the whole pattern — a generation token defends against SUPERSESSION, never against RE-ENTRY, so a control whose `onPress`/`onClick` stays MOUNTED across its own `await` still needs a separate in-flight guard (2026-07-26, review-gate, CASE-20260726-SCANCFM merged → CASE-20260726-SCNDBL):** the rebased 'Confirm — Start' button is `disabled={readerState !== 'connected'}` and awaits `startScanning(svc)` → `beginBatch` → `await createBatch(...)` — a network round trip — before `setPhase('scanning')` finally unmounts the confirming screen. `readerState` does not change during that window, so the button stays enabled and tappable; both taps capture the SAME `myRun` (nothing bumps the counter on a tap), both pass the post-await stale check, and beginBatch runs twice → two `createBatch` rows, `batchIdRef`/`setBatchId` overwritten by the second, and batch #1 left open forever because `captureScans()`/`handleStartAnotherBatch()` only ever finalize `batchIdRef.current`. Contrast the sibling 'Start Anyway' button in the same file, which is safe only incidentally: `setConnWarning(null)` unmounts its modal SYNCHRONOUSLY before the await. Author rule: when converting an auto-advancing flow into a user-confirmed one, whatever the await used to be hidden behind is now a visible re-entrancy window — add `if (busyRef.current) return; busyRef.current = true` plus a `finally` reset, reflect it in `disabled=`, and clear it on the cancel/back path. Reviewer tell: an `async` handler with an `await` whose only `disabled` condition is state that CANNOT change during that await.

Author rule for any MRT/Mantine table: set `background` beside every `color` (`mantineTableBodyCellProps` AND `mantinePaperProps` — the cell background alone leaves the white Paper showing through the loading overlay, the gutters and `renderDetailPanel`), and prefer fixing the CLASS by wrapping the app's routes in `<MantineProvider theme={{ colorScheme: theme }} withNormalizeCSS={false} withGlobalStyles={false}>` driven by `useTheme()` (mirrors `AppFrame.tsx:117`, but theme-DRIVEN — never copy the other pages' hardcoded dark values, they break the light toggle). Reviewer tell: `grep -n 'path="/<app>' frontend/src/App.tsx` — routes wrapped in `PrivateRoute` only never pass through `AppFrame`, and `tsc` is blind to all of it. **Corollary on the regression test such a case commissions (→ CASE-20260726-PCGRDT):** "assert the text is not invisible" means CONTRAST between `getComputedStyle(td).color` and `.backgroundColor` — a test that reads only the background and asserts it is dark encodes the one historical symptom, still passes for dark-on-dark, and (because a `match(/\d+/g)`-style luminance helper scores `rgba(0,0,0,0)` as 0) passes for a transparent cell too. Any new visual regression test must be shown to FAIL with the fix reverted; playwright is in NO CI gate here, so nothing else will ever catch a test that cannot fail. **Same defect class, AG Grid variant — the vendor theme, not the provider, is the thing that must follow `data-theme` (2026-07-28, `d1b791ec`, owner-reported "all Pipeline Cases titles are blank"):** `lib/agGrid.ts` built `grotapGridTheme` as bare `themeQuartz.withParams({accentColor,fontFamily,headerFontWeight})` — AG Grid's Theming API defaults to a WHITE surface and has no idea `<html data-theme="dark">` exists, so EVERY grid on the platform painted `var(--text)`=#fff cells on #fff. - **A live-prod e2e spec dropped into `frontend/e2e/` breaks EVERY other playwright run unless it is env-guarded, because `testDir: './e2e'` collects it for everyone: anything read at MODULE scope (`fs.readFileSync(process.env.X)`, a required token) throws during collection, before a single test starts, so the failure is not "my spec skipped" but "the whole suite aborted" (2026-07-27, commit 9a064b82, caught by the pre-commit Codex pass — `tsc` is blind to it and playwright is in no CI gate here).** Pattern to copy is `e2e/ai-support-live.spec.ts`: file-level `test.skip(() => !process.env.<FLAG>, '...')`, every env read moved INSIDE the test body, and screenshot paths repo-relative (`e2e/screenshots/...`) — a hardcoded `C:/1Claude/...` only resolves on one machine. - **A RESOLVED 2xx carrying the wrong body shape skips your `catch` entirely — so a component that guards `try/catch` around a fetch is still one `.find()`/`.length` away from blanking the whole screen; guard the SHAPE (`Array.isArray`), not just the rejection (2026-07-28, commit f497e217, found finishing 0315479e):** `GridTemplateBar` mounts on EVERY platform grid and did `setTemplates(res.data.templates)`; `templates.find(...)` runs on every render, so an undefined there throws out of the React tree and takes down the entire page the grid lives on — the component's own comment promised "a templates outage must never take the grid with it", and it kept that promise only for a rejected request. Same defect one file over in `ScanTapPrintTagsPage` (`setDocs(res.data.rows)`). That single missing `**/grid-templates*` mock was blanking 5 of 8 tests in `manorview-acceptance.spec.ts`, each failing with an unrelated-looking "grid has no rows". Tell: several independent screens in one mocked spec all failing at `expect(rows)`, and a body that renders only the sidebar. Before debugging per-screen selectors, list the app's on-mount fetches and diff them against the spec's `page.route` calls. **And when a spec has drifted this far, its selectors have too:** assert AG Grid rows via the grid's `data-testid`, not the `<table>` a screen was converted away from; expect columns outside the horizontal viewport to be absent (AG Grid virtualizes them); and pick a row to click by CONTENT — AG Grid recycles row nodes and repositions them with transforms, so `.first()` is not the top row after a filter round-trip.
- **"Also filter it client-side" is a NO-OP when the endpoint the page already calls applies the identical SQL predicate — and adding the second fetch inside `Promise.all` converts an unrelated endpoint's failure into a blank screen (2026-07-29, review-gate, CASE-20260728-EFE218 orch-merged `ceb70452`, post-hoc → CASE-20260729-APPSUB):** the ask was "only show apps the company is subscribed to" on `/setup/app-access`, and the branch added a second `GET /team/invitable-apps` and intersected it with the app list. But `GET /app-registry/app-visibility` — the endpoint that page ALREADY called — runs the same `JOIN tenant_app_subscriptions s ON s.app_id=a.app_id WHERE s.tenant_id=$1 AND s.status='active'` as `/team/invitable-apps` (`backend/app/routers/team.py:202`), so the requirement was already satisfied server-side and the change intersects a list with itself. Not free, though: `load()` became `Promise.all([...])`, which rejects if EITHER call fails, so any error from the newly-added endpoint now renders "Failed to load app access" and nothing else on a screen that previously worked. Its own stated rationale ("guards against endpoint drift") was also self-defeating — the `subscribedIds.size > 0 ? filter : allApps` fallback skips the filter precisely when the new endpoint returns empty, i.e. in the drift case. Author rule: before adding a client-side filter for a "only show X" ask, read the SQL of the endpoint already in use and confirm the predicate is absent — if it is present, the bug is elsewhere (here the invite screen the case described is `SetupUsersPage.tsx`, which had always used `/team/invitable-apps`); and never widen a working `load()` into `Promise.all` with a non-essential call — use `Promise.allSettled` or a per-call `.catch`, so a redundant request cannot blank the page. Reviewer rule: when a diff's own comment says the server "already filters", that is the finding — diff the two endpoints' WHERE clauses and check whether the new fetch's auth predicate matches the old one before assuming a 403 regression.
- **Extracting an inlined computation into a "pure helper" must DELETE it from the call site — a helper that recomputes what the caller still computes doubles the work instead of factoring it out, and every gate stays green (2026-07-30, review-gate batch2, CASE-20260730-CB7AD1 MERGED → CASE-20260730-CHKAGG):** the case asked for `deriveChunkingIdentity(batch, tags)` in `platform/mobile/scantap/services/syncPayload.ts` to encapsulate `aggregateTagRecords(getTagsForBatch(batch.id))` + the chunk-size pin. The helper is correct and the diff reads as a clean −24/+18 extraction, but the new helper aggregates only to read `records.length` and throws the array away, while `app/(tabs)/send.tsx` kept its own `const records = aggregateTagRecords(tags)` on the next line — so the Send prepare loop now collapses every raw tag read to one record per EPC TWICE per selected batch, on a handheld's UI thread, for sweeps of tens of thousands of reads. `tsc`, jest and review-by-diff all pass it because nothing is incorrect; only the cost changed. Author rule: when a helper's job is to compute a value the caller ALSO needs (here the aggregated records, not just their count), return it — or take it as a parameter — rather than deriving it twice; the extraction is not done until the original expression is gone from the caller. Reviewer tell for any "extract into a pure helper" case: grep the call site for every function the new helper calls internally and confirm zero remaining duplicate invocations. Keep any value that is PERSISTED (here the `{chunkSize, recordCount}` resume-mark identity that `buildIdempotencyKey`/`resumeStartPart` name parts from) byte-identical in shape while doing so. Same root cause when the helper is a shared PREDICATE or CONSTANT rather than a computation (2026-08-20, review-gate, CASE-20260820-53DAD1 MERGED → CASE-20260820-RV1A2B): a "create a shared `isX()` utility" case must first grep master for the rule it is restating — `frontend/src/utils/roleVisibility.ts` minted `isGrotapTeamMember()` as a second copy of `AuthContext`'s `isGrotapUser: !!state.user?.email?.endsWith('@grotap.com')` (line ~369, already read by ~10 pages) instead of having the context delegate to it, so the new header and the rest of the app now answer "is this a Grotap user?" from two places that will drift — and only one of the two copies normalises case (`SetupUsersPage.tsx:134` lowercases, `AuthContext` does not). A new shared helper is not done until the pre-existing definition is deleted or calls it.

- **This repo has NO `@testing-library/jest-dom` — every DOM matcher an agent reaches for from muscle memory (`toBeDisabled`, `toBeInTheDocument`, `toHaveTextContent`, `toBeVisible`) is a runtime failure, and `tsc` reports it as a bare `TS2339 Property does not exist on type 'Assertion<HTMLElement>'` that reads like a types-only nit (2026-08-10, CASE-20260810-PIKIOSK, caught at the review gate — the agent shipped a branch whose own new test file failed 2/10):** vitest ships chai, not jest-dom, and `vitest.config.ts` `setupFiles: ['src/test-setup.ts']` does not register it; the runtime error is the more honest `Invalid Chai property: toBeDisabled`. The pattern every passing test in this repo already uses is a plain property read — `expect((btn as HTMLButtonElement).disabled).toBe(true)`, `expect(screen.queryByText(/x/)).toBeTruthy()`. **Do not add jest-dom to fix a single test**; one new dependency to satisfy a matcher habit is how a test suite grows a second idiom. Author rule: before writing an assertion, grep an existing `*.test.tsx` for how that same condition is already asserted. Reviewer rule: a frontend branch is not reviewed until `npx tsc -p tsconfig.json --noEmit` AND `npx vitest run <the new file>` have both been RUN — frontend type/unit failures gate the Vercel deploy, so this merges as a broken build, and a green backend pytest says nothing about it.
- **A `useRef` read INSIDE a `setState(prev => …)` updater is read at RENDER time, not at call time — so any code after the setState that clears that ref (a `detachX()`, a `resetY()`, a cleanup) wins, and the value stored in state is `null` (2026-08-14, owner-reported, embedded feedback list mode):** `addEntry()` stacked a committed feedback entry with `audioBlob: audioBlobRef.current` inside the updater and then called `detachDraftMedia()`, which nulls that ref. Every stacked entry was therefore saved with `audioBlob: null` / `audioUrl: null`, so the narration audio of every item except the live draft was silently dropped at submit — and it survived review because React's eager-state optimisation *does* run the updater synchronously when the fiber has no pending work, so it can appear to work in a hand test and fail under load/StrictMode/concurrent updates. Author rule: read every ref into a `const` BEFORE the `setState` call and close over the const; refs and functional updaters are on different clocks. Reviewer tell: `xRef.current` appearing between `setState(prev =>` and its closing `)`, with any ref-clearing call in the same function. Note unit tests over the pure reducer cannot see this at all — it only shows up in a test that mounts the provider and asserts the POSTed body (`src/contexts/FeedbackFlowContext.test.tsx`).

Author rule: before gating a component, open the endpoint it reads and check the WHERE clause — caller-scoped ⇒ never gate; and NEVER edit a comment that cites an owner spec to fit your change. Reviewer tell: a role-gating diff whose `+` lines outnumber the widgets the spec actually names, or which narrows an "(owner spec)" comment.
- **A "restore my last page" redirect that lives ON the landing route makes that page unreachable — restore ONCE per page load, and never remember a route whose screen lacks the nav that leads back (2026-08-19):** CASE-none, reported by mike.c@grotap.com.
