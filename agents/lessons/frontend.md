- **Never assign `window.name` for per-tab state (2026-07-10):** 88162F used `window.name = 'grotap-win-'+rand` as a window-scope discriminator, but the platform uses `window.name` as the `window.open` TARGET NAME so app tiles refocus instead of stacking (`WorkspaceContext.openApp` names windows by app slug; `ClaudeCodePage` uses `'claude-code-seat'`). Clobbering it made every app open a duplicate window after AI support ran in it. To distinguish a same-tab reload from a `window.open` sessionStorage copy, use a discriminator that does NOT hijack `window.name` (and note plain sessionStorage keys ARE copied by `window.open`). Fix: CASE-20260710-72AF65.
- **A branch that adds a REQUIRED field to a shared TS interface breaks every sibling branch that CONSTRUCTS that type — both pass `tsc` alone, only the COMBINATION fails (2026-07-12):** CASE-20260712-695BAD added `assigned_team_id: string | null` and `location_visibility: LocationVisibility` as non-optional fields to the ranch-plan `Task` interface (`frontend/src/pages/ranch-plan-types.ts`). CASE-20260712-E5E41B (built in parallel against the OLD type) constructs 5 `DEMO_TASKS` object literals of type `Task`; once 695BAD merged, those literals failed `npx tsc --noEmit` with TS2739 (missing the two new required props). Each branch was individually green, so neither agent nor per-branch review caught it — the review gate only saw it at the post-merge combined tsc and had to merge 695BAD solo + route E5E41B's fixtures back (CASE-20260712-E5FX1B). Mitigations: (a) COALESCE a type-defining case with its type-consuming siblings onto ONE branch so the combined tsc runs before sign-off; (b) prefer adding new interface fields as OPTIONAL (`?:`) when existing code/fixtures construct the type, tightening to required only once all constructors are updated; (c) at the gate, always run the FULL combined-tree tsc after merging sibling frontend branches, never trust per-branch green.
- **A static/vanilla form control's submitted `value` must be the backend's exact enum SLUG, not the human-readable display label — the backend does a case-sensitive membership check with NO normalization, so a display-string value = HTTP 422 on every submit and a silently 100%-non-functional form (2026-07-13):** review-gate 2026-07-13 CASE-20260713-7CCF6C built `docs/landing-register/register.html` with four business-category radios whose `value` attrs were the display labels (`Manufacturing`, `Agriculture — Row Crops`, `Re-wholesale`, `Government Agency`). But `backend/app/routers/registration.py` accepts only `VALID_CATEGORIES = {"manufacturing","agriculture_row_crops","re_wholesale","government"}` and rejects anything else with `422 invalid category` (no `.lower()`, no label→slug map). Every submission failed; the 201-success swap never fired. `compileall`/`tsc` are blind to it (static docs file) and even reading the HTML looks fine in isolation — the defect only surfaces by cross-checking the form's `value` set against the backend enum. Gate rule: for any form/select/radio that POSTs to a backend endpoint, grep the target router for the field's allow-list (`VALID_*`/`Enum`/`in {...}`/Pydantic `Literal`) and confirm each control `value` is a member EXACTLY (case + punctuation); keep the label in the visible `<span>`/`<option>` text, put the slug in `value`. Verdict FIX (form's core function 100% broken; not merged — static docs, no gate impact). Fix filed CASE-20260713-7CCFIX.

The branch fixed the 3 tile `data-val`s and the `isSoftware === 'software-development'` check but LEFT `WORK_TYPE_LABELS` keyed on the old short slugs, so the Step-5 review card would render the raw slug `software-development` instead of `Software Development` — a visible regression on a live prospect-facing page. Gate rejected (do not ship a half-rename to a customer page) and filed a fix that aligns ALL sites incl. the label map. Rule: when renaming/aligning an enum value, grep the FILE for the OLD value AND every consumer (submit payload, comparisons, label/format maps) and update them together; verify the FE-sent value byte-matches the backend's canonical slug (grep the router contract), not just internal self-consistency. A branch that updates the value but not its label map is INCOMPLETE. Same root cause when the new field is a PRESENTATION OVERRIDE rather than a renamed slug (2026-08-31, review-gate, CASE-20260831-624A8A MERGED -> CASE-20260831-RG624A): v017 added `print_cloud.printers.display_name` (NULL = fall back to `name`) and the branch rendered `display_name || name` at only the two sites the case sentence named — the Printers page name column and the print-page picker — leaving the three Label Designer pickers, the TPCL warning, CameraDrawer's heading and default nickname, the raw-console heading and both flash messages still showing the raw OS queue name, so an operator's rename reads as if it did not take. An override field is not shipped until EVERY site that renders the overridden field resolves it; grep the surface for `.name` (or whatever field it overrides) and convert each site, and prefer ONE `printerLabel(p)`-style resolver over repeating the `||` at nine call sites. Two carve-outs the grep must not steamroll: a site where the raw field is an IDENTITY (an `<option>`'s `key=`/`value=`, a conflict-target, a join key) keeps the raw field and changes only its visible TEXT, and a table column whose Cell renders the override must move its `accessorKey` to an `accessorFn` returning the same expression, or MRT sorts and global-filters on the value the user can no longer see.
- **Before building a NEW frontend page/route, grep master for a component ALREADY mounted at that route path — a second component for an existing route is a structural collision, not a feature (2026-07-19, review-gate batch24 SKIP, CASE-20260719-5134A4 → CASE-20260719-513AFX):** the case "add a Security tab at /platform-resources/security" was built as a whole new `PlatformSecurityPage.tsx` (465 lines) that re-pointed `App.tsx`'s existing `/platform-resources/security` Route to it — but master ALREADY renders a working 353-line `PlatformResourcesSecurityPage.tsx` at that exact path. Merging would orphan the live page (only one component renders per route). Two-line `App.tsx` conflict on the import + the Route element is the tell. Gate rule: for any "add page/tab/screen at path P" case, `grep -n "path=\"P\"" frontend/src/App.tsx` on master FIRST; if a Route already exists, the case is SUPERSEDED — fold the genuinely-new bits (extra cards/queries) into the EXISTING component via a fix case, never ship a parallel page. (Reviewer diffing `master...branch` can miss this because the branch only shows its own new file as an add; the collision only surfaces at merge-tree against the master Route table.) **Inverse failure, same grep (2026-09-07, found while browser-verifying the pipeline board):** a Route can EXIST and still be dead. `App.tsx:609` and `App.tsx:617` map both `/pipeline` and `/pipeline/:caseId` to the same `<PipelinePage />`, and `PipelinePage.tsx` never calls `useParams` — so a per-case URL silently renders the unfiltered list (both responses byte-identical at 18,579 chars) and no case link anywhere reaches its case. So the route-table grep answers only half the question: after confirming a path is mapped, confirm the component READS the param it was given (`useParams`/`useSearchParams`), or the route is decorative. Corollary for anyone writing an e2e against a detail URL: a detail page that is really a list page will satisfy almost any page-level assertion.
- **A "ref proxy so stable callbacks read current values" block (`const xRef = useRef(x); xRef.current = x;`) placed ABOVE the `const x = useCallback(...)`/`useState` it mirrors fails tsc TS2448/TS2454 "used before its declaration" — block-scoped consts have a temporal dead zone (2026-07-22, review-gate, CASE-20260722-051471 REJECTED → 051F01):** the setup.tsx auto-connect branch inserted `connectTcpRef` referencing `connectTcp` ~120 lines before its later `useCallback` declaration. `strict:true` does NOT flag this via unused-locals — only a real typecheck catches it, and scantap mobile is outside the standard gates. - **An Android app reaching a device on a SECONDARY interface (USB-Ethernet/eth0, USB-tether, a second WiFi) must bind its socket to that interface's `android.net.Network` — Android per-app routing is by network fwmark, NOT source IP, so detecting the NIC and/or setting `localAddress` is NOT enough; while WiFi is the validated default network every unbound socket egresses via WiFi and times out (2026-07-23, bench-verified, CASE-20260723-E70B1D):** ScanTap's CS463 LLRP transport + Connection Doctor opened `react-native-tcp-socket` to `192.168.25.160:5084` with no Network binding. The tablet had WiFi (validated → default) AND eth0 (192.168.25.100, NOT validated because the reader gives no internet, so Android never promotes it to default). WiFi's routing table has no route to 192.168.25.0/24, so every connect timed out — even though `ping -I eth0` worked and the reader's LLRP was live (pushes a 32-byte READER_EVENT_NOTIFICATION, msg type 63, on connect). The `EthernetNetworking` native module only DETECTED the NIC (`listEthernetInterfaces`/`isEthernetAvailable`); it never bound. Proof: dropping WiFi makes eth0 the default and the identical socket reaches the reader. Fix pattern: capture the `Network` from the `ConnectivityManager.NetworkCallback.onAvailable(Network)`, and `cm.bindProcessToNetwork(ethNet)` before opening the socket (rebind on every reconnect to survive an eth0 flap — the USB-Ethernet adapter RE-ENUMERATES when a charger is plugged into a pass-through jack), `bindProcessToNetwork(null)` on stop so the app regains internet for API sync (local-first capture to SQLite makes the no-internet scan window fine). Do NOT rely on Android making eth0 the default — a reader/appliance is not an internet gateway, so its network never validates. `tsc`/`expo config` are BLIND to this (pure runtime routing); only a real device with WiFi UP exposes it. Author/reviewer rule: any mobile feature that talks to hardware on a non-default interface must bind to that `Network`, and must be bench-tested with the phone's normal WiFi still connected — testing with WiFi off hides the bug.
- **A frontend `window.open()` / top-level navigation to a BACKEND-served route (report viewer, file download, SSE, anything under the API) MUST prefix the API origin (`${api.defaults.baseURL ?? The SPA and API are DIFFERENT origins (VITE_API_URL is a full URL), so the browser opened `app-origin/reports/view/...` — no such route, and the cookie set on the API origin is never sent → platform-kind report cards stay dead, the exact symptom the case was filed to fix. The sibling `openPlatformReport` in the SAME file opens the full API-origin URL and the removed `/serve` code also prefixed baseURL; grep confirms ZERO relative `window.open(`/...`)` backend navigations exist on master — every other one prefixes the base. Reviewer tell: `window.open(` / `location.href =` / anchor `href` pointing at a backend route with a leading `/` and no `baseURL`/`VITE_API_URL` = cross-origin dead link + dropped cookie; a green tsc proves nothing.
- **A cancel/supersede guard (boolean flag OR monotonic generation token) must guard every WRITE in the stale-bail path by IDENTITY — `myRun !== current` gates only WHETHER you bail, not WHAT you may clobber; an unconditional `someRef.current = null` / `setX(null)` in that path wipes the NEWER run's live handle, so the resource it owned is never released (2026-07-26, review-gate, CASE-20260726-F4902E merged-with-defect → CASE-20260726-SCANGEN):** scantap `scan.tsx` correctly replaced `preflightCancelledRef` with `preflightRunRef` generation counter, but both stale-bail sites still did bare `readerRef.current = null; setReaderState(null)`. Repro: preflight A → Cancel → Start again within `READER_CONNECT_TIMEOUT_MS` (5s); run B sets `readerRef.current = svcB`, then A's connect promise times out, sees itself stale, and nulls the ref pointing at *svcB* — so `captureScans()`/unmount read null, never call `svc.stop()`/`clearActiveReader(svc)`, and the CS463's single LLRP slot leaks (the exact CLOSE_WAIT wedge `activeReader.ts` exists to prevent). The correct pattern was already in the same codebase: `clearActiveReader(svc)` is written `if (_active === svc) _active = null` — copy that guard (`if (readerRef.current === svc) ...`) to every ref/state write a superseded run performs. Corollary: also generation-guard the ASYNC CALLBACK, not just post-`await` steps — an abandoned run's `svc.start(...)` status callback kept calling `setReaderState(state)`, which became user-visible the moment a sibling case rendered `readerState` on the idle screen (state a stale run writes is harmless only until someone renders it). Author rule: when you introduce a generation token, list every write the losing run can still perform and identity-guard each one. Reviewer tell: a stale-bail block whose condition is generation-checked but whose body assigns to shared refs/state unconditionally — and note `tsc` plus both siblings' own diffs are BLIND to it (git auto-merged these two file-sharing siblings with NO conflict; verify merged SEMANTICS, not the absence of conflict markers). **Gate disposition rule for the LATER siblings of such a group (2026-07-26, same 4-way fan-out onto `scan.tsx`: 4AF604+F4902E landed, stranding 0C079F and AC011F on the pre-token base):** when the token/primitive lands first, a straggler branch does not merely conflict — it still SPEAKS THE REPLACED PRIMITIVE, so force-resolving its conflict silently DELETES the protection the earlier sibling added. Triage by what the straggler's hunk does to that primitive: hunks that are ADDITIVE around it are salvageable by union resolution at the gate (0C079F wrapped `beginBatch`→`startScanning(svc?)`; kept master's post-await stale guard, gates green, MERGED); hunks that DELETE OR RENAME it must be REJECTED to a rebase fix case, never hand-woven (AC011F still wrote `preflightCancelledRef.current = true` — a symbol master no longer has → TS2304 *and*, since it never bumps the generation, the exact LLRP-slot leak faf1d7fc was landed to fix; its conflict also wanted to drop `const myRun = ++preflightRunRef.current`). Corollary for the fix-case body: spell out the primitive's OLD and NEW names and which sibling now owns the flow, or the rebase agent re-derives the stale version. Also: `setCheckingConn` vs `checkingConn` — a case-SENSITIVE grep for a `useState` name misses every `setX` call site, so "dead state" can look already-deleted when three writes remain. **Scope limit of the whole pattern — a generation token defends against SUPERSESSION, never against RE-ENTRY, so a control whose `onPress`/`onClick` stays MOUNTED across its own `await` still needs a separate in-flight guard (2026-07-26, review-gate, CASE-20260726-SCANCFM merged → CASE-20260726-SCNDBL):** the rebased 'Confirm — Start' button is `disabled={readerState !== 'connected'}` and awaits `startScanning(svc)` → `beginBatch` → `await createBatch(...)` — a network round trip — before `setPhase('scanning')` finally unmounts the confirming screen. `readerState` does not change during that window, so the button stays enabled and tappable; both taps capture the SAME `myRun` (nothing bumps the counter on a tap), both pass the post-await stale check, and beginBatch runs twice → two `createBatch` rows, `batchIdRef`/`setBatchId` overwritten by the second, and batch #1 left open forever because `captureScans()`/`handleStartAnotherBatch()` only ever finalize `batchIdRef.current`. Contrast the sibling 'Start Anyway' button in the same file, which is safe only incidentally: `setConnWarning(null)` unmounts its modal SYNCHRONOUSLY before the await. Author rule: when converting an auto-advancing flow into a user-confirmed one, whatever the await used to be hidden behind is now a visible re-entrancy window — add `if (busyRef.current) return; busyRef.current = true` plus a `finally` reset, reflect it in `disabled=`, and clear it on the cancel/back path. Reviewer tell: an `async` handler with an `await` whose only `disabled` condition is state that CANNOT change during that await.
- **A route rendered OUTSIDE `AppFrame` has no `MantineProvider` ancestor, so every Mantine/MRT surface on it silently falls back to the packaged `colorScheme:'light'` and paints `theme.white` UNDER the app's dark design tokens — white text on a white Paper, invisible until you highlight it; and the `var(--text, #374151)` fallback that makes it LOOK safe never fires, because the variable IS defined (2026-07-26, review-gate, case bfda86cc merged clean; same defect class as acba6557 scantap Inventory Items):** `ThemeContext.tsx` defaults to `'dark'` and `index.css` sets `:root[data-theme="dark"] { --text:#fff; --bg-card:#111 }`, so a cell styled `color: var(--text, #374151)` with NO `background` resolves to #fff over Mantine's white Paper. The diagnostic tell is ASYMMETRY: cells with hardcoded colours (chips, buttons) stay visible while plain-text columns vanish. Author rule for any MRT/Mantine table: set `background` beside every `color` (`mantineTableBodyCellProps` AND `mantinePaperProps` — the cell background alone leaves the white Paper showing through the loading overlay, the gutters and `renderDetailPanel`), and prefer fixing the CLASS by wrapping the app's routes in `<MantineProvider theme={{ colorScheme: theme }} withNormalizeCSS={false} withGlobalStyles={false}>` driven by `useTheme()` (mirrors `AppFrame.tsx:117`, but theme-DRIVEN — never copy the other pages' hardcoded dark values, they break the light toggle). Mantine here is v6, where `theme={{ colorScheme }}` + those two `with*` props are correct; they do not exist in v7 — check `frontend/package.json` before copying a provider snippet. Reviewer tell: `grep -n 'path="/<app>' frontend/src/App.tsx` — routes wrapped in `PrivateRoute` only never pass through `AppFrame`, and `tsc` is blind to all of it. **Corollary on the regression test such a case commissions (→ CASE-20260726-PCGRDT):** "assert the text is not invisible" means CONTRAST between `getComputedStyle(td).color` and `.backgroundColor` — a test that reads only the background and asserts it is dark encodes the one historical symptom, still passes for dark-on-dark, and (because a `match(/\d+/g)`-style luminance helper scores `rgba(0,0,0,0)` as 0) passes for a transparent cell too. Any new visual regression test must be shown to FAIL with the fix reverted; playwright is in NO CI gate here, so nothing else will ever catch a test that cannot fail. **Same defect class, AG Grid variant — the vendor theme, not the provider, is the thing that must follow `data-theme` (2026-07-28, `d1b791ec`, owner-reported "all Pipeline Cases titles are blank"):** `lib/agGrid.ts` built `grotapGridTheme` as bare `themeQuartz.withParams({accentColor,fontFamily,headerFontWeight})` — AG Grid's Theming API defaults to a WHITE surface and has no idea `<html data-theme="dark">` exists, so EVERY grid on the platform painted `var(--text)`=#fff cells on #fff. Same asymmetry tell as above (badges/chips with hardcoded colours survived; App and Title/Description vanished), and same false lead: the reporter and I both read it as missing data, but `case_data.title` was populated on all 200 rows and `getCaseDescription()`'s chain ends in `'—'`, so **a blank cell was IMPOSSIBLE from that code path — a fallback chain that cannot return empty is proof the bug is PAINT, not data.** Fix is `themeQuartz.withParams({backgroundColor,foregroundColor,borderColor,chromeBackgroundColor,menuBackgroundColor,headerTextColor,browserColorScheme:'dark'}, 'dark')` plus `document.documentElement.setAttribute('data-ag-theme-mode', theme)` in `ThemeContext` — AG Grid reads that attribute off ANY ancestor, so one line covers every grid; params passed with no mode arg stay the light baseline. **Corollary, and the reason a per-screen light override CANNOT be done with that attribute (2026-09-08, `d14d8cc8`, owner-reported "ScanTap screens should be white like Dead Tags"):** the mode CSS is emitted as `:where(html[data-ag-theme-mode="dark"],body[...],.ag-theme-mode[...="dark"]) .ag-theme-params-N` — a DESCENDANT rule keyed on any ancestor in dark mode, emitted AFTER the default block — and light is the default mode, so it has no block of its own. `data-ag-theme-mode="light"` + `class="ag-theme-mode"` on a wrapper therefore matches NOTHING and changes nothing while looking exactly right in the DOM (prod showed both attributes live on the wrapper and the grid still computing `rgb(17,17,17)`). To pin one screen light regardless of the shell, build a second theme instance carrying the light values in BOTH the default and the `'dark'` mode and select it per grid (`grotapGridThemeLight` + DataGrid's `forceLightTheme`); declaring a key in the default mode also DROPS it from every other mode (`Theme._getModeParams`), so the vendor's own dark scheme cannot reintroduce it. Verify a theme claim by measuring `getComputedStyle('.ag-root-wrapper').backgroundColor` with `<html data-ag-theme-mode="dark">` still set — never by reading the attribute you just wrote. Author rule: any vendor component with its own theming layer (AG Grid, Mantine, MRT) needs an explicit bridge to `data-theme` — inheriting CSS vars is not inheriting a theme. **Reviewer/verifier tell, and the reason automation missed this for weeks: `textContent` SEES INVISIBLE TEXT, so every Playwright assertion on cell text passed while the screen was blank to a human.** Verify contrast instead — `getComputedStyle(leaf).color` vs the COMPOSITED ancestor background (walk up blending translucent layers; AG Grid rows/cells are `rgba(0,0,0,0)`, so reading the cell's own `backgroundColor` scores 0 and passes everything), and flag <3:1. That audit over all 15 grid routes is what proved the fix: 12 grids, 2,600 cells, 0 invisible. Also: this cannot be verified on a local preview build — the prod API CORS-rejects `localhost`, so the grid renders zero rows; the theme swap is provable locally by grid background colour only, row-level contrast must be measured against prod after deploy. **Two more ways a page-level assertion lies, both from 2026-09-07:** (a) an ABSENCE assertion (`expect(body).not.toContain(x)`) is only as wide as what the page RENDERED — the HI board requests `limit=50` of 113 pending holds and truncates each card behind "Show more", so "the stale hold is gone" passed while 63 holds were never in the DOM; prove a negative against the API's full paged listing, never against `body.innerText`. (b) a status word asserted at page level can come from the FILTER UI rather than the data — `toContain('closed')` matches the `<option value="closed">` in the Status dropdown, and a row's own `innerText` contains every option of its status `<select>` too, so scope status assertions to a cell or read them from the API and keep row-scoped text assertions for plain-text columns like priority. Always pair a positive row assertion with a negative control (a marker that must NOT match), or a broken locator reads as a pass. Version tell while writing those locators: this app is on `ag-grid-community` v36, which emits NO `.ag-body-viewport` and no `.ag-viewport`, and nothing under `.ag-root-wrapper` scrolls (the PAGE scrolls) — a virtualization scroll-loop copied from older AG Grid docs just times out.
- **A live-prod e2e spec dropped into `frontend/e2e/` breaks EVERY other playwright run unless it is env-guarded, because `testDir: './e2e'` collects it for everyone: anything read at MODULE scope (`fs.readFileSync(process.env.X)`, a required token) throws during collection, before a single test starts, so the failure is not "my spec skipped" but "the whole suite aborted" (2026-07-27, commit 9a064b82, caught by the pre-commit Codex pass — `tsc` is blind to it and playwright is in no CI gate here).** Pattern to copy is `e2e/ai-support-live.spec.ts`: file-level `test.skip(() => !process.env.<FLAG>, '...')`, every env read moved INSIDE the test body, and screenshot paths repo-relative (`e2e/screenshots/...`) — a hardcoded `C:/1Claude/...` only resolves on one machine. That single missing `**/grid-templates*` mock was blanking 5 of 8 tests in `manorview-acceptance.spec.ts`, each failing with an unrelated-looking "grid has no rows".
