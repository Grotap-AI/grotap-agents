- **An OPERATOR RUNBOOK or SETUP-HOLD case documents actions a human will literally copy-paste during an incident/setup — every path, port, URL, systemd directive, and rm-vs-mv MUST be grepped against the real script/service/router before merge; a "plausible-sounding" instruction is a defect, not docs polish (2026-07-15):** review-gate 2026-07-15 batch13 rejected TWO such cases in one batch. CASE-20260715-31654C (`scripts/free_stream_gmail_hold.sql`) told a human to register GCP redirect URI `https://<domain>/api/loop-engine/oauth/gmail/callback`, but the backend builds `{api_base_url}/loop-engine/oauth/google/callback` (`loop_engine.py:617 _make_redirect_uri`; router mounted with NO `/api` prefix at `main.py` `include_router(loop_engine_router)`; segment is `google` not `gmail`) → copying it fails GCP OAuth with `redirect_uri_mismatch`. CASE-20260715-E5CD3A (JUMPBOX §8.6 wedged-session runbook) said the loop is caused by `Restart=on-failure` (real unit is `Restart=always`+`RestartSec=5`, and on-failure wouldn't even restart a clean exit — self-contradictory), attributed the rapid-exit self-heal to "Claude Code v2.1.200+" (it's OUR `claude-remote-wrapper.sh` §4, fires at ≥2 exits under `RAPID_EXIT_SECS`=30s), and told operators to `rm -rf ~/.claude/projects/<proj>/.claude/resume-state/` — a path that DOESN'T EXIST (real dir is the single `~/.claude/projects/-home-<user>-workspace-grotap`, and the wrapper deliberately `mv`s it to a backup, NEVER `rm`s). `compileall`/`tsc`/`vitest` are all blind to prose. The rest of a wrong doc can be perfectly good (31654C's `human_holds` INSERT, ON CONFLICT index match, and enable-SQL were all correct) — one wrong operational line still blocks, because that's the line a human runs. RECURRENCE 2026-07-26 (review-gate rg12, CASE-20260726-7E7F42 merged-by-orch WITH fix case CASE-20260726-ORHOLD) — **a script's own runtime `alert_human` string IS operator runbook text, and it must stay GENERIC + ACTIONABLE: never bake the root cause of one past incident into it, and never hardcode a value the same string already interpolates.** The case (correctly) removed a stale "add agent-06 pubkey to grotap-cobrowse-01:~/.ssh/authorized_keys" instruction from `scripts/backup/weekly-openreplay.sh`, but replaced it with "Ensure supportagents.grotap.com DNS resolves and confirm /home/agent/.ssh/grotap_agents is the fleet identity file (no operator action needed — script fix only)" — literal host + literal key path in a message whose FIRST sentence interpolates `${OR_SSH_USER}@${OR_HOST}` with key `${OR_SSH_KEY}`, both documented three lines above as "override via env", so under any override the alert names a host that did not fail. Worse, that text fires on EVERY future SSH failure at `high` priority: a human-intervention hold that pre-emptively tells the operator to stand down ("no operator action needed") is an anti-signal the day the fleet key is rotated or the host is rebuilt again. Rule: incident narrative belongs in the past-tense report; the live alert gets the interpolated variables plus what to CHECK. Second half of the same defect — **correcting stale operator text must not overshoot into MISQUOTING the stored record: the hold is a row you can read, so read it.** The branch rewrote `Reports/backup-audit-2026-07-26.md` to state the hold said weekly-openreplay "could not SSH to `root@supportagents.grotap.com`", while `human_holds.task_id='backup-alert-weekly-openreplay-2026-07-26'` still says `ubuntu@grotap-cobrowse-01` — and root@supportagents.grotap.com is the combination that WORKS (verified from agent-06: `ssh -i /home/agent/.ssh/grotap_agents -o BatchMode=yes root@supportagents.grotap.com true` → rc 0, remote hostname `grotap-cobrowse-01`; `supportagents.grotap.com` resolves to the previously-verified `5.161.189.143`, so the `OR_HOST` default change itself was sound). The report now describes a failure that never happened and erases the real root cause (stale host/user config, already fixed by CASE-20260726-D62936), so the next reader chases DNS instead of reading the audit trail. Gate rule: when a docs branch restates what an alert/hold SAID, `SELECT description FROM human_holds WHERE task_id=…` and require a quote; the corrected procedure goes in a separate sentence as the RESOLUTION, never retrofitted into the incident. RECURRENCE 2026-07-26 #2 (review-gate rg13, CASE-20260726-C0CA51 merged-by-orch WITH fix case CASE-20260726-ORMNIO) — **"requires a one-time operator step" is a DIAGNOSIS, not an excuse: before writing an external/human dependency into a script comment or an alert, SSH the box and prove the thing is actually missing — a NAME MISMATCH IN OUR OWN REPO is the likelier cause and it is ours to fix.** An end-to-end test case ran `scripts/backup/weekly-openreplay.sh`, correctly verified the Postgres (45 KB) + ClickHouse (`default`/`experimental`/`product_analytics`) uploads, then explained the failed MinIO step away with `# MinIO mirror requires one-time operator step: mc alias set minio <url> on cobrowse-01 (non-fatal)`. Nothing was missing: `mc` has been installed at `/usr/local/bin/mc` since 2026-07-07 and the alias EXISTS — it is named **`orminio`** (`mc ls orminio/` lists the real buckets `records/ sessions-assets/ sessions-mobile-assets/ spots/ mobs/ sourcemaps/`, URL `http://10.43.127.248:9000` = svc `minio` in ns `db`), while the script defaults `OR_MINIO_ALIAS:=minio`. So a one-word wrong default in the repo was published as an operator's homework, and the same file's setup comment still tells that operator to point mc at `minio.openreplay.svc.cluster.local:9000` — the wrong namespace, contradicting the header comment three lines up that says "pods live in 'db' namespace (not 'openreplay')". Consequence: step 3 fails on EVERY weekly run (`platform-backups` prefix `openreplay/minio/` = **0 objects** — OpenReplay session recordings have NEVER been backed up) and fires a `high` hold each time whose text sends the operator to check an alias and credentials that are both fine. Second, generalizable half — **a CLI that takes a bare `remote/` argument can silently REINTERPRET an unknown remote as a LOCAL PATH, so a failure there is not evidence about credentials or setup:** `mc mirror "minio/"` degraded to `/root/minio` ("Requested path `/root/minio` not found"), which is exactly why this hid for weeks — assert the alias/remote resolves (`mc alias ls "$ALIAS"`) BEFORE using it, and make the alert name the actual unresolved alias instead of guessing. Gate rule: for a test/verification case whose whole deliverable is a comment asserting "it works now", re-run the decisive check yourself — list the destination prefix and require a non-zero object count; a step the branch labels `(non-fatal)` is the one to probe, because non-fatal + silent is how a permanent backup gap survives a passing end-to-end test. Third variant, same root cause — **a docs-only branch whose deliverable is a RECORD of a change made by hand in an EXTERNAL admin panel is a CLAIM, not a change: read the live system back through its `backend/app/providers/` wrapper before merging, because merging enshrines a false audit record that is worse than no record at all (2026-07-30):** review-gate rejected CASE-20260730-B8FD97, which added only `docs/11-devops/headwind-mdm-config.md` asserting `com.grotap.scantap` had been added to Headwind config 1 'Common - Minimal' with `selected=true, action=1` and the APK URL moved to `scan-m-1.1.4.apk`. Do NOT conclude 'no code changed, nothing to review' and do NOT accept the seat can't reach it: the credentials are in Doppler (`MDM_*`) and the read is one provider call. Two traps when you do check: an object's *global* list endpoint may return the join fields (`selected`/`action`/`configurations`) UNPOPULATED for every row — calibrate against a record you know is linked before reading an empty result as absence — and the parent `GET .../configurations/{id}` returned `applications: []` for ALL THREE configs, so **an empty collection on one endpoint is not evidence; find the endpoint that hydrates the link and quote its response.** Same fix shape as the runbook cases: reject, file a fix case that performs the change through the provider (never a second by-hand edit), requires re-reading the live state afterwards, and only then lands the doc with the numbers verification actually returned. **Correction, 2026-07-30 — "read it back through the provider" is NOT sufficient and this line's own advice produced the next failure:** the replacement case CASE-20260730-A31F70 did exactly that, and audited the wrong Headwind panel again, because `get_headwind_provider()` takes `panel: str = "self"` and `self` is the demo `mdm.grotap.com`. Read it back through the DEVICE's own feed, which cannot be aimed at the wrong instance (`curl https://srv.h-mdm.com/rest/public/sync/configuration/<device>`, device number lowercase), and grep the provider call sites for an explicitly-passed panel/env/region argument — a defaulted one is unverified. - **Never pass a task prompt / large generated text as a single exec ARGUMENT — the kernel caps one argv string at MAX_ARG_STRLEN (~128 KiB), so `claude ... -- "$FULL_PROMPT"` dies instantly with E2BIG ("Argument list too long") the moment a case's spec + clarifications outgrow it; feed big payloads via stdin or a file (2026-07-21):** `agents/dispatch.sh`'s generated `run-task-*.sh` runner passed the whole prompt as one argv; the two biggest ScanTap P1 cases (CASE-20260721-D2ADCD, CASE-20260720-F317AE) each failed in <5s on the reconciler re-drive path (`/usr/bin/claude: Argument list too long` → "no commits produced"), while the SAME cases succeeded via orchestrator-run.sh, which streams the prompt from a payload file over stdin. The failure masquerades as a broken server: it re-drove to agent-04 both times only because agent-04 is FIRST in reconcile_dispatch.py's SERVERS list — the box was healthy. Fix pattern: `printf '%s' "$FULL_PROMPT" | claude --print ...` (printf is a bash builtin, no exec limit; `--print` reads stdin when no positional prompt). Fix case CASE-20260721-6CF676. Diagnosis rule: a dispatch that fails in seconds with no branch and no runner log → read `/home/agent/logs/task-<id>.log` on the box BEFORE blaming the server; "same case, same box, different dispatch path succeeded" means the PATH is the defect. Author rule: any script that execs a CLI with generated/user-sized content (prompts, diffs, JSON payloads) must pipe it via stdin or `--file`, never interpolate it into argv.
- **A case must NEVER sit in `awaiting_human` with zero open `human_holds` rows — that state is INVISIBLE to the review gate, the assign loop, AND the HI surfacing UI, so it strands forever until a manual sweep (2026-07-24, owner-proxy sweep: 5 cases stranded this way in ONE morning — 91B29E, D90FC2, B1FB36, 8EAE3D, 6651BE; fix case CASE-20260724-HOLDFX):** agents/orchestrator flipped executing cases to `awaiting_human` without filing a hold; the awaiting-human-self-heal auto-recovered only ONE (RPTVFX). Agent rule: when parking a case for a human, the hold INSERT and the status UPDATE are one atomic action — if the hold write fails, do not park the case; keep it executing or fail it. Sweep rule: any `awaiting_human` case with no open hold and no active dispatch row → check whether the deliverable is ALREADY ON MASTER first (three of the five were already shipped: RPTVFX=ReportsPage.tsx:1447 apiBase fix, B1FB36=RO_REPORT_N 50, 3199D6=mdm.py fully merged); if shipped, close done/already_shipped; else requeue to plan_approved with a metadata note narrowing the remaining scope. Also from the same sweep: a case filed with the WRONG `org_id` (tenant UUID or literal 'grotap' instead of the WorkOS `org_…` id) never matches the assign loop's per-org query and sits `plan_approved` forever unclaimed (QMBFIX + CD6FIX, 24h invisible) — filer rule: `org_id` on pipeline_cases must be the WorkOS org id the `pipeline_automation` row carries, never the tenant UUID.
- **An audit that concludes a vendor feature is OFF must query the VENDOR's own API, not just the S3/AWS-compatible one — "the compatible API returns NotFound" means the compatible API doesn't model the feature, NOT that the feature is disabled (2026-07-26, CASE-20260726-EF0ED4 REJECTED → CASE-20260726-WSBLCK):** the audit ran only `aws s3api get-object-lock-configuration` against Wasabi, got `ObjectLockConfigurationNotFoundError` on `platform-backups`, and published "Object Lock: NO / lock retention: 0 days / prune vs lock: no mismatch / **Risk: None**" — then rewrote the `scripts/backup/lib.sh` heartbeat() comment to assert the bucket has NO object lock, deleting a TRUE warning. The bucket is in fact immutable for 30 days via Wasabi's PROPRIETARY bucket Compliance feature, which lives on a non-S3 sub-resource and is invisible to `GetObjectLockConfiguration`: `GET https://s3.us-west-1.wasabisys.com/platform-backups?compliance` (SigV4; Wasabi 400s without an explicit `X-Amz-Content-Sha256` header) returns `<Status>enabled</Status><RetentionDays>30</RetentionDays><DeleteAfterRetention>false</DeleteAfterRetention>`. Corroborating tell the audit had in hand and explained away: the sibling bucket `grotapsourcecode` answers that same URL with `409 ComplianceNotAllowed — "not allowed after object locking is enabled"`, i.e. the two immutability mechanisms are MUTUALLY EXCLUSIVE, so one bucket showing S3-lock-enabled and the other showing S3-lock-absent is the signature of the other mechanism being in play, not of "no protection". Author rule: an audit whose deliverable is a NEGATIVE finding ("not enabled", "no retention", "risk none") owes a second, independent probe before it may say so — for object immutability check BOTH `GetObjectLockConfiguration` AND `?compliance`; a bare `NotFound` from one API is never sufficient evidence of absence. Gate rule: re-run a rejected/asserted audit's decisive query yourself READ-ONLY (boto3 + `SigV4Auth` is enough, ~15 lines, no `aws` CLI needed) — never merge a doc or a code COMMENT whose factual claim you have not independently reproduced, because a comment that says "no lock here" is what licenses the next agent to delete the dated-key workaround that is the only thing keeping writes succeeding.
- **Hand-running a scheduled job OUT of its slot can MANUFACTURE a failure that is not happening in production — check the job's SIDE EFFECTS before reporting an outage (2026-07-26, CASE-20260726-0655D3 merged, false side-finding corrected by CASE-20260726-WSBLCK):** a root-cron ownership diagnostic re-ran `daily-neon.sh` and `weekly-all.sh` by hand at 18:04, both died with `AccessDenied: object protected by object lock`, and the report concluded "backups have been silently failing (Human Intervention holds are being filed)". They are not: the 00:00 cron had ALREADY written that day's dated key, and the bucket's 30-day Wasabi Compliance retention forbids overwriting it — the manual re-run collided with its own successful scheduled run. Listing the bucket proved health in one query: `platform-backups/neon/daily/` holds 12 objects on every date 2026-07-19..07-26, each landing 00:01–00:02 UTC, sizes growing 59.7 MB → 85.9 MB. Author rule: a job that is idempotent-per-DAY (dated keys, `ON CONFLICT`, once-per-window guards) is NOT safe to re-run for diagnosis inside the same window; scope a manual re-run to a throwaway prefix/date, or read the artifacts instead of re-executing. Reporter rule: never escalate "X is broken" from a hand-run exit code alone — verify the SIDE EFFECT the schedule is supposed to produce (list the objects / count the rows / read the last-success stamp) and put that evidence in the report; a fleet-wide "backups are down" claim that is wrong burns a P1 and teaches the next reader to distrust the true findings in the same doc.

- **An audit whose deliverable IS live host state must be produced by RUNNING the command on the target host — a repo-derived audit that reports `crontab -l` as EMPTY is not a negative finding, it is a finding from the wrong machine, and everything built on it inherits the hole (2026-07-30, review-gate, CASE-20260730-81AF4E merged by the orchestrator → CASE-20260730-CRONAU):** the merged `docs/cron/cron-audit-CASE-20260730-81AF4E.md` opens with "`crontab -l` (agent user) | **EMPTY** — no user crontab" and concludes "no scheduled job on this host touches /home/agent/grotap-platform". On grotap-agent-06 that crontab has FOUR entries, and TWO of them run git against that exact tree: `*/15 * * * * review-gate-cron.sh` (which does `git fetch`, `git checkout master`, and **`git reset --hard origin/master`** on `$AGENT_HOME/grotap-platform`, lines 70-72 and again at 120, under `$AGENT_HOME/.review-gate.lock`) and `17 4 * * * git-prune-janitor.sh` (`git fetch origin --prune` on the same tree, lines 21-27, with **no lock at all**). Neither appears in the manifest or the collision matrix, so the doc's summary — "the only git-mutating operations … are git fetch, git worktree add, git branch -D, git worktree remove. All paths that perform these operations share `$HOME/.grotap-platform.git.lock`" — is false in both halves: the most destructive command on the box runs every 15 minutes under a DIFFERENT lock than dispatch uses, which is precisely the unguarded collision the case existed to find. Root cause worth generalising: **the repo does not describe the deployment that actually runs.** The live agent-uid crons execute `/home/agent/automation/pipeline_failure_monitor.py` and `deploy_freshness_watchdog.py` — separate copies OUTSIDE the checkout, no flock, logging to `/home/agent/logs/` — while the repo's own docstrings describe a root-crontab deployment (flock + `reconciler-venv` + `/var/log/grotap/*.log`) that has apparently never run here (`/var/log/grotap/` does not exist), at a schedule that is also wrong (`*/10`, not the documented `*/5`), from a file that has DIVERGED from its in-repo twin (the repo copy logs RSS; the live one does not). So two sibling cases mis-fired off the same bad map: CASE-20260730-7E51A8 was told to flock those two named jobs and instead flocked a weekly ROOT job in docs/installer text, and CASE-20260730-95978E's `install-monitoring-cron.sh` writes a MARKED block of `systemd-run --scope -p MemoryMax=400M` entries that will not replace the existing UNMARKED agent-uid ones — so both copies stay scheduled, `flock -n` lets whichever wins the lock decide whether that run is capped, and the memory ceiling applies about half the time. Author rule: for any cron/systemd/host-state audit, paste the literal `crontab -l` (and `sudo crontab -l`, or record explicitly that root was unreadable from this seat — the agent seat has no sudo password) from the NAMED host into the doc, then reconcile it against the repo; where they disagree, the divergence IS the deliverable. Grep `$AGENT_HOME`-relative scripts in the SIBLING repo (`grotap-agents/agents/scripts/*.sh`) too — a job that mutates the platform tree does not have to live in the platform repo. Gate rule: when a docs/audit branch asserts a negative about live state ("empty", "none", "no job does X"), reproduce the command yourself before merging; a wrong negative in a doc labelled "the foundation for all subsequent fixes" is worse than no doc, because the follow-on cases stop looking. **The FIX side of the same trap, and it bites even when the audit was right (2026-07-30, review-gate rg3, CASE-20260730-CBF15D REJECTED → CASE-20260730-CBFFIX):** the case correctly diagnosed that the review gate operates on the shared `~/grotap-platform` tree, and the branch correctly parameterised `agents/scripts/review-gate-cron.sh`... in the grotap-PLATFORM repo. `crontab -l` on agent-06 runs `/home/agent/grotap-agents/agents/scripts/review-gate-cron.sh` — a DIVERGED copy of the same filename (6545 bytes, 2026-07-26, vs 11377 on platform master) that still hardcodes `PLATFORM_REPO="$AGENT_HOME/grotap-platform"`. The branch would have merged green, changed the file its diff named, and changed nothing about the running gate. Two identically-named scripts in two repos is not a hypothetical: it is the current state of this box. Author rule: before editing ANY script that a scheduler invokes, resolve the path the SCHEDULER names (`crontab -l`, the unit file) and edit THAT file — then `diff` it against every same-named copy in the other repo and either delete the loser or state in a header comment which one is authoritative. Reviewer rule: for a branch whose value is "the deployed script now behaves differently", the merge check is not the diff — it is `crontab -l` plus reading the file at the path it prints; a change to a non-executed copy is INERT, in the same family as an e2e spec no gate runs. Three compounding causes, all confirmed by controlled A/B on the box: (1) the payload was UNBOUNDED — the gate's `claude -p` ran inside `cron.service`'s own cgroup and two of its pytest processes reached 4.9 GB and 2.3 GB RSS on a 7.6 GB box while every other process was under 52 MB (read the kernel's own task dump, it ranks everything: `journalctl -k | sed -n '/Tasks state/,/Out of memory/p'`); (2) `timeout N cmd` signals only its own process group, so anything the payload DETACHED survived and reparented to init **while staying charged to the launching unit's cgroup** — the tell is `cpuset=init.scope` with `task_memcg=/system.slice/cron.service` in the oom-kill line, and PID 1543545 born 07-26 22:30 was still resident when the kernel killed it 27 h later; (3) `OOMPolicy=stop` then converted each of those grandchild kills into a stop of the DAEMON. - **git reports a RACE and a PERMISSIONS fault in wording that reads like the other, and picking wrong costs days — classify by DETERMINISM, at failure time, because the evidence is usually gone by the time anyone looks (2026-07-30, CASE-20260730-9B4988):** the case was filed as "reads as a permissions bug, is really a git race, waved off twice". Half right, and the wrong half was load-bearing: BOTH faults are real and they need opposite fixes. `error: cannot lock ref 'refs/remotes/origin/master': is at X but expected Y` is the race — intermittent, a different SHA every time, gone next tick, retries genuinely help. `error: unable to unlink old '<path>': Permission denied` / `unable to create file '<path>'` + `fatal: Could not reset index file` is NOT that: it is deterministic against the same path on every attempt for hours (2026-07-09 12:30→15:30, seven consecutive gate runs, both retries each; again 07-30 00:02 and 00:32) and **no retry can ever win it** — reproduced on the box: 3/3 attempts rc=128 until ownership was repaired, then rc=0. Cause is root writing into an agent-owned clone: root cron jobs that `cd` into it (root-owned `__pycache__` — set `PYTHONDONTWRITEBYTECODE=1` + `PYTHONPYCACHEPREFIX` on every root job whose cwd is a repo) and root SSH sessions doing incident work in the same tree. **Why it keeps getting dismissed: whoever checks afterwards runs `find . ! -user agent`, gets 0, and concludes "not permissions" — the strays get cleaned up between the failure and the check.** agent-02 was carrying **673** root-owned paths at the moment of inspection and its `git reset --hard` had been failing for weeks. Fixes: `grotap-git-lock <repo> <cmd>` — ONE lock per clone at mode 0666 so root and agent contend on the same file, held across a whole fetch→checkout→reset sequence rather than per-command (a peer lands between your fetch and your reset otherwise); **three different locks are the same as no lock** — agent-06 had `/tmp/grotap-reconcile.lock`, `~/.review-gate.lock`, and a `*/5` writer with no lock at all, on periods sharing factors, so they collided on a fixed cadence (34 + 84 + 6 logged errors).
