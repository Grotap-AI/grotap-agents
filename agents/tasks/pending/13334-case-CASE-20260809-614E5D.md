## Context

## Requirements
LANE-3 — Lane cost verification + fallback-rate alerting: prove the saving is real and make the next silent leak impossible.

CONTEXT: the LANE-1 leak ran for weeks at ~9% of triage with nobody noticing, because a
lane failure is INVISIBLE by design — the cascade catches it, Claude answers, the user
sees a correct result, and only llm_usage_log knows. We are about to widen routing
substantially (LANE-2), which multiplies the blast radius of any similar failure. There
is currently no alert on lane fallback rate and no report answering "what did the hedge
actually save this month".

Existing surfaces to build on (read them first, do not duplicate):
- llm_usage_log (control plane): lane, task_key, model, ok, fell_back, cost_usd,
  input_tokens, output_tokens, cached_input_tokens, latency_ms, meta.
- GET /telemetry/llm-usage/summary and /trend already aggregate by service/model/brand.
- backend/app/providers/model_router.py `_record_usage` writes every row.

SCOPE:
1. A lane-economics report answering, per task_key and per lane, for a chosen window:
   calls, fallback rate, mean latency, total cost_usd, and — the number that matters —
   COST AVOIDED: what the Lane A/C calls WOULD have cost on Lane B at Sonnet rates,
   minus what they actually cost. Reuse the existing pricing table
   (backend/app/services/llm_pricing.py or equivalent — find it) rather than hardcoding
   rates. Lane C marginal cost is 0 (our hardware).
2. Publish it as a report per the house rule — R2 upload + a `report_definitions` row +
   the archive commit (ALL THREE; the row is the ACL, not a listing). Follow the
   existing report-publishing scripts under scripts/ for the exact mechanism.
3. Alerting: raise an HI hold when, over a rolling 6h window with a minimum call volume
   (pick a floor that avoids noise, e.g. >=20 calls), a lane's fallback rate for any
   task_key exceeds a threshold (start at 5%). Alert on the STATE TRANSITION, never on a
   heartbeat — a heartbeat-based alert cannot distinguish "healthy and quiet" from
   "dead". Include task_key, lane, rate, and the top meta->>'error' value in the hold
   body so the diagnosis is in the alert.
4. Include `finish_reason` (added by LANE-1) in the error breakdown — a spike of
   "length" is a token-budget regression, distinct from a provider outage.
5. Tests: fixture rows producing a known cost-avoided figure; a fallback-rate crossing
   raises exactly ONE hold (not one per evaluation); a below-floor volume raises none.

ACCEPTANCE: py_compile + tests green; the report renders with real prod numbers for the
last 30 days and is reachable through the normal gated report path; a simulated
fallback-rate breach creates exactly one HI hold and a return below threshold does not
create a second. Report the actual 30-day cost-avoided figure in the case result.
