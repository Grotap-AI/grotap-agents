# Task: Bug: frontend/ServersTabletsPage — MDM automations dropdown: field-name mismatch breaks selection & run.  File: fro

## Context
Component: frontend/ServersTabletsPage

## Requirements
MDM automations dropdown: field-name mismatch breaks selection & run.

File: frontend/src/pages/ServersTabletsPage.tsx (from CASE-20260724-8EAE3D).

DEFECT: The `Automation` interface and all three usages read `a.automation_id`, but GET /mdm/automations returns each row keyed `id` (backend `_fmt_automation` in backend/app/routers/mdm.py returns `id`, description, name, kind, payload, created_by, created_at, updated_at — there is NO `automation_id` field). Result: `a.automation_id` is `undefined` for every row → dropdown <option> key/value are undefined, `setSelectedAutomation(list[0].automation_id)` never sets a valid id, and runAutomation() POSTs to `/mdm/automations/undefined/run` (404). Feature is non-functional and is a regression from the previous working hardcoded dropdown.

FIX SCOPE (frontend-only, ~4 lines): in ServersTabletsPage.tsx rename the `Automation` interface field `automation_id: string` -> `id: string`, and update the three usages: `setSelectedAutomation(list[0].id)`, `key={a.id}`, `value={a.id}`, and label fallback `{a.name ?? a.kind ?? a.id}`. Do NOT touch the run-results mapping — it already correctly uses r.device_number / r.error_msg / results.devices and is confirmed matching the backend. Verify with `cd frontend && npx tsc --noEmit`.

CONTEXT: The rg10-flagged /api/v1/mdm prefix and d.number/d.message defects were already fixed in the 8EAE3D rebuild; only this id/automation_id mismatch remains.
