# Task: Bug: Platform — Print Cloud sweep marks managed (hand-registered) printers offline with no recov

## Context
No additional context provided.

## Requirements
Print Cloud sweep marks managed (hand-registered) printers offline with no recovery path

DEFECT (latent, shipped to master 2026-08-14 as part of CASE-20260814-E39013 / CASE-20260814-402184)

backend/app/services/print_cloud_computer_sweep.py -> _sweep_computers(), "Pass 1b" UPDATE
sets print_cloud.printers.state = 'offline' for EVERY printer whose computer is offline:

    UPDATE print_cloud.printers SET state='offline'
     WHERE tenant_id=$1 AND state='online'
       AND computer_id IN (SELECT id FROM print_cloud.computers WHERE tenant_id=$1 AND state='offline')

The ONLY code path that sets printers.state back to 'online' is report_printers() in
backend/app/routers/print_cloud_agent.py (~line 288):

    INSERT INTO print_cloud.printers (... state) VALUES (..., 'online')
    ON CONFLICT (computer_id, name) DO UPDATE SET ..., state='online', ...
    WHERE NOT print_cloud.printers.managed        <-- excludes managed rows

Hand-registered network printers (managed = TRUE, created with state='online' at
backend/app/routers/print_cloud.py ~line 428) are excluded by that WHERE clause. Their state
is NOT agent-reported, so once the sweep flips them to 'offline' nothing ever restores them.
The heartbeat endpoint (print_cloud_agent.py ~line 387) only restores computers.state.

TRIGGER: any 15-minute heartbeat gap (laptop asleep, flaky link, agent restart) on a computer
that hosts a managed TCP printer. Permanent from then on.

CUSTOMER-VISIBLE EFFECT (display + default-selection; printing is NOT blocked):
frontend/src/pages/print-cloud/print-cloud-api.ts:334 and print-cloud-labels-api.ts:225 compute
    online: p.state === 'online' && p.computer_state === 'online'
so a managed ZPL/TPCL label printer permanently shows:
  - "(offline)" suffix in the printer picker  (PrintCloudLabelDesignerPage.tsx:651 and :1540)
  - a red/offline OnlineChip               (PrintCloudPrintersPage.tsx:445)
  - and stops being auto-selected as the default printer (PrintCloudLabelDesignerPage.tsx:201)
even after its host computer is back online and heartbeating normally.
PrintCloudPrintPage.tsx gates only on computer_state, so the print path still works — this is a
misleading-status defect, not an outage.

FIX SCOPE (preferred option (a) — minimal and consistent with existing ownership rules):
(a) In backend/app/services/print_cloud_computer_sweep.py, exclude managed printers from the
    pass-1b UPDATE by adding  AND NOT managed  to the WHERE clause. Rationale: a managed
    printer's state is user-owned, never agent-reported, and the codebase already treats managed
    rows as off-limits to discovery (see the "Hand-registered network printers ... are owned by
    the user, not by discovery" comment in report_printers()). If the sweep cannot restore a
    row, it must not modify it.
(b) Alternative if (a) is rejected: restore managed printers to 'online' when their computer
    transitions back to online in the heartbeat endpoint. More moving parts; do NOT do both.

ALSO REQUIRED:
  - Update the module docstring in print_cloud_computer_sweep.py, which currently claims
    "Their printers are set to 'offline' in the same pass" without the managed carve-out.
  - Add a regression test: computer goes offline -> managed printer state unchanged; computer
    returns online -> non-managed printer restored by report_printers(). Suggested location
    alongside the existing sweep tests.

DO NOT touch the pass-1 computer offline-marking or computers.updated_at — both are correct and
deliberately preserve the last-heartbeat clock.
