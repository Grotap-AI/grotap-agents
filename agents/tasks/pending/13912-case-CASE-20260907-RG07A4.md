# Task: Bug: Platform — CI py3.5 compat guard rejects legitimate stdlib imports  DEFECT ON MASTER (merge

## Requirements
CI py3.5 compat guard rejects legitimate stdlib imports

DEFECT ON MASTER (merged knowingly with this case filed, from CASE-20260907-BF041E,
master 61e77530). Filed under the freeze exception because it BLOCKS a priority-surface
case: CASE-20260907-BD0530 cannot pass CI until it is fixed.

.github/workflows/ci-backend.yml, step "Build validate — reader_agent.py", walks the AST of
agent/reader-agent/reader_agent.py and fails on any import whose top-level module is not in
a hardcoded set:
    allowed = {'argparse','json','logging','os','random','socket','subprocess',
               'sys','time','urllib','uuid'}
The step is labelled "Non-stdlib imports", but that set is not "the stdlib" — it is exactly
the modules reader_agent.py happened to import on the day the check was written. Any new
stdlib import fails CI with a message saying it is not stdlib, which is false and sends the
next agent hunting for a dependency problem that does not exist.

CONFIRMED IMPACT: CASE-20260907-BD0530 (clock guard) is in flight and imports email.utils,
ssl and datetime. All three are stdlib on every supported version; all three are rejected by
this check. Running the step's exact code against that branch fails with:
    Non-stdlib imports: ['email.utils', 'ssl', 'datetime']

FIX SCOPE:
 1. Replace the hardcoded allowlist with a real stdlib test:
      import sys
      stdlib = getattr(sys, 'stdlib_module_names', None)
    and fail only when the top-level module is not in that set. sys.stdlib_module_names
    exists on Python 3.10+, which is what CI runs — this checks the actual property the
    step claims to check.
 2. Keep a small explicit DENYlist for stdlib modules the reader agent must not use if any
    are genuinely unwanted, rather than an allowlist of the ones it currently uses.
 3. If sys.stdlib_module_names is unavailable, fail the step loudly rather than falling back
    to a narrow allowlist — a compat guard that silently narrows is how this happened.
 4. Fix the error message to say which module and why, e.g.
    "import 'requests' is not in the Python standard library".
 5. Keep everything else in that step as-is: py_compile and the f-string grep are correct
    and are doing real work. Do not weaken the Python 3.5 source rule.

NOTE the guard checks the SOURCE against the CI interpreter's stdlib, not against Python
3.5's. A module that is stdlib now but absent in 3.5 would pass. If that matters, pin the
comparison to a checked-in list of 3.5 stdlib module names and say so in the step name.

VERIFY: run the step's code against agent/reader-agent/reader_agent.py with email.utils, ssl
and datetime imported and confirm it passes; add `import requests` temporarily and confirm it
still fails.
