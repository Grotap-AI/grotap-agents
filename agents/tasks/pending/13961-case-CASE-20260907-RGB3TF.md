FILED BY THE REVIEW GATE 2026-09-07. This is PRE-EXISTING RED on master — it is not caused by
CASE-20260907-0AF156 or D70D34 (both merged today; both were verified against this same baseline
and neither changed the failing block). Reproduce on master with:
    cd platform/mobile/scantap && npx jest services/__tests__/syncQueue.test.ts
  -> Tests: 2 failed, 4 passed, 6 total     (before today's merges)
  -> Tests: 2 failed, 12 passed, 14 total   (after them; the 8 new tests all pass)

ROOT CAUSE (already traced — do not re-derive it). services/__tests__/syncQueue.test.ts:64
    function makeTags(count, batchId) => ({ ..., epc: `EPC${String(i).padStart(8, '0')}`, ... })
produces EPCs like "EPC00000000": 11 characters, and 'P' is not a hex digit. syncPayload.ts:75
    if (classifyEpcFault(tag.epc) !== null) { malformedEpcs.add(tag.epc); continue; }
therefore DROPS every fixture tag inside aggregateTagRecords(), so deriveChunkingIdentity()
returns recordCount 0 and chunkRecords() yields a single empty part. The two failures are the
visible half of that:
  * "resumes at the recorded part index and skips already-confirmed chunks" — markBatchProgress
    called with (id, 1, {chunkSize: 2, recordCount: 0}) instead of (id, 3, {..., recordCount: 6}).
  * "restarts from part 0 when the stored mark identity does not match the current chunking" —
    1 POST instead of 3.
The other four tests in the file pass only because their assertions do not depend on record count;
they are asserting against an empty payload and would keep passing if uploadBatch() were gutted.
The EPC guard landed after these tests were written and silently hollowed them out.

The PRODUCTION code is correct — classifyEpcFault, aggregateTagRecords, deriveChunkingIdentity and
resumeStartPart are all behaving as designed. Do NOT "fix" syncPayload.ts or syncQueue.ts. The
fixture is what is wrong.

FIX:
 1. makeTags() must emit EPCs that pass classifyEpcFault: 24 uppercase hex characters, unique per
    tag. e.g. `('CAFE' + String(i).padStart(20, '0')).toUpperCase()`. Derive the width from
    _ACCEPTED_EPC_LENGTHS / the classifier, do not hardcode a number the classifier could change
    out from under.
 2. Re-run and confirm 14/14 pass, and that the two resume tests now assert the real values
    (partsSent 3, recordCount 6, 3 POSTs).
 3. MUTATION CHECK — required, because "N passed" is exactly what a toothless suite looks like and
    this suite has been one for weeks. Prove each of the 6 original tests can fail: temporarily
    break resumeStartPart() to always return 0, confirm the resume tests go red; restore; then
    break markBatchSynced()'s call site, confirm the sync assertions go red. Paste both outcomes.
 4. Add one test that a genuinely malformed EPC IS filtered — that behaviour is real and is
    currently untested, which is why the fixture bug went unnoticed.
