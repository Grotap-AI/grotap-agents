## Requirements
SCANM-SYNC-A: Auto-sync a saved scan batch, and make an unsent batch impossible to miss

PRIORITY SURFACE: Scan M mobile (tablet). App lives at platform/mobile/scantap/
(repo-relative: <repo-root>/platform/mobile/scantap — note the DOUBLED platform/
segment; C:/1Claude/platform/mobile is a DIFFERENT app). Expo / React Native.

PROBLEM (measured on the owner's tablet, grot001 / Samsung SM-X930, 2026-09-06):
five saved batches were sitting on the device, none of them ever sent:

    ZLRRW111   80,993 reads   3:54:11 PM PDT
    9ZLXNMZC  530,224 reads   3:19:34 PM PDT
    XSCNRP44   20,310 reads  12:13:39 PM PDT
    UAR0NQIQ        0 reads  12:04:06 PM PDT
    L5RAG0BM      640 reads  11:24:04 AM PDT

631,527 tag reads stranded for five hours. The control plane's last scan
session was 2026-09-06 18:23 UTC (11:23 AM PDT) — i.e. everything from the
11:24 AM batch onward never left the tablet. The owner reported this to us as
"the tags aren't reading" and "the encoding isn't coming up on the scanner".
It was neither: the encoding was correct and the tags read fine. The data
simply never arrived. Four of those batches were synced by hand during the
investigation and every one uploaded first try, so the transport is healthy —
nothing had ever asked it to run.

WHY IT HAPPENS: finishing a scan writes the batch locally and shows "Batch
saved — 80993 tag(s). Go to the Send tab to sync." Then the app stops. Sending
requires the operator to (1) open the Send tab, (2) TAP EACH BATCH to select
it — the button reads "Send to Cloud" and does nothing at all with zero
selected — and (3) tap "Send to Cloud (N)". There is no auto-sync, no retry, no
badge, and no nagging. A batch that is never selected is invisible forever, and
the operator has no signal distinguishing "synced" from "sitting here".

RELEVANT CODE (do not re-derive):
- app/(tabs)/send.tsx (~990 lines) — the batch list, selection, and the chunked
  send loop. buildSections() splits on `!b.synced`; the card is `disabled={item.synced}`
  and selection is a tap on the card. postChunkWithRetry() already does per-chunk
  retry with exponential backoff; the loop already supports cooperative cancel and
  never interrupts a POST already on the wire.
- services/api.ts — postScanSession() -> POST /scantap/scans.
- services/syncPayload.ts — chunking identity + MAX_RECORDS_PER_REQUEST.
- db/database.ts — `batches` table already carries everything resume needs:
  synced, synced_at, synced_parts, synced_chunk_size, synced_record_count.
  synced=1 is written ONLY after every chunk is confirmed, and synced_parts lets
  a partial send resume. Do not change that durability contract.

SCOPE:

1. AUTO-SYNC. When a batch transitions to closed/saved, queue it for upload and
   run the EXISTING chunked send path against it — do not write a second
   transport. Resume semantics stay exactly as they are (synced_parts +
   synced_chunk_size); an auto-sync that dies mid-way must be indistinguishable
   from a manual one that dies mid-way.
   - Never auto-sync a batch that is still recording.
   - Serialize: one upload at a time, oldest batch first. A 530k-read batch must
     not starve a 640-read one behind it forever — but do NOT reorder by size,
     the operator's mental model is chronological.
   - Reuse checkCloudReachable() before starting; a failed reachability check is
     a retry, not an error banner.

2. RETRY SCHEDULE. On failure leave the batch unsynced and try again on:
   app foreground, connectivity regained, and a bounded backoff timer. Cap the
   backoff (e.g. 5 min) so a tablet left on a bench catches up on its own. Never
   retry so aggressively that a yard tablet on bad LTE burns its battery.

3. MAKE UNSENT STATE LOUD. Today it is silent, which is the whole defect.
   - Numeric badge on the Send tab icon = count of unsynced batches.
   - A persistent banner on the Scan tab whenever an unsynced batch exists,
     showing the count AND the age of the oldest ("3 batches waiting — oldest
     5h"). Age is the part that would have caught this.
   - Replace the post-scan "Go to the Send tab to sync" copy with what is
     actually happening: "Syncing…", "Synced", or "Waiting for signal — 3
     batches queued".

4. KEEP THE MANUAL PATH. "Send to Cloud" stays, for force-retry and for an
   operator who wants to push now. With auto-sync on it becomes a retry button,
   not the only door. Also fix the dead-button case: with zero batches selected
   the button must either be disabled or select-all — silently doing nothing on
   a tap is what trained the owner to think sync was broken.

5. SETTINGS TOGGLE, default ON. An operator on metered data may want it off;
   when off, the badge and banner from (3) still show.

OUT OF SCOPE: the backend ingest endpoint (POST /scantap/scans is fine — it
accepted every batch we pushed by hand), the reader services, the label/encode
path, and branding. Do NOT rename ScanTap -> Scan M.

## Clarifications
- Q: When auto-sync is toggled OFF by the operator, should batches already queued for sync be cancelled, or should they finish their current upload and then stop queuing new ones?
  A: Let the in-flight batch finish, then stop queuing new ones. Do not cancel an upload already on the wire -- reuse the cooperative-cancel contract send.tsx already implements for the manual path, which explicitly never interrupts a POST in flight. A batch interrupted anyway (app kill, signal loss) stays resumable through synced_parts / synced_chunk_size, so nothing is lost either way. With the toggle OFF the badge and banner from scope item 3 KEEP showing the backlog and its age -- switching off auto-sync must not also switch off the warning, or we are back to silent stranded batches.
- Q: For the backoff timer cap (e.g. 5 min), should this reset per batch, or is it a global ceiling across all retries in a session?
  A: Per batch. Each batch keeps its own attempt counter and its own backoff, reset on success. A global ceiling lets one poison batch throttle every healthy batch queued behind it -- with 530k-read batches in the real queue that could stall a day's scanning. Cap at 5 minutes per batch. App-foreground and connectivity-regained bypass the timer and trigger one immediate retry, because those are real signals that the world changed rather than blind polling.
