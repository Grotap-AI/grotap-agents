# Task: Bug: Platform — Print Cloud drops the copies and duplex the operator set.  The print page collec

## Context

## Requirements
Print Cloud drops the copies and duplex the operator set.

The print page collects copies from 1 to 999 and duplex of none, long-edge, or short-edge. The submit function in frontend/src/pages/print-cloud/print-cloud-api.ts does not send them. The print job record does not store them. The agent claim payload does not include them. The three agent programs then print with options that only set raw and title, so every job is one copy and one-sided. platform_print already honors options.copies and a truthy options.duplex.

Keep as one case. Do not decompose.

Ship it as one change:
- Add print job columns copies (integer, default 1) and duplex (text, default none) in a new migration file v026 under both migrations/apps/print-cloud and ingestion-worker/migrations/apps/print-cloud. Do not edit v001 through v025.
- Accept those fields on the print job submit route, store them, and return them on the job list.
- Include them on the agent claim payload in backend/app/routers/print_cloud_agent.py.
- Pass them into platform_print from agent/print-cloud-agent/print_cloud_agent.py, backend/app/static/print_cloud_agent.py, and agent/print-cloud-windows/src/pc_worker.py. Those three programs must stay in agreement. copies is an integer. duplex none means off. long-edge and short-edge both use the existing truthy duplex path, which is long-edge. Do not add a printer command.
- The job list must show the stored copies and duplex, not a hardcoded 1 and none.
- Tests: a job submitted with copies 3 and duplex long-edge is stored, listed, and claimed with those values, and all three agent programs pass copies 3 and duplex on. duplex none stays off.

Do not change the pipeline, sign-in screens, printer commands, or scan screens.
