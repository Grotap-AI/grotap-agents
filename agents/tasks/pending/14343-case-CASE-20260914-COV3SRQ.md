WHAT LANDED: platform/mobile/scantap/services/locationsCache.ts gained a `sides_required`
column (INTEGER NOT NULL DEFAULT 2), a required `sides_required: number` on the CachedLocation
interface, an optional `sides_required?: number | null` on the CloudLocation input interface,
and pass-through in replaceCloudLocations().

DEFECT: nothing ever supplies a non-default value, so every cached location reads
sides_required = 2 forever, including the one-road locations the COV-1 backend derives as 1.
Verified end to end:
  - The backend DOES return it: backend/app/routers/scantap_core.py line ~3226 emits
    "sides_required" on the /scantap/locations rows (defaulting to 2 pre-v037).
  - platform/mobile/scantap/services/locationsSync.ts syncInner() (line ~64) maps the API rows
    into replaceCloudLocations with an EXPLICIT 5-key object literal —
    location_id, location_name, zone, site, geo_points — and drops everything else.
  - platform/mobile/scantap/services/api.ts: the RfidLocation interface has no sides_required,
    so even if the map were spread the field would not be typed through.

FIX SCOPE (two files):
1. api.ts — add `sides_required?: number | null` to the RfidLocation interface.
2. locationsSync.ts — add `sides_required: r.sides_required ?? null` to the object literal at
   line ~64.

ACCEPTANCE: extend test/locationsSync.test.ts — its existing
`expect(replaceCloudLocations).toHaveBeenLastCalledWith([...])` assertion (line ~48) pins the
exact object shape, so it must be updated and must FAIL if the new key is dropped again.
Add a case where the API returns sides_required=1 and assert the cached row reads 1, NOT 2 —
a test that only ever sees the default value 2 cannot tell the wiring from the default and is
worthless here. Verify with `npx jest` and `npx tsc --noEmit` from platform/mobile/scantap.
