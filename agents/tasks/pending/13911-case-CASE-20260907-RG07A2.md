## Requirements
Reader agent unit: ProtectSystem=strict makes /home/root read-only

LATENT DEFECT in agent/reader-agent/grotap-reader-agent.service (merged to master as
CASE-20260907-767DDC, 15e7c6d2). Merged deliberately — the unit is correct for the daemon
as it exists today — but it will silently break the next commands in this wave.

The unit sets ProtectSystem=strict and carries this comment:
    # ProtectHome intentionally absent — CSL configuration lives in root's home
    # (/home/root), which ProtectHome would make inaccessible to the daemon.
Omitting ProtectHome does make /home/root READABLE, so the comment is right as far as it
goes. But ProtectSystem=strict mounts the ENTIRE filesystem hierarchy read-only except
/dev, /proc and /sys, with RW carve-outs only for StateDirectory (/var/lib/grotap-reader)
and LogsDirectory (/var/log/grotap-reader). /home/root and /etc are therefore read-only.

Today that is harmless: reader_agent.py only READS /etc/grotap-reader/config.json,
/etc/cs463-version and /proc/uptime, and writes only state and logs. It stops being
harmless as soon as the write-side commands in the v100 allowlist are implemented —
write_config, apply_profile, restore_config and firmware_update all have to write reader
configuration on the reader itself. Those will fail with EROFS, and the failure will look
like a reader/CSL problem rather than a unit-file problem, because the sandbox is invisible
from inside the process.

FIX SCOPE: add an explicit read-write carve-out for the paths the agent must write, e.g.
    ReadWritePaths=/home/root
(plus /etc/grotap-reader only if config is written back, which it is not today), keeping
ProtectSystem=strict. Do NOT downgrade to ProtectSystem=full or drop the hardening — the
carve-out is the correct mechanism and is available on the target systemd 237
(ReadWritePaths= has existed since v231).

While in the file, confirm the exact CSL config path on a real CS463 rather than assuming
/home/root, and cite it in the comment. If CSL config actually lives elsewhere, the
carve-out and the existing ProtectHome comment should both name the real path.

VERIFY on a systemd 237 reader: systemd-analyze verify the unit, then as the running
service attempt a write under the carved-out path and confirm it succeeds while a write
to an uncarved path still fails.
