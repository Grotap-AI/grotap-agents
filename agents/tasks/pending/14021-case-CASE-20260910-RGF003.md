DEFECT: option (a) says to normalize app_slug 'platform' -> 'platform_core' in resolve_screen_context_a "before the database lookup". That function (backend/app/services/screen_context.py:47) makes TWO lookups: (1) `SELECT app_id, name FROM apps WHERE slug = $1` and (2) `SELECT ... FROM screen_contexts WHERE app_slug = $1 AND route_pattern = $2`. MEASURED: the apps table has NO row with slug='platform_core' (only slug='platform'). So aliasing before BOTH lookups makes the apps lookup return None and the function returns {"is_fallback": True, "reason": "app_not_found"} for every platform route — fallback filing continues, app_name is lost, and the failure reason silently changes to look like a different bug.

Also correct the row counts — measured 2026-09-10 the table holds 178 rows across 29 distinct app_slugs, of which 75 (not 73) are 'platform_core' and 1 is 'platform' — and reconcile the doc's internal 73/72 inconsistency.
